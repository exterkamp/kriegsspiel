# Decision log

Short records of decisions made, why, and what is still open. Newest at the bottom. Detail lives in the linked docs.

## D1: LLM umpire on a server, hybrid adjudication

**Decision.** A deterministic engine owns state, movement, line of sight, combat and dice. The LLM parses free-text orders, makes bounded judgment calls, and narrates per-side reports. It never edits state directly, and dice are rolled by a seeded server RNG.
**Why.** A pure LLM umpire is inconsistent and unauditable (the free-Kriegsspiel failure mode). Related LLM wargaming work also converges on this pattern.
**See.** [design.md](design.md), [research.md](research.md)

## D2: The player's interface is a general's HQ

**Decision.** Players see no HUD or minimap. Everything arrives as paper: dispatches, reports, rosters, a journal. Their map shows only what they or their staff marked.
**Why.** It makes fog of war, stale information and delegation the game, and it matches the original Kriegsspiel.
**See.** [hq-interface.md](hq-interface.md)

## D3: Hybrid rendering: Three.js table + Svelte desk

**Decision.** A Three.js scene with a **flat** historical map on a table and 3D wooden-block pieces, plus a Papers Please-style 2D desk built in HTML/Svelte. Phaser is dropped.
**Why.** The game is mostly documents plus one map. A DOM UI is much better for text and drag-and-drop, and a 3D table gives the physical Kriegsspiel feel. A flat map avoids needing elevation data.
**Alternatives considered.** Phaser, PixiJS, Babylon.js, Godot web export, full 3D room, fully 2D desk.
**Consequence.** The earlier Phaser prototype is abandoned and removed from the repo. The new engine and client are written fresh against the continuous-clock design. (The old code is kept outside the repo as a reference only.)
**Client structure.** `client/src/table/`: `buildSceneState(view, map, facings)` is a pure `SideView` to `SceneState` function; `TableScene` reconciles the Three.js scene to it (idempotent); picking is pieces by mesh raycast, then the map plane. Facing is not yet on the wire, so the client takes it as a side input (default N). Runs from a fixture with no server.
**See.** [hq-interface.md](hq-interface.md), [architecture.md](architecture.md)

## D4: Continuous game clock with an adjustable ratio, not turns

**Decision.** Game time is tied to wall-clock time at a per-game ratio (1:1, 4:1, 12:1, custom). Couriers and battles take real hours at 1:1. The engine is a continuous-time event simulator that never reads the wall clock. Manual-step and fast-forward modes are required, for testing and for optional turn-based play.
**Why.** It makes order lag and delegation real, and one engine supports every pace. An earlier turn-based design with deadlines was superseded.
**Consequence.** An **LLM barrier** stops game time from advancing past an unresolved LLM result. Inputs are logged for deterministic replay.
**Open.** The default ratio is chosen after the first scenario's pacing is measured.
**See.** [architecture.md](architecture.md), [gameplay.md](gameplay.md)

## D5: Pause by unanimous vote

**Decision.** All human players across all sides can vote to pause. One "no" or a timeout cancels it (hosts may allow a majority). A paused game allows reading and drafting, but signed orders dispatch on resume. After server downtime the game restarts paused.
**Suggested, not confirmed.** Emergency hold: a short, limited, single-player clock stop that lapses unless ratified.
**See.** [architecture.md](architecture.md), [gameplay.md](gameplay.md)

## D6: Collaborative play with roles and shared drafts

**Decision.** Each side is a group of roles (commander, chief of staff, intelligence, quartermaster, subordinate commanders). Orders are shared drafts that anyone can propose to and the commander signs and stamps. An LLM staff check shows how a subordinate would read a draft. Empty roles are filled by the LLM.
**Open.** Default hierarchy is assumed to be shared HQ, with chain-of-command as an option. Command level is assumed to be brigades and battalions.
**See.** [gameplay.md](gameplay.md)

## D7: Wire format is zod schemas in `packages/protocol`

**Decision.** Every command and server message carries a version field `v` and is validated with strict zod schemas (unknown fields rejected). Types are inferred from the schemas. The package exports no master-state types.
**Why.** One source of truth for server and client, and strict parsing keeps hidden state from leaking onto the wire.
**See.** [architecture.md](architecture.md), `packages/protocol/README.md`

## D8: Engine world model and scenario data

**Decision.** Game time is an integer count of game milliseconds. The map is continuous vector terrain (see D15; it began as a tile grid). Scenarios are plain JSON-compatible data, and `loadScenario` validates them and builds the initial `GameState` at t=0. "Hold the Bridge" is 4000 x 3000 m, with 3 units per side. Blue wins by holding the bridge for 180 game minutes, and Red wins by taking it. A test greps the engine sources for wall-clock and ambient-random calls.
**Why.** Integer time keeps replay exact, and validated plain data keeps state JSON round-trippable.
**See.** [architecture.md](architecture.md)

## D9: First scenario (proposed, maintainer to confirm)

**Proposal.** Ball's Bluff, 21 October 1861, recommended over Podol (1866) and Wissembourg (1870).
**Why.** Smallest of the three, the only one with a period map and order of battle already located, public-domain English sources, and a river-crossing bottleneck that exercises couriers and fog of war.
**Map.** Verified for #84: the 1861 Corbett seat-of-war map at the Library of Congress is public domain with no usage terms beyond a credit line. Scan, holder, URL and licence are in `assets/maps/sources.json`.
**Open.** The maintainer has not confirmed. The Lander/Gorman order-of-battle conflict must be checked.

## D10: Movement is step events over planned routes

**Decision.** A move order plans a route (a list of free points, from where the unit stands when the order fires) and schedules one `move.step` event per leg, firing when the unit reaches the end of the leg. Legs longer than 100 m are split into equal steps of at most 100 m, so contact, range and the objective are checked at least that often. A leg takes its length times the ground's move-cost multiplier times the unit's march rate: road 0.5, open 1, wood 3, bridge 1; a river is impassable, so the bridge is the only crossing. Units have a `kind` (infantry, cavalry, artillery) with a march rate in game ms per metre of cost-1 ground (infantry 100 m/min, cavalry 300, artillery 66.7). Orders are queued events (`intent.move`, `intent.halt`) so they replay. A newer intent makes pending steps stale (they check the unit's `move` intent `startedAt`), and an interrupted unit stays at the last waypoint it reached. An order that cannot be carried out (unreachable destination, or an unknown unit, which emits `order.rejected`) is reported and leaves any march already under way alone.
**Why.** Event-driven steps keep quiet marches free and give the same result under any `advanceTo` chunking.
**Routing (continuous space, D15).** `findPath` (`packages/engine/src/navigation.ts`) is a visibility graph built per query and private to the engine: free waypoints just outside the corners of woods, marsh and water, around the ends and bends of rivers, along roads and on bridges and fords, plus the start and goal. Two waypoints are joined when the straight line stays on passable ground; the edge costs what the ground along it costs, and A* (ties broken by smaller h, then node index) picks the cheapest chain, so routes are free legs at any angle that prefer a road to a wood when it is faster and cross a river only at a bridge or ford. Unit width matters: a bridge or ford that spans impassable ground carries only units no wider than twice its radius (or its width), so a column (frontage about 10 m) crosses a 50 m bridge that a line (about 80 m) cannot. A bridge over open ground constrains nobody. An order that fails only for width emits `unit.moveBlocked` with `tooWide: true`. Changing formation (`issueFormation`, event `intent.formation`) stops the unit and takes game time (infantry 2 min, cavalry 1, artillery 3), after which `formation.done` swaps the footprint and emits `unit.reformed`; a newer order cancels it.
**Interruption.** A marching unit records its current `leg` (where it left, where it arrives and when). A new intent, halt or formation change stops it where it has got to, interpolated across the ground types along the leg (`positionAt`), so re-issuing orders loses no progress. `center` itself still moves only at the end of each step of at most 100 m, so combat and sight see the last step reached.
**Placement.** `validatePlacement(world, { unitId, center, facing?, elapsedMs })` checks physical plausibility only, for the umpire's free placement: inside the map (footprint included), centre and sub-positions on passable ground, footprints overlapping by no more than `OVERLAP_TOLERANCE_MM` (1 m; loose shapes exempt), and no further than the unit could march along the cheapest route in `elapsedMs`. It returns `accept`, `clamp` (the point reached along the route when time runs out, itself re-checked) or `reject`, each with reasons. It snaps to nothing and changes no state.
**Open.** The graph is an approximation of any-angle optimal routing: a route bends at corners with a 1.5 m margin and does not refract at ground boundaries, so it can be slightly dearer than the true optimum across a wood edge. The graph is rebuilt per query, `carries` re-samples the ground around each bridge or ford centre every time a leg meets one (a per-query feature-width map would make that flat), and A* scans its open list linearly (fine for scenario-sized maps; add a heap and a cache if maps grow). Width is only checked at bridges and fords, not at gaps between a wood and a river. Ordering a reforming unit back to the formation it still has cancels the reform where it stands. A reforming unit may end overlapping a neighbour, and the umpire's placements are not yet wired to a command. Units may overlap on the march (no collision or stacking rules yet), and facing does not follow the march. Slopes and pace (march/quick/forced) are not modelled. Rates are a first pass, not the 1824 movement table.
**See.** [architecture.md](architecture.md)

## D11: Orders are couriers carrying intents

**Decision.** An `Order` (id, side, target unit, issue time, original text, parsed `OrderIntent`s) is queued with `issueOrder` as an `order.issue` event. When it fires, a courier route is planned from the side's `hq` (a new `Side` field, validated on passable ground) to where the unit stands, using the same route planner as movement; delivery time is the route cost times `COURIER_MS_PER_METRE` (400 m/min on open ground, so 800 on roads). An `order.deliver` event fires then and the unit adopts the intent: `move`, `withdraw` (a retreat that marches and then idles) or `hold` (march to the point if elsewhere, then hold). Until delivery, and after it, the unit keeps its standing intent. Orders to a missing, destroyed (strength 0) or enemy unit, or with no courier route, emit `order_failed` with a reason and change nothing; delivery emits `order_delivered`. The unit is checked again at delivery, so a unit destroyed in the meantime also fails.
**Why.** Orders lag by real game time, and everything stays an event, so replay and chunking guarantees hold.
**Open.** `order_delivered` is emitted even if the unit then cannot march (`unit.moveBlocked`, destination unreachable from where it stands); the two events are not linked yet. The courier route is fixed when the order is issued from the unit's position then, not chased as the unit moves, and couriers cannot be intercepted. Only the first parsed intent is adopted; conditional and timed intents, and `attack` as a courier-carried intent (D12 has the direct `issueAttack` order), are not yet modelled. Strength 0 stands in for "destroyed" until combat decides how units are removed.
**See.** [architecture.md](architecture.md), [gameplay.md](gameplay.md)

## D13: Contact, combat ticks and victory

**Decision.** Opposing active units are in contact when either can reach the other: infantry 200 m, cavalry 100 m, artillery 400 m between unit centres (placeholders). Every movement step schedules a `combat.check`; the first contact emits `contact.begin` and starts a chain of `combat.tick` events every 2 game minutes, which ends (`contact.end`) at the first tick with no contact. A tick lets each active unit fire once, at its `attack` target if reachable, else the nearest enemy. Casualties are `strength x rate x (d6 / 3.5) x morale factor x (1 - cover)`, where cover is the terrain cover at the target's centre and stay fractional; all hits in a tick use start-of-tick strengths, and dice come from the seeded RNG in unit order. Losses cut morale (2 points per percent of strength lost); below 25 a unit breaks, becomes `withdrawn`, walks to its start point (`home`) and takes no further part. Units at 0 strength are `destroyed`. `attack` is an order (`intent.attack`): the unit marches on the target, stops in range, and re-plans whenever the target moves out of reach (while marching or after stopping; each target step triggers a `combat.check`). Each shot is a structured `combat.fire` event. Victory is a single `game.end` event with a reason: `objective-taken` (only the attacker's active units stand within 30 m of the objective, checked at once), `objective-held` (the clock reaches `holdMs` with the objective not taken), `eliminated`, or `withdrawn` (a side has no active units). `startGame` arms the clock deadline (at once if the clock is already past `holdMs`); after `game.end` combat and victory handlers do nothing.
**Why.** Ticks only run during a fight, so quiet marches stay free, and every effect is an event handler, so replay and chunking stay exact.
**Open.** All numbers are placeholders until the Epic #2 tables. "Holds" is measured from game start, so the defender need not be on the bridge. Broken units never rally; marching and withdrawing units still fire; no friendly-fire or line-of-sight rules; units and movement do not stop at `game.end`.
**See.** [architecture.md](architecture.md), [gameplay.md](gameplay.md)

## D12: Visibility is a pure filter over per-side intel

**Decision.** `viewFor(world, side, now)` in `packages/engine/src/visibility.ts` is the only function that turns master state into an `EngineSideView`. A unit sees an enemy within its sight range (infantry and artillery 600 m, cavalry 800 m) when no sight-blocking ground (concealment 1, such as a wood) lies on the straight line between their centres; a unit in or looking from a wood sees or is seen only within 200 m. A repeating `intel.scan` event (every game minute) records sightings in `GameState.intel[side]` (last-known contacts and reports), and files a contact report the first time an enemy comes into sight. `intel.report` events file unit-lost and order-delivered reports. Every report is delivered `COURIER_DELAY_MS` (10 game minutes) after it happened, and the view shows it with its age. Enemy size is a coarse phrase, never a number. Last-known contacts show the position where the enemy was seen, its age, and an uncertainty radius that grows 100 m per minute of age, capped at the map's longer side. Views speak metres; a visible enemy also shows its facing, formation and footprint, the footprint only to the nearest 10 m because it follows from strength.
**Why.** Keeping memory in state makes stale contacts replayable, and one filter function makes the leak tests meaningful.
**Open.** The `EngineSideView` is not yet mapped to the protocol `SideView` (no clock, dispatches or supply); tracked in #109. The courier delay is a flat constant, not distance to HQ. Sight ignores facing, weather and night. Contacts are never pruned, not even for destroyed enemies; tracked in #110.
**See.** [architecture.md](architecture.md)

## D15: Continuous space, no grid

**Decision.** Maps are not square or tile based. The world is a continuous 2D plane in metres (x east, y south, origin at the north-west corner) with map bounds. Master state stores every position and length as an integer number of millimetres, so serialisation and replay are exact; scenarios are authored in metres and quantised on load. There is no cell snapping and no adjacency rule anywhere in the model or protocol. A unit has a `center`, a compass `facing` in radians (0 north, clockwise), a `formation` and an oriented `footprint` (`frontage` x `depth`) that the formation gives by default; a loose formation (a skirmish line along a treeline, an arc) also lists `shape` sub-positions as offsets in the unit's own frame. Units may sit at any position and facing in any arrangement. Terrain is vector features: polygons (woods, marsh, water, fields), polylines with a width (roads, rivers, streams) and points with a radius (bridges, fords, buildings), each with a move-cost multiplier, cover, concealment, a height tag, passability and a layer; where features overlap the higher layer decides the ground (road over wood, river over road, bridge over river). The engine offers `terrainAt(point)`, `featuresAlong(segment)` and `featuresIn(polygon)`. The umpire may place units in any configuration subject only to the engine's plausibility checks: the centre, sub-positions and footprint lie on the map, the centre and sub-positions are on passable ground, and footprints do not overlap (loose shapes are exempt, as their rectangle is only a bound). Any spatial index is a private optimisation and does not leak into the model or protocol.
**Why.** The owner's direction: Kriegsspiel is loose, and the judge decides what is realistic. A grid would force every order and every placement through cells.
**Open.** Visibility and combat are reworked for continuous space in separate tasks; movement is reworked (D10: visibility-graph routing, mid-leg stops, formation width, placement validation), but sight is a straight line through features, and combat measures range between unit centres and takes cover from the ground under the target's centre (footprints, facing and flanks are not used yet). The client table still draws a tile display map from the wire's metres (a stopgap scale in `client/src/table/sceneState.ts`); redrawing it from the vector map is a follow-up. Footprints per man are a first pass and cavalry and artillery frontages are not from the rules tables. This entry was proposed as D10 in the issue; D10 to D14 were already taken.
**See.** [architecture.md](architecture.md), [hq-interface.md](hq-interface.md)

## D14: Server game actor, scheduler and store

**Decision.** `server/src/game/`: a `GameActor` is the single writer for one game and owns the engine state, a `GameClock` and a serial command queue. Commands (`order`, `setRate`, `pause`, `resume`, `setMode`, `advanceTo`) run in arrival order. Each one first advances the engine to the clock's "now", then applies itself, then saves a snapshot. The scheduler sleeps until the next queued event is due (`clock.wallDueFor`) and re-plans after every command, so rate, pause and mode changes wake it. It sleeps not at all when paused, stopped, in manual mode or with an empty queue; fast-forward jumps to the next event with a zero delay. Orders are parsed through `OrderParser` in the background under the **LLM barrier**: the signing time is recorded as a pending dependency and `GameClock.holdAtNow` holds game time there in one step (so a wall clock that moves meanwhile cannot leave the barrier behind the clock) until the result arrives. Game time stalls, then carries on from the barrier (the clock re-anchors, so it never jumps), and other commands are served meanwhile. The order enters the engine at its signing time, so outcomes do not depend on LLM latency. A parse that fails or exceeds `parseTimeoutMs` is retried (`parseRetries`, `parseRetryDelayMs`), then replaced by a conservative fallback: nothing is issued, the player gets a clarification asking to restate, and the failure is logged on the input entry (`fallback`). The actor reports `staffAtWork` changes, and the protocol has a `staffAtWork` server message for the client indicator. `GameHost` runs many actors in one process; `open` brings a stored game back **paused**. `GameStore` is the persistence seam (latest snapshot plus an append-only input log of commands and parse results); `MemoryGameStore` is the only implementation until SQLite (Epic #2). Timers and the wall clock are injected, so tests run on a fake clock, and `close`/`shutdown` clear every timer, including those of a parse still in flight (an abandoned parse makes no further attempts). An order's input entry takes its `seq` and `gameMs` at signing but is appended when its parse completes, so the log is not in `seq` order. This is safe for replay (D14a): game time cannot pass the barrier, so every entry written while an order is being parsed carries the order's signing `gameMs`, and replaying in log position reaches the same state.
**Why.** One serial writer gives a total order with no locks, and lazy advancement keeps quiet stretches free.
**Open.** The barrier is held at the signing time because the order's addressee comes from the parse, so the courier cannot leave earlier; letting the courier ride while only the intents are pending would need the parse split into addressing and intents. Only order parsing is a dependency so far; judge and narrate will register theirs the same way. `attack` intents are refused as not modelled. The snapshot is rewritten after every command and tick; a log-plus-periodic-snapshot scheme is for the SQLite store. Pause voting is not modelled: `pause` and `resume` are plain commands.
**See.** [architecture.md](architecture.md)

## D16: WebSocket API with Fastify and dev side tokens
**Decision.** `server/src/api/`: a Fastify app (`buildApp`) with `POST /games` (creates "Hold the Bridge", body `{ "rate"?: number }`, rate from 0.01 to 86 400; returns the game id and one random token per side) and `GET /games/:id/ws?token=...` (a WebSocket for the side that token belongs to; a missing or wrong token or an unknown game is refused with 401 or 404 before the upgrade). A `Hub` holds the connections. It validates every inbound frame with the protocol's `parseCommand` (text frames only, at most 16 KiB; anything else gets a `bad_message` error and the connection stays up) and pushes only what `sideViewOf` returns, which is the engine's `viewFor` mapped to the wire `SideView`. On connect it sends the `SideView`; after every tick or command (`GameActor.onUpdate`) it sends a `viewUpdate` when the view changed, a `dispatch` for each paper not yet sent on that connection, and a `clockState` when the clock re-anchored. `issueOrder` carries the wording as `text` (until shared drafts exist; `draft` is accepted by the schema but answered `not_implemented`); a clarification or rejection from the parser comes back as an `error` (`order_clarification`, `order_rejected`) naming the `orderId`. Other commands answer `not_implemented`. A delivered order now files an `orderDelivered` report, so the sender gets a dispatch one courier delay after delivery. `GameHost` takes an `init` hook; the server passes `startingState` (in `game/registry.ts`) to queue the combat and visibility chains for a new game, and `replayLog` takes the same hook so such a game replays to the same state.
**Why.** The same filter that D12 makes the only path to a client is the only thing the hub calls, and a token in the URL is enough until accounts (Epic #5).
**Open.** Tokens live in process memory, like the store, so they are lost on restart. Morale is mapped from 0..100 to 0..1, and supply is always 1 until a supply model exists. No CORS headers yet, so a browser client must be served from the same origin or proxied. Pause votes, readiness and drafts are not wired.
**See.** [architecture.md](architecture.md), `packages/protocol/README.md`

## D14a: Input log format and replay
**Decision.** Each game's input log is a JSON-lines file, `<dir>/<gameId>.jsonl` (`FileGameStore`). The first line is a header `{gameId, scenarioId, seed}`, each later line an `InputLogEntry`: `seq`, `wallMs` (record only), `gameMs` (game time the command was applied at), `endGameMs` (game time after it and the catch-up), the command, the parser's result for orders, and `error` if it failed. `replayLog` rebuilds the starting state from the header (applying the same `init` hook the host used, `startingState` for the server, which queues the first scans and the combat chain), then per entry advances to `gameMs`, applies the order from its recorded parse (the same `applyLoggedOrder` the live actor uses), and advances to `endGameMs`. Clock commands (rate, pause, mode) need no step of their own because every entry carries its game time. `npm run replay -w server -- <logfile>` runs it with no wall-clock waits and no parser.
**Why.** Chunking `advanceTo` never changes the result, so replay needs only the game time of each input, and the result cannot depend on the original rate or mode.
**Open.** Game time that passed after the last input is not in the log, so replay ends at the last input unless `--until` is given. LLM calls other than order parses (judge, narrate) are logged through `CallRecorder` once those stages exist.

## D13: UmpireClient wraps the Anthropic SDK behind a transport seam (generalised by D14)

**Decision.** All LLM calls go through `UmpireClient`. The Anthropic implementation uses structured outputs (`output_config.format` with a JSON schema) rather than forced tool use, which newer models reject. The SDK's own retries are off; the wrapper owns retry, backoff and the per-attempt timeout so behavior is testable with a fake transport. Playback matches recordings on stage, prompt version and input (key order ignored) and fails loudly on a miss rather than calling the model.

**Failure handling.** A `Retry-After` longer than four times `maxBackoffMs` fails the call at once instead of sleeping. Output truncated at `max_tokens` is terminal (retrying the same request would truncate again). A failed call throws `UmpireError` carrying the summed `usage` and `costUsd` of its attempts, so spend on failures is visible, but nothing is recorded for it.

**Open.** The price table in `pricing.ts` is hand-maintained. The OpenAI-compatible adapter sends `max_tokens`, which OpenAI's newer models reject in favour of `max_completion_tokens` (a per-provider option is future work). Recording to the persistent input log is behind the `CallRecorder` interface; the log itself is not built yet. Prompt files and the `OrderParser` adapter that uses this client are separate work. A failed live call leaves no recording, so on replay it surfaces as `missing-recording` rather than the original `schema` or `transport` error; callers must treat all `UmpireError` kinds alike when falling back, or failures need recording too (open).

## D14: The umpire runs on any LLM through provider adapters

**Decision.** The owner wants to run the umpire on any model, cloud or local (Gemma 4 on Ollama in particular). `UmpireTransport` becomes the `LlmProvider` interface (Strategy): `generate(request, signal)` maps one request to one HTTP call and returns text, usage and refusal/truncation flags, plus `capabilities` (`structuredOutput: native | json-mode | none`, `contextWindow`, `toolUse`). Adapters: `anthropic` (SDK, `output_config`), `openai-compatible` (chat completions with a configurable `baseUrl`; covers OpenAI, Ollama `/v1`, llama.cpp, LM Studio, vLLM) and `ollama` (native `/api/chat` with `format` set to the JSON schema). A `ProviderRegistry` builds providers from config by `type`, so a new provider is one `register` call. Config maps each stage (parse, judge, narrate) to `{provider, model, params}`; it comes from defaults, an optional JSON file (`UMPIRE_CONFIG_FILE`) and env overrides. API keys come only from environment variables named by `apiKeyEnv`; a key in a file is rejected, and only Anthropic has a default key variable, so a cloud key is never sent to a local server by accident. Model names are plain strings.
Retry, backoff, the per-attempt timeout and schema validation stay in `ProviderUmpireClient`, because the repair loop shares those attempts. Rate limit and budget are decorators over `UmpireClient` (`RateLimitedUmpireClient`, `BudgetedUmpireClient`), as is playback, so all behave identically for every provider. For a provider without native structured output the client puts the schema in the system prompt, asks for JSON mode where the server has it, strips a code fence, validates, and on failure sends a repair message quoting the error, within `maxAttempts`. When attempts run out the caller uses the existing conservative fallback.
**Why.** Local judging and mixed setups (small local parser, cloud narrator) should be a config change, with no change to stage code.
**Open.** Prices exist only for Claude models, so local calls have `costUsd: null` and count against the token budget only. The budget is per process and in memory (it resets on restart) and can overshoot by the calls in flight. There is no streaming. Tool-use is a flag only; nothing uses it yet. The Gemma 4 tag is whatever the local server serves; the live test needs a pulled model.
**See.** [llm-providers.md](llm-providers.md), [architecture.md](architecture.md)

## Debug trace store (story 8.1, #120)

**Decision.** Tracing is an injected `TraceSink`; a no-op sink is the default so the disabled admin view has zero overhead. Correlation ids travel by `AsyncLocalStorage` rather than being threaded through every signature. Redaction happens inside the store, so no producer can forget it. Details in `docs/architecture.md` (Debug trace).

**Open.** HTTP and WebSocket transports do not exist yet; they should wrap each request in `traceRequest`. The composition root still has to construct the `TraceStore` from config (size, file path, the API key as a registered secret) and wrap the live umpire client with `traceUmpire`.
