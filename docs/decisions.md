# Decision log

Short records of decisions made, why, and what is still open. Newest at the bottom. Detail lives in the linked docs.

## D1: LLM umpire on a server, hybrid adjudication

**Decision.** A deterministic engine owns state, movement, line of sight, combat and dice. The LLM parses free-text orders, makes bounded judgment calls, and narrates per-side reports. It never edits state directly, and dice are rolled by a seeded server RNG.
**Why.** A pure LLM umpire is inconsistent and unauditable (the free-Kriegsspiel failure mode). Related LLM wargaming work also converges on this pattern.
**Turn mode.** D39 amends this for the turn-based mode only: there the umpire proposes each turn's outcome and the engine validates, clamps and records it, and resolves the turn itself when the umpire fails.
**See.** [design.md](design.md), [research.md](research.md)

## D2: The player's interface is a general's HQ

**Decision.** Players see no HUD or minimap. Everything arrives as paper: dispatches, reports, rosters, a journal. Their map shows only what they or their staff marked.
**Why.** It makes fog of war, stale information and delegation the game, and it matches the original Kriegsspiel.
**See.** [hq-interface.md](hq-interface.md)

## D3: Hybrid rendering: Three.js table + Angular desk (Svelte superseded by D29)

**Decision.** A Three.js scene with a **flat** historical map on a table and 3D wooden-block pieces, plus a Papers Please-style 2D desk built in HTML. The framework was Svelte; D29 replaced it with Angular. Phaser is dropped.
**Why.** The game is mostly documents plus one map. A DOM UI is much better for text and drag-and-drop, and a 3D table gives the physical Kriegsspiel feel. A flat map avoids needing elevation data.
**Alternatives considered.** Phaser, PixiJS, Babylon.js, Godot web export, full 3D room, fully 2D desk.
**Consequence.** The earlier Phaser prototype is abandoned and removed from the repo. The new engine and client are written fresh against the continuous-clock design. (The old code is kept outside the repo as a reference only.)
**Client structure.** `client/src/table/`: `buildSceneState(view, map, facings)` is a pure `SideView` to `SceneState` function; `TableScene` reconciles the Three.js scene to it (idempotent); picking is pieces by mesh raycast, then the map plane. Facing is not yet on the wire, so the client takes it as a side input (default N). Runs from a fixture with no server.
**See.** [hq-interface.md](hq-interface.md), [architecture.md](architecture.md)

## D4: Continuous game clock with an adjustable ratio, not turns

**Decision.** Game time is tied to wall-clock time at a per-game ratio (1:1, 4:1, 12:1, custom). Couriers and battles take real hours at 1:1. The engine is a continuous-time event simulator that never reads the wall clock. Manual-step and fast-forward modes are required, for testing and for optional turn-based play.
**Why.** It makes order lag and delegation real, and one engine supports every pace. An earlier turn-based design with deadlines was superseded.
**Consequence.** An **LLM barrier** stops game time from advancing past an unresolved LLM result. Inputs are logged for deterministic replay.
**Open.** The default ratio is chosen after the first scenario's pacing is measured. (Measured in D35: 12:1 stays the default for a first game.)
**Turn mode.** D39 adds a turn-based mode as a per-game setting: its clock stays in manual mode and advances one fixed turn at a time once the turn is resolved. Real-time games are unchanged.
**See.** [architecture.md](architecture.md), [gameplay.md](gameplay.md)

## D5: Pause by unanimous vote

**Decision.** All human players across all sides can vote to pause. One "no" or a timeout cancels it (hosts may allow a majority). A paused game allows reading and drafting, but signed orders dispatch on resume. After server downtime the game restarts paused.
**Emergency hold (confirmed by the maintainer, #66).** A single voter can stop the clock at once for a short wall-clock period, a limited number of times per game. The hold lapses unless the other voters ratify it; a ratifying vote turns it into an ordinary pause (with the usual resume vote and maximum pause length), while a "no" or the deadline resumes the clock where it stopped. It is the pause machine's own proposal flow (`PauseVoting.callHold`, command `proposeHold`, same `vote`/`pauseExpire` commands), not a parallel mechanism: the phase stays `pause_proposed` and the proposal and its transitions carry `hold: true`. The actor stops and resumes the game clock with `clock.pause()`/`resume()`, so the LLM barrier and every rate and mode behave as for any pause, and the hold's wall-clock deadline and every vote are inputs in the log (replay needs no model calls).
**Hold settings** are the `PauseConfig` fields `holdMs` (default 300,000: five minutes), `holdsPerPlayer` (default 2) and `holdsPerGame` (default 6; zero turns holds off), also accepted in the lobby's `pause` settings. A lapsed or refused hold still counts as used, and the counts are rebuilt from the input log when a game is reopened, so a restart does not refund them. A game that restarts during a hold comes back paused like any other (the hold becomes a plain pause). Only one hold can be open, and none while a pause vote is open or the game is paused. Refusals use fixed wording (`hold_refused`: "no emergency hold is left to you in this game"); `pauseState` carries `holdsLeft` for the viewer and the proposal's `hold` flag, with vote tallies only, never names.
**See.** [architecture.md](architecture.md), [gameplay.md](gameplay.md)

## D6: Collaborative play with roles and shared drafts

**Decision.** Each side is a group of roles (commander, chief of staff, intelligence, quartermaster, subordinate commanders). Orders are shared drafts that anyone can propose to and the commander signs and stamps. An LLM staff check shows how a subordinate would read a draft. Empty roles are filled by the LLM.
**Open.** Default hierarchy is assumed to be shared HQ, with chain-of-command as an option. Command level is assumed to be brigades and battalions.
**See.** [gameplay.md](gameplay.md)

## D7: Wire format is zod schemas in `packages/protocol`

**Decision.** Every command and server message carries a version field `v` and is validated with strict zod schemas (unknown fields rejected). Types are inferred from the schemas. The package exports no master-state types.
**Why.** One source of truth for server and client, and strict parsing keeps hidden state from leaking onto the wire.
**See.** [architecture.md](architecture.md), `packages/protocol/README.md`

## D8: Engine world model and scenario data

**Decision.** Game time is an integer count of game milliseconds. The map is continuous vector terrain (see D15; it began as a tile grid). Scenarios are plain JSON-compatible data, and `loadScenario` validates them and builds the initial `GameState` at t=0. "Hold the Bridge" is 4000 x 3000 m, with 3 units per side. Blue wins by holding the bridge for 50 game minutes (`holdMinutes: 50`; it began as 180, shortened in #178 so a first game fits a sitting), and Red wins by taking it. A test greps the engine sources for wall-clock and ambient-random calls.
**Why.** Integer time keeps replay exact, and validated plain data keeps state JSON round-trippable.
**See.** [architecture.md](architecture.md)

## D10: Movement is step events over planned routes

**Decision.** A move order plans a route (a list of free points, from where the unit stands when the order fires) and schedules one `move.step` event per leg, firing when the unit reaches the end of the leg. Legs longer than 100 m are split into equal steps of at most 100 m, so contact, range and the objective are checked at least that often. A leg takes its length times the ground's move-cost multiplier times the unit's march rate: road 0.5, open 1, wood 3, bridge 1; a river is impassable, so the bridge is the only crossing. Units have a `kind` (infantry, cavalry, artillery) with a march rate in game ms per metre of cost-1 ground (infantry 100 m/min, cavalry 300, artillery 66.7). Orders are queued events (`intent.move`, `intent.halt`) so they replay. A newer intent makes pending steps stale (they check the unit's `move` intent `startedAt`), and an interrupted unit stays at the last waypoint it reached. An order that cannot be carried out (unreachable destination, or an unknown unit, which emits `order.rejected`) is reported and leaves any march already under way alone.
**Why.** Event-driven steps keep quiet marches free and give the same result under any `advanceTo` chunking.
**Routing (continuous space, D15).** `findPath` (`packages/engine/src/navigation.ts`) is a visibility graph built per query and private to the engine: free waypoints just outside the corners of woods, marsh and water, around the ends and bends of rivers, along roads and on bridges and fords, plus the start and goal. Two waypoints are joined when the straight line stays on passable ground; the edge costs what the ground along it costs, and A* (ties broken by smaller h, then node index) picks the cheapest chain, so routes are free legs at any angle that prefer a road to a wood when it is faster and cross a river only at a bridge or ford. Unit width matters: a bridge or ford that spans impassable ground carries only units no wider than twice its radius (or its width), so a column (frontage about 10 m) crosses a 50 m bridge that a line (about 80 m) cannot. A bridge over open ground constrains nobody. An order that fails only for width emits `unit.moveBlocked` with `tooWide: true`. Changing formation (`issueFormation`, event `intent.formation`) stops the unit and takes game time (infantry 2 min, cavalry 1, artillery 3), after which `formation.done` swaps the footprint and emits `unit.reformed`; a newer order cancels it.
**Interruption.** A marching unit records its current `leg` (where it left, where it arrives and when). A new intent, halt or formation change stops it where it has got to, interpolated across the ground types along the leg (`positionAt`), so re-issuing orders loses no progress. `center` itself still moves only at the end of each step of at most 100 m, so combat and sight see the last step reached.
**Placement.** `validatePlacement(world, { unitId, center, facing?, elapsedMs })` checks physical plausibility only, for the umpire's free placement: inside the map (footprint included), centre and sub-positions on passable ground, footprints overlapping by no more than `OVERLAP_TOLERANCE_MM` (1 m; loose shapes exempt), and no further than the unit could march along the cheapest route in `elapsedMs`. It returns `accept`, `clamp` (the point reached along the route when time runs out, itself re-checked) or `reject`, each with reasons. It snaps to nothing and changes no state.
**Open.** The graph is an approximation of any-angle optimal routing: a route bends at corners with a 1.5 m margin and does not refract at ground boundaries, so it can be slightly dearer than the true optimum across a wood edge. The graph is rebuilt per query, `carries` re-samples the ground around each bridge or ford centre every time a leg meets one (a per-query feature-width map would make that flat), and A* scans its open list linearly (fine for scenario-sized maps; add a heap and a cache if maps grow). Width is only checked at bridges and fords, not at gaps between a wood and a river. Ordering a reforming unit back to the formation it still has cancels the reform where it stands. A reforming unit may end overlapping a neighbour, and the umpire's placements are not yet wired to a command. Units may overlap on the march (no collision or stacking rules yet), and facing does not follow the march. Slopes and the quick pace are not modelled (march and forced are, see "Supply, fatigue and ammunition"). Rates are a first pass, not the 1824 movement table.
**See.** [architecture.md](architecture.md)

## D11: Orders are couriers carrying intents

**Decision.** An `Order` (id, side, target unit, issue time, original text, parsed `OrderIntent`s) is queued with `issueOrder` as an `order.issue` event. When it fires, a courier route is planned from the side's `hq` (a new `Side` field, validated on passable ground) to where the unit stands, using the same route planner as movement; delivery time is the route cost times `COURIER_MS_PER_METRE` (400 m/min on open ground, so 800 on roads). An `order.deliver` event fires then and the unit adopts the intent: `move`, `withdraw` (a retreat that marches and then idles) or `hold` (march to the point if elsewhere, then hold). Until delivery, and after it, the unit keeps its standing intent. Orders to a missing, destroyed (strength 0) or enemy unit, or with no courier route, emit `order_failed` with a reason and change nothing; delivery emits `order_delivered`. The unit is checked again at delivery, so a unit destroyed in the meantime also fails.
**Why.** Orders lag by real game time, and everything stays an event, so replay and chunking guarantees hold.
**Open.** `order_delivered` is emitted even if the unit then cannot march (`unit.moveBlocked`, destination unreachable from where it stands); the two events are not linked yet. The courier route is fixed when the order is issued from the unit's position then, not chased as the unit moves, and couriers cannot be intercepted. Only the first parsed intent is adopted; conditional and timed intents, and `attack` as a courier-carried intent (D12 has the direct `issueAttack` order), are not yet modelled. Strength 0 stands in for "destroyed" until combat decides how units are removed.
**See.** [architecture.md](architecture.md), [gameplay.md](gameplay.md)

## D13: Contact, combat ticks and victory
**Decision.** Opposing active units are in contact when either can reach the other: infantry 200 m, cavalry 100 m, artillery 400 m between unit centres (placeholders). Every movement step schedules a `combat.check`; the first contact emits `contact.begin` and starts a chain of `combat.tick` events every 2 game minutes, which ends (`contact.end`) at the first tick with no contact. A tick lets each active unit fire once, at its `attack` target if reachable, else the nearest enemy. Casualties are `strength x rate x (d6 / 3.5) x morale factor x (1 - cover) x reach x aspect`, and stay fractional. Cover is the terrain cover at the target's centre. *Reach* is range falloff for fire (1 point-blank, falling linearly to 0.25 at the shooter's maximum range) or, for melee, a flat factor of 2. A shot is melee when the two footprints touch or overlap, or when a cavalry shooter's centre is within 60 m (the charge distance) of the target's. *Aspect* comes from the bearing of the shooter from the target against the target's facing: within 45 degrees of it is the front (x1), up to 135 degrees the flank (x1.5), beyond that the rear (x2); a square has no flanks. A unit that fires turns to face its target after the volley. All hits in a tick use start-of-tick strengths and facings, and dice come from the seeded RNG in unit order. Losses cut morale (2 points per percent of strength lost); below 25 a unit breaks, becomes `withdrawn`, walks to its start point (`home`) and takes no further part. Units at 0 strength are `destroyed`. `attack` is an order (`intent.attack`): the unit marches on the target, stops in range, and re-plans whenever the target moves out of reach (while marching or after stopping; each target step triggers a `combat.check`). Each shot is a structured `combat.fire` event (distance in metres, cover, aspect, melee flag, die, casualties). Victory is a single `game.end` event with a reason: `objective-taken` (only the attacker's active units have their centres inside the objective area, a polygon, and have kept it that way for `takeMs`, 10 game minutes by default; see "Hold rule" below), `objective-held` (the clock reaches `holdMs` with the objective not taken), `eliminated`, or `withdrawn` (a side has no active units). The scenario's `victory.objective` is a polygon of at least three `[x, y]` points in metres, centred on a bridge. `startGame` arms the clock deadline (at once if the clock is already past `holdMs`); after `game.end` combat and victory handlers do nothing, and every unit is stopped where it stands (intent idle, mid-leg position fixed at the end time) and movement, orders, formation changes and halts are ignored.

**Hold rule and fair start (#178).** Arriving is not enough. `combat.check` (queued after every movement step and combat tick) sets `heldSince` the moment only the attacker's active units are on the objective, and clears it the moment that stops being true; the same check queues a further check for `heldSince + takeMs`, and the attacker wins at the first check where it has held for the whole time. `takeMs` comes from the scenario's `victory.takeMinutes` (default 10). In "Hold the Bridge" Blue's 1st and 2nd Battalion start about 200 m south of the bridge and the cavalry 350 m behind them, while Red starts 1200 to 1370 m north. The scripted Red forms up for 10 game minutes before its first order, and a Red unit within 120 m of the objective gets one last order onto its exact centre (the aim spread alone leaves many units just outside the 60 m square) and then stays on it instead of chasing an enemy. Result: with no Blue orders Red usually takes the bridge, at about game minute 25 to 35 (not before): it does in 30 of 30 seeds tried (1 to 30), but not in the scenario's own seed 1815, where Blue's idle battalions, 200 m away, win the firefight and hold. Red is not guaranteed the bridge, since a passive Blue still shoots. With 1st and 2nd Battalion sent to the bridge at once the sides fight and Blue can hold. A first game thus lasts about 25 to 60 game minutes or longer if contested, so staff answers (10 and 15 game minutes) and narration windows complete at 4:1 and 12:1. The tests keep the old far-apart layout as `holdTheBridgeFarStart` for the movement and order numbers.
**Battles resolve (#315).** A fight now ends with a result, in tens of game minutes. (1) *Broken force.* A side's force is broken when at least one of its units has broken or been destroyed and the men it can still fight with, strength weighted by morale (`strength x morale / 100`, active units only), are under 25% (`BROKEN_FORCE_FRACTION`) of the men it started with (`GameState.startStrength`, set by `loadScenario`). In "Hold the Bridge" Red's last cavalry squadron alone is about 12%. A side with no active unit is broken too. (2) *Umpire's ruling.* When exactly one side is broken, the engine records a `BattleRuling` in `rulings` (`kind: 'battle'`, winner, loser, rationale for the record, and a narrative such as "Red's attack on the bridge has been broken; Blue holds the field"), emits `umpire.ruling`, and files a `battle` report to both sides, delivered at once, in the same words. The words carry no figure, so nothing hidden leaks; the post-game window shows the ruling. The ruling is built by the engine from the rule, not asked of a model: wiring the `judge` stage to the actor (with the LLM barrier) is left to a follow-up, and the keyless test umpire needs no canned judge. If both sides are broken together there is no declaration and the old rules apply. (3) *Close.* The game does not end at the declaration; it ends `BATTLE_CLOSE_MS` (20 game minutes) later with `attack-broken` (the attacker was broken, the defender wins) or `defence-broken` (the defender was broken, the attacker wins), so the pursuit is played out. A side with nobody left on the field ends the game at once, also with the battle's reason when its force had broken. The deadline (`holdMs`, now 50 minutes in "Hold the Bridge") still ends a battle nobody has broken. (4) *Pursuit.* A unit that breaks keeps `brokenAt` and for `PURSUIT_MS` (20 minutes) can be run down: it cannot fire, enemies that reach it hit it three times as hard (`ROUT_FACTOR`), and cavalry hits it as melee at any distance in reach. Free cavalry (idle or holding) within `PURSUIT_RANGE_M` (1500 m) of a unit that breaks is given an attack order on it; the chase uses the existing attack intent. A destroyed unit stops where it fell. Active enemies are fired on before routed ones. (5) *Dispatches.* A destroyed unit files a `unitLost` report with its own side, and an enemy who sees it die files `destroyed` (D12); when the game ends, reports still on the road are handed in so the closing dispatches are read. (6) *Scripted Red.* Cavalry reacts to an enemy within 1500 m (infantry 900 m), and a unit told to advance or attack that has not moved for two decisions in a row (a lost, garbled or intercepted order) is ordered again. Result in the end-to-end test with both Blue battalions sent to the bridge: Blue wins with `attack-broken` at game minute 40.8, Red's 1st Battalion destroyed, identical at rates 1, 4 and 12. Not in scope, left to combat v2 (#30): flanking beyond the existing aspect factors, melee detail, rallying. **Players see the battle (#320).** (7) *Field reports.* A unit in a tick's exchange files an `engaged` report with its own side (once per `ENGAGED_REPEAT_MS`, 10 minutes), a `heavyLosses` report when its strength first falls under `HEAVY_LOSS_FRACTION` (half) of its start, and a `broke` report when it breaks; the heavy-losses report is also filed when the unit breaks in the same tick or is run down below the line after it broke (#323: most of a beaten unit's casualties come in the pursuit, so the first version, which skipped both, almost never fired); a destroyed unit still files `unitLost`. They come by the nearest rider, `FIELD_REPORT_DELAY_MS` (3 minutes), and are about the side's own unit only, so they carry nothing of the enemy; the narrate stage (or the test umpire's canned wording, or the template text) puts them in a voice. (8) *The ruling.* The `battle` report is from "Dispatch from the field", and the narrate stage leaves it out so the ruling's words reach both sides as written. Its narrative reads "Red's attack at the bridge, on the High road, has been broken" (the place carries its own preposition). (9) *Wiped out.* `Outcome.loserOut` is set (`eliminated` or `withdrawn`) when the loser had nobody left, is sent on the `gameOver` message, and the game-over paper says so. (10) *Window and screens.* The umpire's window lists every ruling up to the scrubbed time with its time and text; the new-game screen reads the length and the win condition from the scenario (`holdMinutes`). (11) *Map.* The table rings the ground between an own unit and a visible enemy within 400 m (`engagementsOf`) as "Fighting", from the filtered view only. Once a battle is declared its result stands: the pursuit window decides the game, so an objective hold that would complete during it is not checked and the declared winner takes the game when it closes. **Order of evaluation (#417).** A QA game was ruled "Blue's defence ... has been broken" at about minute 31, but the 50-minute time limit fired before the 20-minute close and gave Blue `objective-held`; in another seed the winner's last unit broke in the pursuit and the side-out rule gave the game to the side ruled broken. The victory check (`evaluateVictory`, run by `combat.check`, `combat.tick`, `victory.deadline` and an umpire turn's `umpire.turn`) now goes in this order: (a) a declared battle decides: its winner takes the game with its reason at `declaredAt + BATTLE_CLOSE_MS`, or at once when either side has nobody left (`loserOut` set only if it is the loser); (b) with no ruling, both sides out ends in no winner, one side out gives the other the game; (c) the objective taken; (d) at the time limit, a declared battle closes there with its ruling, cutting the pursuit short so the game is never longer than `holdMinutes`, and only a game with no ruling goes to the defender (`objective-held`). Before reading the time limit, `victory.deadline` and the umpire turn declare a battle broken at that same minute, so a break and the limit on the same tick go to the ruling. Events at one game time run in queue order, and the deadline, queued by `startGame`, comes before that minute's `combat.tick`; so on its first firing it re-queues itself once at the same time (`payload.last`), which puts it behind everything already queued for the minute, and the tick's break is ruled on before the limit is read (a tick queues its successor 2 minutes on, so one step back is enough). Between the close and the limit the order does not matter: either gives the same outcome. Tested headlessly (engine: breaks at limit minus 20, 15 and 5, every clock stepping, and a break made by a real combat tick on the limit's own minute; server end to end: seeds 117 and 27 of "Hold the Bridge" with both battalions holding the bridge, at rates 1, 4, 12 and fast-forward, and replay). *Lost courier wording.* A `courierLost` report keeps the time its order was due (`orderDueAt`); if a report from that unit about something after then had reached HQ by the time the courier was given up, it reads "<unit> has sent word, but not that it has its orders: the courier carrying them is overdue and must be given up for lost" instead of "no word from <unit>". The choice is fixed once the report is delivered.
**Why.** Ticks only run during a fight, so quiet marches stay free, and every effect is an event handler, so replay and chunking stay exact. In continuous space there is no adjacency, so range, facing and footprints decide the fight.
**Combat v2 (#30).** (1) *Data.* The combat multipliers (long-range falloff, melee, flank and rear, rout) and the new morale and rally numbers are plain data in `packages/engine/src/combatRules.ts`, checked by `parseCombatData`, instead of constants scattered through `combat.ts`; `contact.ts` and `combat.ts` re-export them under their old names. Only the cover halving and the flank bonus on artillery fire have a counterpart in `src/data/fire.json`; the rest are placeholders, as `docs/rules.md` ("Combat v2") says. (2) *Morale checks.* Morale shock from casualties is now scaled by where the blow came from (flank x1.25, rear x1.5, on top of the casualty bonus). A unit that loses at least 4% of its strength in a tick then takes a check: two seeded dice, which must not total more than `round(morale / 100 x 12)`; a failure costs 4 more morale. In a melee tick the side that dealt less than it took loses 4 morale. The check is rolled after all fire dice, in unit order, so one seed gives one fight. (3) *Rally.* A unit that breaks schedules `combat.rally` 6 game minutes later and then every 2 minutes up to 40 minutes after it broke. A try is skipped (and retried) while an active enemy is within 500 m of where it is; otherwise a d6 of 4 or more rallies it: active again, idle where it stands, morale raised to at least 40, strength unchanged. A unit under 30% of its starting strength never rallies. A declared battle (D13 above) stands, so no rally after the declaration. (4) *Combat log.* `combat.fire` now carries the factors that made its casualties (`fireRate`, `formation`, `vulnerability`, `morale`, `range`, `ammo`, `aspect`, `rout`), `combat.morale` carries each check (loss, roll, needed, passed), and `unit.rallied` / `unit.rallyFailed` carry the rally tries, so a reveal can recompute any shot. (5) *Tests.* Determinism per seed, strength never negative or rising, morale in 0..100, and a 1000-seed balance smoke test (an even fight is 40-60%, a flank shot wins more than 60%, a 10% larger battalion wins more than 70% and fewer than all).

**Open.** All numbers are placeholders until the Epic #2 tables. The broken-force and pursuit numbers above are first guesses tuned on "Hold the Bridge" only. "Holds" is measured from game start, so the defender need not be on the bridge. A scripted Red that restarts forgets its orders (its memory is not in the log), so a restart can re-order units still on the march. Rallies (combat v2) restore morale only, not men, and are not reported to the player yet; marching and withdrawing units still fire; no friendly-fire or line-of-sight rules. Range and the objective use unit centres (not the nearest sub-position of a loose formation). Facing does not follow a march, only a volley, and a unit does not turn to answer fire it does not return. Melee is not exclusive: both sides trade blows each tick as in fire, with no pushing back (pursuit of a broken unit is in #315 above).
**See.** [architecture.md](architecture.md), [gameplay.md](gameplay.md)

## D12: Visibility is a pure filter over per-side intel
**Decision.** `viewFor(world, side, now)` in `packages/engine/src/visibility.ts` is the only function that turns master state into an `EngineSideView`. A unit sees an enemy within its sight range (infantry and artillery 600 m, cavalry 800 m, times the optional `GameState.sightFactor` weather hook) when nothing blocks the straight line between their centres: no sight-blocking ground (concealment 1: woods and buildings) and no ground whose height tag is above both ends (a `rise` or `high` ridge hides flat ground behind it, but a unit standing on that height sees over it; `low` ground never blocks). A unit in or looking from a wood or building sees or is seen only within 200 m. Partial concealment (#29): ground with concealment between 0 and 1 (marsh 0.2, scrub or an orchard a scenario tags) does not block but lengthens the distance sight feels: each metre of the line through it counts as 1 + 4 x concealment metres, and a unit standing in it counts as 1 / (1 - concealment) times as far away to every watcher, so it is hidden inside as well as behind (`perceivedDistance`; placeholder numbers, `docs/rules.md`). The weather `sightFactor` shortens the range the perceived distance is held against. Cover (`attrs.cover` at the target’s centre) already feeds combat casualties through `coverFactor`. A line that only touches a feature's corner is not blocked. A repeating `intel.scan` event (every game minute) records sightings in `GameState.intel[side]` (last-known contacts and reports), and files a contact report the first time an enemy comes into sight. `intel.report` events file unit-lost and order-delivered reports. Every report is delivered `COURIER_DELAY_MS` (10 game minutes) after it happened, except an order acknowledgement (`orderDelivered`), which is delivered `ACK_DELAY_MS` (2 game minutes) after the order arrives (#267). Each side also gets an opening `situation` report from its chief of staff when the game starts, so its in-tray is not empty before contact. The view shows each report with its age. Enemy size is a coarse phrase, never a number. Last-known contacts show the position where the enemy was seen, a facing estimate (rounded to the nearest eighth of a turn), its age, and an uncertainty radius that grows 100 m per minute of age, capped at the map's longer side. Reports carry a plain-language `place` built from nearby named features (`describePlace`, for example "near the mill, east of the road") and an `uncertaintyRadius` (a tenth of the sighting distance, at least 20 m) instead of coordinates in their text. Views speak metres, with no grid or cell concept; a visible enemy also shows its facing, formation and footprint, the footprint only to the nearest 10 m because it follows from strength. Last-known contacts are pruned (#110): a contact ages out once its uncertainty radius would grow past the cap (the map's longer side), and a contact for a destroyed enemy is dropped once the side has been told of the destruction, by a `destroyed` report the scan files when one of the side's units can see the wreck, delivered after the usual courier delay; until that report arrives the contact stays, so a death nobody witnessed does not leak through the filter.
**Why.** Keeping memory in state makes stale contacts replayable, and one filter function makes the leak tests meaningful.
**Open.** The `EngineSideView` is not yet mapped to the protocol `SideView` (no clock, dispatches or supply); tracked in #109. The courier delay is a flat constant, not distance to HQ. Sight ignores facing, weather and night.
**See.** [architecture.md](architecture.md)

## D15: Continuous space, no grid

**Decision.** Maps are not square or tile based. The world is a continuous 2D plane in metres (x east, y south, origin at the north-west corner) with map bounds. Master state stores every position and length as an integer number of millimetres, so serialisation and replay are exact; scenarios are authored in metres and quantised on load. There is no cell snapping and no adjacency rule anywhere in the model or protocol. A unit has a `center`, a compass `facing` in radians (0 north, clockwise), a `formation` and an oriented `footprint` (`frontage` x `depth`) that the formation gives by default; a loose formation (a skirmish line along a treeline, an arc) also lists `shape` sub-positions as offsets in the unit's own frame. Units may sit at any position and facing in any arrangement. Terrain is vector features: polygons (woods, marsh, water, fields), polylines with a width (roads, rivers, streams) and points with a radius (bridges, fords, buildings), each with a move-cost multiplier, cover, concealment, a height tag, passability and a layer; where features overlap the higher layer decides the ground (road over wood, river over road, bridge over river). The engine offers `terrainAt(point)`, `featuresAlong(segment)` and `featuresIn(polygon)`. The umpire may place units in any configuration subject only to the engine's plausibility checks: the centre, sub-positions and footprint lie on the map, the centre and sub-positions are on passable ground, and footprints do not overlap (loose shapes are exempt, as their rectangle is only a bound). Any spatial index is a private optimisation and does not leak into the model or protocol.
**Why.** The owner's direction: Kriegsspiel is loose, and the judge decides what is realistic. A grid would force every order and every placement through cells.
**Open.** Visibility and combat are reworked for continuous space in separate tasks; movement is reworked (D10: visibility-graph routing, mid-leg stops, formation width, placement validation) and so is combat (D13: range, facing and flanks, melee by footprint, polygon objective; cover is still taken from the ground under the target's centre), but sight is a straight line through features. The client table draws continuous space: the base map is vector features painted in metres onto a texture on a metre-scaled plane, pieces are drawn from `position`, `facing`, `footprint` and `shape`, last-known contacts carry an uncertainty circle of the wire's radius, and picking returns map coordinates in metres. The base map is a client-side type (`BaseMap`, now under `client/src/legacy/table`); the live game receives the scenario's public map from the server. Footprints per man are a first pass and cavalry and artillery frontages are not from the rules tables. This entry was proposed as D10 in the issue; D10 to D14 were already taken.
**Judge placement.** The `judge` stage can place any unit in any arrangement: a position, facing, formation and optional loose sub-positions (`shape`), all in metres on the wire and quantised to mm in the engine. `judgePlacements` (`server/src/umpire/judgePlacement.ts`, prompt `judge-placement-v1`) returns proposals; the engine's `issuePlacement` queues each as a `umpire.placement` event carrying the whole proposal, and `validatePlacement` rules on it when it fires: accept, clamp to what the elapsed time allows, or reject (off the map, impassable ground, hard overlap, a shape point further than `MAX_SHAPE_EXTENT_MM` from the centre). Only physical plausibility is checked. Every proposal, verdict (with reasons), rationale and narrative is kept as a `Ruling` in `GameState.rulings`, so replay re-queues the logged proposals and needs no model call. A placement replaces the unit's shape and ends any march it was on (a hold stays, at the new spot).
**Open (placement).** Nothing triggers the judge during a game yet: when it runs, and writing placements into the input log, belong to the scheduler/barrier work. A shape's footprint is just its bounding rectangle and loose units may overlap each other; the route check uses the unit's current frontage, and a change of formation is free. `GameState.rulings` keeps every ruling for the life of the game, so cap it or move it to the input log once the scheduler drives the judge; and `elapsedMs` is the time since the engine last placed all units, so a unit just placed gets the same clamp allowance as one untouched for an hour (per-unit elapsed time belongs with the scheduler work).
**See.** [architecture.md](architecture.md), [hq-interface.md](hq-interface.md)

## D14: Server game actor, scheduler and store
**Decision.** `server/src/game/`: a `GameActor` is the single writer for one game and owns the engine state, a `GameClock` and a serial command queue. Commands (`order`, `setRate`, `pause`, `resume`, `setMode`, `advanceTo`) run in arrival order. Each one first advances the engine to the clock's "now", then applies itself, then saves a snapshot. The scheduler sleeps until the next queued event is due (`clock.wallDueFor`) and re-plans after every command, so rate, pause and mode changes wake it. It sleeps not at all when paused, stopped, in manual mode or with an empty queue; fast-forward jumps to the next event with a zero delay. Orders are parsed through `OrderParser` in the background under the **LLM barrier**: the signing time is recorded as a pending dependency and `GameClock.holdAtNow` holds game time there in one step (so a wall clock that moves meanwhile cannot leave the barrier behind the clock) until the result arrives. Game time stalls, then carries on from the barrier (the clock re-anchors, so it never jumps), and other commands are served meanwhile. The order enters the engine at its signing time, so outcomes do not depend on LLM latency. A parse that fails or exceeds `parseTimeoutMs` is retried (`parseRetries`, `parseRetryDelayMs`), then replaced by a conservative fallback: nothing is issued, the player gets a clarification asking to restate, and the failure is logged on the input entry (`fallback`). The actor reports `staffAtWork` changes, and the protocol has a `staffAtWork` server message for the client indicator. `GameHost` runs many actors in one process; `open` brings a stored game back **paused**. `GameStore` is the persistence seam (latest snapshot plus an append-only input log of commands and parse results); `MemoryGameStore` and `FileGameStore` are for tests and tools; `SqliteGameStore` is the durable one (D14b). Timers and the wall clock are injected, so tests run on a fake clock, and `close`/`shutdown` clear every timer, including those of a parse still in flight (an abandoned parse makes no further attempts). An order's input entry takes its `seq` and `gameMs` at signing but is appended when its parse completes, so the log is not in `seq` order. This is safe for replay (D14a): game time cannot pass the barrier, so every entry written while an order is being parsed carries the order's signing `gameMs`, and replaying in log position reaches the same state.
**Why.** One serial writer gives a total order with no locks, and lazy advancement keeps quiet stretches free.
**Open.** The barrier is held at the signing time because the order's addressee comes from the parse, so the courier cannot leave earlier; letting the courier ride while only the intents are pending would need the parse split into addressing and intents. Only order parsing is a dependency so far; judge and narrate will register theirs the same way. `attack` intents are refused as not modelled. Snapshots follow D14b. Pause voting (D5) is a pure state machine, `server/src/pause.ts` (`PauseVoting`: running, pause_proposed, paused, resume_proposed), driven by the actor through the `proposePause`, `proposeResume`, `vote` and `pauseExpire` commands. Voters come from `GameHostOptions.pause` (player ids, `rule` unanimous or majority, `voteTimeoutMs`, `maxPauseMs`); without it the vote commands are refused. Vote timeouts and the maximum pause length are wall-time deadlines on an actor timer, and each fires as a logged `pauseExpire`. Every transition is stored on the input entry (`pause`). A passed vote calls `clock.pause()` / `resume()`, so the LLM barrier and replay are unaffected; the plain `pause` and `resume` commands remain as host overrides (they settle any open proposal, and a host pause is also bounded by `maxPauseMs`, as a safety net so a game cannot hang). A reopened game starts in `paused`, and resuming it needs a vote. The host records the wall time it was last seen alive (a heartbeat saved with every progress write and on a clean close), and on reopen the actor logs a journal-only `restart` input carrying the estimated `downMs` (a lower bound after a hard crash, since a quiet running game saves nothing between events). Game time is never advanced across the gap. Each player who connects to a reopened game gets a `serverRestarted` message once, which the HUD shows as a notice. **On the WebSocket (story 5.4):** `proposePause`, `proposeResume` and `vote` run as the signed-in user, who is the voter id. The hub sends `pauseState` (phase plus the open proposal as that player sees it: who asked by side, reason, yes/no tallies, voter count, their own vote, `msLeft`) on connect and on every change, and `pauseResult` (paused, resumed or cancelled, with the cause) when a vote settles. Votes are tallies, never names, and a refusal carries fixed wording so no account id leaks. A voter who is disconnected simply does not answer: a unanimous vote then times out and cancels, and on reconnecting they are shown any vote still open. Not wired yet: `setReady` and the emergency hold. The voters are the seats taken when the game starts, so use the lobby flow for a pause vote between several people. **Ratio change by vote.** `RatioVoting` (`server/src/ratioVote.ts`) uses the same voters, rule and vote timeout as the pause vote (they share `tallyVotes`) and the commands `proposeRate`, `rateVote` and `rateExpire`. One proposal is open at a time. A passed vote calls `clock.setRate`, which re-anchors at the current game time, so game time never jumps and the LLM barrier is untouched. Steps are stored on the input entry (`ratio`), and a reopened game takes the last passed ratio; replay needs no step for it, as for `setRate`. The plain `setRate` stays as the host override. Not wired to the WebSocket yet, like the pause messages.
**Narrate.** `narrateReports` (`server/src/umpire/narrate.ts`, prompt `narrate-dispatches-v1`) turns one side's `viewFor(...).reports` into period dispatches. The input is that side's report list only (id, officer, place, minutes ago, size estimate, confidence, radius), never master state. `checkNarration` rejects a reply that cites an unknown report id, leaves a report out, or whose prose has an id, a number (digits or words, up to thousands and compounds such as "four hundred") or a capitalised name (sentence-initial ones too, bar a list of ordinary openers) not in the input; the call is repeated (the input then lists what was wrong) up to `maxCalls`, then the engine's template text is used, so nothing is lost or invented. One call covers a side's whole window. `narrateWindowMs(rate)` is the window length in game time (5 min at rate 1, scaled by the rate and capped at `NARRATE_WINDOW_MAX_MS`, 20 min, so a fast clock still reaches a window: #342), and `reportsDueForNarration` holds reports until the window closes. A side a server-side agent plays (the scripted or LLM opponent) is never narrated, and the game's narration circuit breaker can skip a window; both are in "Narration on a small local model" (#419).
**Narrate in the actor.** With a `narrator` (a per-game `UmpireClient`, `GameHostOptions.narrator`; `main.ts` sets one when the umpire is configured) the actor runs the narrate stage once per side per window. When a side's window (`narrateWindowMs(rate)` of game time) has closed, `beginNarrations` hands its due reports to `narrateReports` and registers the call as an LLM-barrier dependency, so game time holds at that instant until the text is back (or the call times out after `narrateTimeoutMs`, 150 s by default and separate from the parse timeout, then the template text stays; #342). The actor also wakes at each window close, since reports are delivered by time rather than by event. The result goes to `GameActor.narrationFor(side)`, which `sideViewOf` uses in place of the template text; the first report of a dispatch carries its text and the others it covers are left out. Every model call is logged on a journal-only `narrate` input (`calls`, `UmpireCallRecord[]`), which replay ignores because narration never changes the engine. **Open (narrate).** A report shows its template text from delivery until its window closes and the call returns, then the narrated text arrives in a `viewUpdate` (the dispatch was already pushed once, so there is no second `dispatch` message). Narrations are held in memory: a reopened game shows template text for earlier reports, though the calls are in the log. The check is lexical: it catches invented names and numbers, not a wrong claim made of known words, and a legitimately capitalised common word outside the opener list may force a retry (then the template text).
**Staff answers in the actor (#418).** A conference question waits on the actor until game time reaches its `answerAtGame`. `advanceEngine` stops there exactly (as it does for a scripted agent's turn) and the answer is written from the officer's view at that instant, so a report delivered later cannot be quoted however far one tick jumps. The model call runs off the clock's critical path: game time never waits for a staff answer. See D6b.

**See.** [architecture.md](architecture.md)

**Test umpire (#294).** A `test` provider in the registry answers every umpire stage from rules and templates, offline and at zero cost, so a demo with no key is fully playable (`parse` understands ordinary sentences, `narrate` passes `checkNarration`, `staff` gives topic advice, `judge` rules nothing, `command` holds). `UMPIRE_PROVIDER=test` selects it; `UMPIRE_KEYLESS_PROVIDER=test` (set in the Docker image and compose file) moves only the Anthropic stages that have no key, so `ANTHROPIC_API_KEY` switches back to the real model. The game shows a badge and the admin LLM panel marks its calls `test`. Its limits are in [llm-providers.md](llm-providers.md#test-provider).

**Local Ollama umpire (#326).** The compose file runs an `ollama` service (`ollama/ollama`, CPU, volume `ollama`) pulling `qwen2.5:0.5b` in the background, and `UMPIRE_KEYLESS_PROVIDER=ollama` becomes the compose default (the bare image still defaults to `test`). The model serves `narrate` and `staff`; any failure (down, still pulling, timeout, schema-invalid after two attempts) is answered by the `test` provider through `FallbackUmpireClient`, with a 30 s skip after a transport failure or timeout, so the LLM barrier never waits long and an order is never lost. `parse` stays on `test` by default because on the golden corpus no model that fits the host parses a clear order (0/10; all three candidates), `OLLAMA_STAGES` opts it in. Model choice, the comparison, memory and disk are in [llm-providers.md](llm-providers.md#local-model-in-the-docker-demo) and [deployment.md](deployment.md). Judge and the AI commander are unchanged (`test`). Narration windows grow with the clock rate, so at 12:1 a 50-minute battle is over before the first window closes and the model is never asked.

## D16: WebSocket API with Fastify (dev side tokens, replaced by accounts in D17)
**Decision.** `server/src/api/`: a Fastify app (`buildApp`) with `POST /games` (creates "Hold the Bridge", body `{ "rate"?: number }`, rate from 0.01 to 86 400; returns the game id and one random token per side) and `GET /games/:id/ws?token=...` (a WebSocket for the side that token belongs to; a missing or wrong token or an unknown game is refused with 401 or 404 before the upgrade). A `Hub` holds the connections. It validates every inbound frame with the protocol's `parseCommand` (text frames only, at most 16 KiB; anything else gets a `bad_message` error and the connection stays up) and pushes only what `sideViewOf` returns, which is the engine's `viewFor` mapped to the wire `SideView`. On connect it sends the `SideView`; after every tick or command (`GameActor.onUpdate`) it sends a `viewUpdate` when the view changed, a `dispatch` for each paper not yet sent on that connection, and a `clockState` when the clock re-anchored. `issueOrder` carries the wording as `text` (until shared drafts exist; `draft` is accepted by the schema but answered `not_implemented`); a clarification or rejection from the parser comes back as an `error` (`order_clarification`, `order_rejected`) naming the `orderId`. Other commands answer `not_implemented`. A delivered order now files an `orderDelivered` report, so the sender gets a dispatch `ACK_DELAY_MS` (2 game minutes) after delivery. `GameHost` takes an `init` hook; the server passes `startingState` (in `game/registry.ts`) to queue the combat and visibility chains for a new game, and `replayLog` takes the same hook so such a game replays to the same state.
**Why.** The same filter that D12 makes the only path to a client is the only thing the hub calls, and a token in the URL is enough until accounts (Epic #5).
**Open.** (Superseded: tokens were replaced by accounts and seats in D17 and games persist in SQLite, D14b; the CORS note is met by the Angular dev server proxy, D29.) Tokens lived in process memory. Morale is mapped from 0..100 to 0..1, and supply is the share of ammunition left (story 2.6). No CORS headers yet, so a browser client must be served from the same origin or proxied. Readiness and drafts are not wired (pause votes are, see D14).
**See.** [architecture.md](architecture.md), `packages/protocol/README.md`

## D17: Accounts, magic-link login and seats (story 5.1, #61)
**Decision.** `server/src/auth/`. Login is a magic link: `POST /auth/login {email, next?}` mails a one-time link (32 random bytes, valid 15 minutes) and always answers 202, so it does not reveal which addresses have accounts; `GET /auth/verify?token=&next=` spends it, creates the user on first use, starts a session and redirects to the validated relative `next` (the page the visitor signed in from, e.g. an invite `/?game=<id>`; anything not a plain same-site path is dropped, default `/`). A game WebSocket upgrade with an `Origin` that is not the `PUBLIC_URL` origin, the request's own `Host` or listed in `ALLOWED_ORIGINS` (`*` disables the check) is refused with 403 (#208); no `Origin` header passes. A session is 32 random bytes in an `HttpOnly; SameSite=Lax; Path=/` cookie (`ks_session`, 30 days, `Secure` when `PUBLIC_URL` is https). Only SHA-256 hashes of link tokens and session ids are stored. `GET /auth/me`, `POST /auth/logout`, `DELETE /auth/account` (removes the user, sessions, pending links and seats, and closes their sockets). Rate limits, fixed windows in memory: 5 links per email and 20 per client address per hour, 30 verify attempts per address per 15 minutes. Users, links, sessions and seats live in `auth_*` tables in the game's SQLite file (`SqliteAuthStore`), or in memory without `DB_PATH`.
A **seat** is one user on one side of one game; it replaces the per-side token. `POST /games` (signed in) creates a game and seats the creator on `side` (default: the first side the built-in opponent does not play); `GET /games/:id` lists the sides and which is yours; `POST /games/:id/join {side}` takes a free side (409 if taken or you already sit on another). `GET /games/:id/ws` has no token: the session cookie is checked before the upgrade (401 without a session, 403 without a seat) and the socket gets the view of the side the user holds. Logout closes that user's sockets; deleting the account does too.
Mail goes through the `Mailer` interface: `WebhookMailer` POSTs `{to, subject, text}` to `MAIL_WEBHOOK_URL` (any HTTP-to-SMTP bridge), `LogMailer` writes the link to the server log for development.
**Why.** A magic link needs no password store and no reset flow. Cookies keep the credential out of URLs and logs, and `SameSite=Lax` stops a cross-site page from using it on state-changing requests or the WebSocket. Hashing means a leaked database cannot be used to log in.
**Open.** No SMTP client or vendor mail integration: a deployment needs a webhook gateway (follow-up issue). A mail scanner that prefetches the link would spend it (a confirm page would fix that). Rate limits are per process and keyed on `req.ip`, so behind a proxy `TRUST_PROXY=1` is required (off by default, as a forged `X-Forwarded-For` would dodge them); the admin guard still treats any forwarded header as non-loopback. Anyone can use up a victim's 5 links an hour by posting their address (the usual per-email trade-off); the per-address counter is charged before the per-email one on purpose. The WebSocket upgrade has no `Origin` check (`SameSite=Lax` covers cross-site pages, not sibling subdomains). Games are still not reloaded after a restart, so seats outlive the process but the games they point to do not (D14b open item). No lobby, invitations or display names yet, and a user has one seat per game. `/admin/api` keeps its own token and is not tied to accounts.
**See.** [architecture.md](architecture.md), [deployment.md](deployment.md)

## D17c: Guest play (#260)
**Decision.** `POST /auth/guest` creates a guest user (`guest-<uuid>@guest.invalid`, `guest` flag on `auth_users`) and a session cookie like a login, with no email. `GET /auth/guest` says whether it is on. Setting: `GUEST_PLAY` (`1`/`0`; unset: on outside production, off under `NODE_ENV=production`; the compose file turns it on for the demo). Disabled: 404. A request that already has a session reuses it. 10 guests per address per hour (`req.ip`, so `TRUST_PROXY` applies). A guest session slides: it lasts `GUEST_IDLE_HOURS` (default 168) from last use (refreshed at most hourly), and every 10 minutes guests with no live session are deleted with their seats, notification settings and unstarted lobby games, as an account deletion would. A guest's game is private: `GET /games/:id` and `/join` answer 404 to anyone but its creator, and the WebSocket needs a seat as before. Signing in by email while holding a guest session adopts the guest, but only the guest session that was sent with `POST /auth/login` (its id is stored on the link, #268), so a link requested elsewhere and opened in a guest's browser signs in as the link's owner without taking that guest's games: seats (a seat colliding with one the account already holds is dropped), lobby ownership and ready/role entries move to the account, whether new or existing, then the guest and its sockets are removed. The magic-link flow is otherwise unchanged. Client: the sign-in screen has "Play as guest" when enabled, which starts a game in one click; the guest's menu offers "Sign in to keep your games on other devices" in place of sign-out.
**Why.** A single-player demo has nobody to log in as, and the login link is only in the server log.
**Open.** Idle cleanup counts sessions, not game activity, so a guest whose game runs on but who never returns is removed with it. A guest is as strong as their cookie: no recovery. Multiplayer for guests (inviting others into a guest's game) is not supported.

## D17a: Lobby and game creation (story 5.2, #62)

**Decision.** Every game has a lobby record (`server/src/lobby/store.ts`; memory, or SQLite in the game database) made when the game is created: scenario, clock ratio, session type (`team_vs_team`, `co_op_vs_ai`, `hot_seat`), optional pause rules (`unanimous` or `majority`, vote timeout, maximum pause) and a `lobby` or `started` status. `POST /games` with `lobby: true` makes the record and the creator's seat only; no engine state or clock exists until `POST /games/:id/start`. Without `lobby` the game starts at once, as before. The invite link is `/?game=<id>`, which opens the game and offers a free side. Players take a side (`/join`) and mark themselves ready (`/ready`); the creator starts once every side people play is taken and every other player is ready (`/start`). `GET /games` lists the games the account made or sits in. A lobby game's WebSocket is refused (409 `not_started`).
- **Co-op vs AI** leaves the scenario's `scripted` side to the built-in opponent (needs `SCRIPTED_OPPONENTS` on); **team vs team** and **hot-seat** leave every side to people. The scenario data is never changed, so replay is unaffected; `GameHost` takes `scriptedOpponents` per game.
- **Hot-seat** has no seats: the creator plays every side and picks one with `?side=` on the WebSocket; the client offers a switch button. No one else can join.
- Pause rules chosen here become the game's `PauseConfig`, with the seated accounts as voters.
**Why.** A seat model already existed (D17); the lobby adds the pre-start state without touching the engine's determinism, since a game's inputs begin at start.
**Open.** Human-umpire sessions are not offered yet. Leaving a seat or kicking a player is not implemented, and lobby records of abandoned games are kept. Custom clock ratios are limited to 0.01 to 86400, like `POST /games`.
**See.** [gameplay.md](gameplay.md) (Session shapes)

## D16a: Game-over notice (story 1.20, #170)
**Decision.** A separate `gameOver` server message (`winner`, `reason`, `atGame`) rather than a `SideView` field: the result is public and one-off, so it does not belong in the per-side fog-filtered view, and a message lets the hub guarantee exactly one per connection (it follows the final `viewUpdate`, and a late joiner gets it right after the initial view). The actor stops the game clock as soon as the engine records an outcome. The client shows an end-of-game panel and disables the order box; the final view stays on screen.
**Why.** The outcome carries nothing about the other side beyond what both sides are told, so no filtering is needed, and the schema is strict so nothing can be added by accident.

## D14a: Input log format and replay
**Decision.** Each game's input log is a JSON-lines file, `<dir>/<gameId>.jsonl` (`FileGameStore`). The first line is a header `{gameId, scenarioId, seed}`, each later line an `InputLogEntry`: `seq`, `wallMs` (record only), `gameMs` (game time the command was applied at), `endGameMs` (game time after it and the catch-up), the command, the parser's result for orders, and `error` if it failed. `replayLog` rebuilds the starting state from the header (applying the same `init` hook the host used, `startingState` for the server, which queues the first scans and the combat chain), then per entry advances to `gameMs`, applies the order from its recorded parse (the same `applyLoggedOrder` the live actor uses), and advances to `endGameMs`. Clock commands (rate, pause, mode) need no step of their own because every entry carries its game time. `npm run replay -w server -- <logfile>` runs it with no wall-clock waits and no parser.
**Why.** Chunking `advanceTo` never changes the result, so replay needs only the game time of each input, and the result cannot depend on the original rate or mode.
**Open.** Game time that passed after the last input is not in the log, so replay ends at the last input unless `--until` is given. LLM calls other than order parses (judge, narrate) are logged through `CallRecorder` once those stages exist.

## D14b: SQLite store, snapshots and crash recovery
**Decision.** `SqliteGameStore` (`server/src/game/sqlite.ts`) keeps every game in one SQLite file in WAL mode, using Node's built-in `node:sqlite` (Node 22.5 or later, no native dependency). Tables: `games` (header and how far game time has run), `input_log` (append-only, one row per `InputLogEntry`), `snapshots`, `clock_history` and `side_views` (the latest `viewFor` of each side). The event queue is inside the engine state in each snapshot. Schema changes are numbered migrations in `MIGRATIONS`, tracked by `PRAGMA user_version`; a database newer than the server is refused. The actor takes a snapshot every `snapshotEvery` logged inputs (default 1) and tags it with the seq of the last input it includes; it keeps the newest three. Scheduler ticks write only the cheap high-water game time. Recovery (`GameHost.open`) is the latest snapshot, then `replayFrom` over the inputs logged after it, then an advance to the stored game time, so the state equals the one before the stop whatever the snapshot interval. The game comes back paused, with the rate and mode of the last logged input.
**Why.** Replay already is the determinism guarantee, so recovery reuses it instead of a second path. Chunking `advanceTo` never changes a result, which lets progress be stored as a single number.
**Open.** The crash test abandons the open database handle (every write is already committed) rather than killing a real process. `node:sqlite` is still flagged experimental by Node. There is no pruning of old input log rows behind a snapshot, and the stored side views are the engine `EngineSideView`, not yet the wire `SideView`. Wiring the store into a server entry point waits for the composition root.

## D13: UmpireClient wraps the Anthropic SDK behind a transport seam (generalised by D14)

**Decision.** All LLM calls go through `UmpireClient`. The Anthropic implementation uses structured outputs (`output_config.format` with a JSON schema) rather than forced tool use, which newer models reject. The SDK's own retries are off; the wrapper owns retry, backoff and the per-attempt timeout so behavior is testable with a fake transport. Playback matches recordings on stage, prompt version and input (key order ignored) and fails loudly on a miss rather than calling the model.

**Failure handling.** A `Retry-After` longer than four times `maxBackoffMs` fails the call at once instead of sleeping. Output truncated at `max_tokens` is terminal (retrying the same request would truncate again). A failed call throws `UmpireError` carrying the summed `usage` and `costUsd` of its attempts, so spend on failures is visible, but nothing is recorded for it.

**Open.** The price table in `pricing.ts` is hand-maintained. The OpenAI-compatible adapter sends `max_tokens`, which OpenAI's newer models reject in favour of `max_completion_tokens` (a per-provider option is future work). Recording to the persistent input log is behind the `CallRecorder` interface; the log itself is not built yet. Prompt files and the `OrderParser` adapter that uses this client are separate work. A failed live call leaves no recording, so on replay it surfaces as `missing-recording` rather than the original `schema` or `transport` error; callers must treat all `UmpireError` kinds alike when falling back, or failures need recording too (open).

## D14: The umpire runs on any LLM through provider adapters

**Decision.** The owner wants to run the umpire on any model, cloud or local (Gemma 4 on Ollama in particular). `UmpireTransport` becomes the `LlmProvider` interface (Strategy): `generate(request, signal)` maps one request to one HTTP call and returns text, usage and refusal/truncation flags, plus `capabilities` (`structuredOutput: native | json-mode | none`, `contextWindow`, `toolUse`). Adapters: `anthropic` (SDK, `output_config`), `openai-compatible` (chat completions with a configurable `baseUrl`; covers OpenAI, Ollama `/v1`, llama.cpp, LM Studio, vLLM) and `ollama` (native `/api/chat` with `format` set to the JSON schema). A `ProviderRegistry` builds providers from config by `type`, so a new provider is one `register` call. Config maps each stage (parse, judge, narrate) to `{provider, model, params}`; it comes from defaults, an optional JSON file (`UMPIRE_CONFIG_FILE`) and env overrides. API keys come only from environment variables named by `apiKeyEnv`; a key in a file is rejected, and only Anthropic has a default key variable, so a cloud key is never sent to a local server by accident. Model names are plain strings.
Retry, backoff, the per-attempt timeout and schema validation stay in `ProviderUmpireClient`, because the repair loop shares those attempts. Rate limit and budget are decorators over `UmpireClient` (`RateLimitedUmpireClient`, `BudgetedUmpireClient`), as is playback, so all behave identically for every provider. For a provider without native structured output the client puts the schema in the system prompt, asks for JSON mode where the server has it, strips a code fence, validates, and on failure sends a repair message quoting the error, within `maxAttempts`. When attempts run out the caller uses the existing conservative fallback.
**Why.** Local judging and mixed setups (small local parser, cloud narrator) should be a config change, with no change to stage code.
**Open.** Prices exist only for Claude models, so local calls have `costUsd: null` and count against the token budget only. The process-wide budget is in memory (it resets on restart) and can overshoot by the calls in flight. Per-game caps (`GameUmpireClient`, story 3.10) have the same limits: in memory, and a cap can be overshot by the calls in flight. A capped game gets `UmpireError` kind `budget` or `rate-limit` and each stage falls back; only narrate sets the in-fiction "staff overloaded" notice so far, and `judgePlacements` still throws on refusal (its caller must catch). `GameUmpireClient` is not yet created per game by `GameHost`, because no live umpire is wired into the server. The parse stage now defaults to Haiku. There is no streaming. Tool-use is a flag only; nothing uses it yet. The Gemma 4 tag is whatever the local server serves; the live test needs a pulled model.
**Update (3.11, #47): the rigid-to-free dial and umpire personas.** Two settings are chosen when a game is made (`POST /games` body `dial`, `persona`; defaults `standard` and `dry`), kept on the lobby record (`umpire`) and recorded with the game, in the input-log header (`settings`; SQLite column `games.settings`, migration 7). They are set by the owner's brief as follows; the numbers are this entry's assumptions.
- **Dial** (`rigid | standard | free`) changes one thing: the cap on the judge's modifier (`DIAL_CAPS` in the engine): rigid 0 (tables only: `judgeSituation` makes no model call and every ruling is the standard rule, a fallback that is not case law), standard 0.25 (what the cap was before), free 0.40. It lives on `GameState.dial` (absent counts as standard) because the engine clamps with it. The prompt tells the model the cap, and the engine still clamps, so a small model cannot exceed it.
- **Persona** (`dry | pedantic | dramatic`) appends one voice passage to a stage's system prompt (`withPersona`, used by narrate and the judge's situation task). It never changes the schema, the bounds or the facts the model may use, and it is not engine state, so a persona swap leaves engine outcomes identical (tested at rates 1, 4 and 12) and the canned test provider and a weak Ollama model work with any of them.
- **Replay** is unchanged apart from reading the dial from the header into the starting world; the persona has no effect on a replay, which makes no model calls. A game with no settings in its header replays as `standard`.
- The dial does not yet touch placement bounds (D15) or the turn length; only the judgment cap. The judge situation task is not yet called by the actor, so the dial's effect is in the engine clamp and the stage function until it is wired.

**See.** [llm-providers.md](llm-providers.md), [architecture.md](architecture.md)

## Scripted Red opponent (story 1.11, #18)

**Decision.** A side whose scenario `controller` is `scripted` is played by a server-side `SideAgent` (`server/src/opponent/`). The game actor wakes it every 5 game minutes (a multiple of the interval, so the times do not depend on the clock rate or mode) and gives it `viewFor(world, side)`, an `EngineSideView`, and nothing else; `assertFogOnly` refuses anything that carries master state. It returns orders that go through `applyLoggedOrder` and the engine's `issueOrder`, so they leave HQ, ride with a courier and arrive late like a human's. Behaviour: advance on the objective, close on an enemy it sees (or saw in the last 10 minutes) within 900 m, fall back to HQ when a unit's morale is under 40 or its strength under half its peak. Hesitation and the aim point come from an RNG seeded by (game seed, side, think tick), so a decision is a pure function of the view and the unit's last order.
**Replay.** Each agent order is appended to the input log as an ordinary `order` entry with its parse result and `agent: true`, so replay needs no agent. The actor flushes them before the next logged command; `replayLog` sorts by game time (an agent first at the same instant) and now catches the world up lazily instead of after every input.
**Why.** One human can play against it, and the fog and order-lag rules apply to it without special cases.
**Open.** The engine has no attack order yet, so "attack" is a move onto the enemy's position. Agents are enabled with `GameHostOptions.scriptedOpponents` (off by default) until a server entry point creates games. A restarted game keeps the decision times but not the agent's memory of earlier orders, so it may reissue one.

## Conditional and timed intents (story 2.8, #33)

**Decision.** An order's intents may include `{kind:'when', trigger, then}` and `{kind:'at', gameTime, then}` (an `at` is a `timeReached` trigger). On delivery a unit adopts the first immediate intent (move, hold, withdraw) and keeps each `when` / `at` as a `StandingOrder` on `Unit.standing` until its trigger fires, once. Triggers: `enemySighted {area}`, `strengthBelow {strength}` (men), `orderReceived {from}` (`Order.from`, default `'hq'`) and `timeReached {gameTime}`. They are judged right after each intel scan, and a `timeReached` one also gets its own `standing.check` event at its moment, so a timed order fires on time at any clock rate.
**Fog.** `enemySighted` uses the unit's own `canSee`, never master state and never what a sibling unit or the side's shared intel knows. An enemy inside the area but out of sight (range, wood, ridge) does not trigger it.
**Rules.** A standing order carried from an earlier order is kept when a new order arrives, and an `orderReceived` one fires on an arriving order from the named sender after that order is applied, so it overrides it. The order that carries a standing order never sets it off. A fired `then` can itself hold `when` / `at`. Destroyed or withdrawn units do not act. Firing emits `standing_fired`.
**Open.** The parser does not produce `when` / `at` yet, and the wire protocol and client do not show standing orders. `strengthBelow` is an absolute count, not a fraction of the unit's starting strength. Nothing validates `when` / `at` intents (an `enemySighted` area under 3 points, a `NaN` time or strength just never fires); the parser story should. A withdrawn or destroyed unit keeps its `standing` list, unused, rather than having it cleared.

## Unit types, formations and data-driven stats (story 2.2, #27)

Fitting them to the fire and casualty tables, and loading the data from the JSON files of story 2.1 rather than a typed module, is later work. ## Supply, fatigue and ammunition (story 2.6, #31)

**Decision.** Each unit carries `fatigue` (0 fresh .. 100 spent), `ammo` (0..100, share of a full load) and `pace` (`march` or `forced`). All three are master state; `viewFor` shows a side its own units' values. Rules and constants live in `packages/engine/src/fatigue.ts` and `supply.ts`:
- **Forced march.** A move can carry `pace: 'forced'` (`issueMove`, or on a move order's intent). It marches 1.5 times as fast and gains 4 times the fatigue per minute (1.2 against 0.3). Fatigue is charged at each step event for the leg just marched, so it is exact however the clock is chunked.
- **Fatigue.** Fighting adds 3 per combat tick to every unit in an exchange. Up to 20 it costs nothing; beyond that march speed falls linearly to 40% slower at 100. At 70 a unit is exhausted: each supply tick costs it a point of morale, down to its break point and no further (exhaustion alone never breaks a unit).
- **Rest.** Every 10 game minutes (`supply.tick`, queued by `startGame`) a unit that is idle or holding, and out of reach of any enemy, sheds 4 fatigue.
- **Ammunition.** Firing (not melee) spends 10% of a load for infantry, 5% for cavalry and 12% for artillery per combat tick. At 0 a unit's fire does a tenth of its damage and costs it a point of morale per supply tick. It still takes casualties normally.
- **Resupply.** A resting unit takes 25% of a load per supply tick if a wagon can reach it: the route from one of its side's depots (`Side.depots`, default the HQ) costs at most 6 km of march cost. Roads cost half, so along a road the reach is 12 km. Depots are unlimited stores.
- **Dispatches.** Crossing 25% ammunition and crossing 70 fatigue each file a report (`lowAmmo`, `exhausted`) to the unit's own side, delayed by the usual courier time. The wire `supply` of an own unit is `ammo / 100`.
**Why.** A forced march has to be a real trade: arrive sooner, but spent, slower afterwards and short of morale. Resupply that follows the road net gives roads and depots a reason to matter.
**Open.** Numbers are placeholders, not from the 1824 rules (see `rules.md`). Wagons are a reach test, not units: they carry no finite load, can be neither delayed nor captured, and a resupplied unit gets its ammunition at the tick, not when a train arrives. Fatigue is not shown on the wire (`SideView` only has `supply`), and the order parser and umpire schema do not yet produce `pace: 'forced'`. Fatigue does not affect fire. A march interrupted mid-leg loses that leg's fatigue.
**See.** [rules.md](rules.md)

## Courier model v2: interception, loss and garbling (story 2.7, #32)

**Decision.** An order's courier is a map entity (`GameState.couriers`) that rides the cheapest route from HQ to the unit, in timed legs. Each game minute, every enemy unit in reach rolls to take it (cavalry from 800 m at 0.3, infantry from 300 m at 0.1, artillery never; halved in sight-blocking ground, scaled by the weather's `sightFactor`). When it sets out, the ride rolls once for being lost and once for garbling. Both chances grow with the ride's length, with how rough the ground is (route cost over straight length) and with bad weather, and garbling falls with the addressee's `training` (a new 0..1 field on unit types). A lost courier emits `order_failed` ("courier lost"). A garbled order moves the unit's destination 300 to 1200 m and emits `order_garbled`. A taken courier never delivers: the order is not executed and `courier_intercepted` is emitted. All rolls come from the game RNG inside event handlers, so a ride is fixed by the seed and does not depend on how the clock is chunked or on the rate.
**Captured dispatches.** The captor's intel gets a `CapturedDocument` with the order's original wording. It reaches the captor's HQ one courier delay later and then appears in `EngineSideView.documents`; the server sends it as an `intelligence` dispatch. The sender gets nothing: no acknowledgement ever arrives.
**Why.** It makes cavalry screens and rear-area security matter, and a dispatch read by the enemy is the "umpire hands it over in-fiction" feature from [design.md](design.md).
**Open.** All figures are placeholders until playtested. Couriers are not drawn on the table for either side yet, and the garble only moves a destination (it does not change the kind of order). A side is not told that a courier was lost.
**See.** [design.md](design.md), [architecture.md](architecture.md)

## parseOrders stage: free text to intents (story 3.2, #38)

**Decision.** `LlmOrderParser` (`server/src/orders/llmParser.ts`) implements `OrderParser` on the umpire's `parse` stage. The model sees the order text (as a JSON data field, with the prompt telling it the text is never instructions), the issuing side's own units and the named places, never master state or the other side. It answers with a unit id and place ids, not coordinates; the server maps ids back to the engine's anchors, so the model cannot invent a position or address a unit the side does not own. Output is one of `intents`, `clarification` or `rejection`. Any failed call or invalid output (unknown unit or place, no intents, empty question or reason) becomes a clarification saying the unit holds and awaits clarification, and is reported through `onFallback` for logging. A mixed real-order-plus-injection text is answered with a clarification, not half executed. The prompt is versioned (`parse-orders-v1`) and every call goes through the recorded `UmpireClient`.
**Why.** Ids-only output makes the engine's validation the single gate, in line with "the LLM never mutates state", and a conservative fallback keeps a model outage from moving troops.
**Wiring (#253).** `main.ts` parses orders with `LlmOrderParser` whenever the `parse` stage's provider is configured (`llmOrderParserEnabled` in `config.ts`: Anthropic needs its API key, any other configured provider counts; `ORDER_PARSER=stub` forces the stub), and with `StubOrderParser` otherwise, as in tests and with no key. Each game gets its own parser over that game's capped umpire client, shared with its LLM commander. The host takes `parser` as an instance or a `(gameId) => OrderParser`. When the call fails, is over budget or returns output the checks refuse, `fallbackParser` (the stub) answers if it can read the order; if not, the player gets the restate-the-order clarification. Either way the order is not lost: the actor's barrier, retries and input log are unchanged, and replay reads the logged parse, so it makes no model call. The client shows a clarification or rejection without the order id the server prefixes for matching.

**Open.** The recording of corpus outputs is a hand-authored seed until someone runs `--llm --live --record`. The intent vocabulary still has no conditions or schedules, so those orders are clarified. Fallbacks are logged by the caller of `onFallback` (the server logs a warning), not yet persisted. The stub quotes the lower-cased phrase in its questions.
**See.** [order-eval.md](order-eval.md), [architecture.md](architecture.md)

## D16b: Player marks layer (story 4.3, #50)
**Decision.** A mark is a pin, pencil line, arrow or range ring (`Mark` in `packages/protocol/src/marks.ts`, strict schema) with an id chosen by the client, an optional note, `madeAtGame`, and an optional `sourceReport` (a dispatch id). Marks are per side, which is the player in shared-HQ mode (the only mode until roles exist): each side's list is kept by the hub, saved in `GameStore` (`saveMarks`/`loadMarks`, SQLite table `side_marks`), sent as one `marks` message on connect and after every change, and so shared by every connection of that side. Clients send `putMark` (create, replace or move, by id) and `deleteMark`. Marks are not game input: they never reach the engine, are not in the input log and are not replayed. A side keeps at most 500 marks (`too_many_marks`). The server stores a mark exactly as sent and never moves, snaps or corrects it, wherever the truth is. On the table a mark ages with game time, going grey and fading over 12 game hours, and the note shows its age. The overlay toggles are order arrows, planned routes and last-known shading; the first two draw whatever `SceneState.orderRoutes` holds, which stays empty until the server sends pending orders and routes.
**Why.** Docs say the picture can be wrong and the server never silently corrects it. Keeping marks outside the engine and the log keeps replay deterministic with no model calls. A full list on every change is simple and cheap at 500 marks, and avoids per-mark merge rules; the last writer of an id wins.
**Open.** Per-player marks inside a side (chain-of-command mode) need player identities. Staff-placed marks from reports (and a good or poor chief of staff plotting them) are not built; the player plots a report by hand.

## D17b: Notifications (story 5.8, #68)
**Decision.** The `Notifier` (`server/src/notify`) runs after each host update. It keeps, per game, what each side had seen (report and document ids from `viewFor`, clock status, open pause and ratio proposals, game over), reports nothing on its first look, and then turns each change into an event for the seat's side: `dispatch`, `contact`, `unitLost`, `pauseProposed` (to sides that are not the proposer and have not voted), `decision` (an open ratio vote), `paused`, `resumed`, `gameOver`. A player with the game open gets a `notification` WebSocket message; a player with no open socket gets web push (VAPID, `PushSender`, `web-push`) and email (`Mailer.sendNotification`), unless their quiet hours are on. Preferences are per user (`GET/PUT /notifications/prefs`): threshold `all`, `urgent` (contact, unit lost, pause proposed, decision, game over), `contact` or `off`; quiet hours as minutes of the local day plus a UTC offset; push and email switches. Default: urgent, push and email on. Push subscriptions are registered at `/notifications/push/subscription` (https endpoints only, at most 10 per user) and dropped when the push service answers 404 or 410. Routine emails are limited to one a minute per player per game.
**No hidden information.** Title and text are fixed per event kind (`NOTICE` in `policy.ts`); a notification never names a unit, place, number or the content of a dispatch. The link in push and email is the game URL only.
**Why.** Players are away most of the time, and a fixed-text message cannot leak what the visibility filter withheld.
**Open.** "Your turn to decide" is only the open votes for now; order clarifications are answered in the same request, and the roles epic will add more decisions. Dispatches that arrive while the server is down are not announced. There is no client UI yet for preferences or for subscribing (no service worker); the HUD shows an in-game notification as a notice. The accepted live app wires pause voting and receives `pauseProposed`; the fixture HQ has no live pause-voting adapter. Hot-seat games send no notifications: they have no seats (the creator plays every side at one table), so there is nobody to route to. Push endpoints are checked for https and a public-looking host (no IP literals, `localhost` or single-label names), but a public name that resolves to a private address is not caught, so a deployment should also block egress to private ranges. One notice per side and kind is sent for each look at a game, so five contact reports in a tick are one push and one email.
**See.** [architecture.md](architecture.md), [gameplay.md](gameplay.md)

## D6a: Roles, per-role views and permissions (story 6.1, #72)
**Decision.** The engine has five roles: commander, chief of staff, intelligence, quartermaster and subordinate commander. A `Seat` is a role plus, for a subordinate, the ids of the units they command. `viewForRole` returns a subset of `viewFor` for the seat (see [architecture.md](architecture.md), "Role views"). `maySign` lets the commander sign for any living unit of the side and a subordinate sign for their own units only; staff roles never sign. `mayDraft` lets any staff role draft for any living unit and a subordinate for their own. Intelligence sees our units as an outline: footprint to the nearest 10 m (as for an enemy) and no loose shape, because an exact footprint is area per man times strength. Shared-HQ mode uses `viewFor` unchanged.
**Why.** The visibility filter stays the only path from master state to a client, and a role can only narrow what a side knows.
**Lobby and wire (#216).** The side's seat holder is its commander. Other players join the same side with `POST /games/:id/join { side, role, units? }` while the game is in the lobby: one holder each for chief of staff, intelligence and quartermaster, and any number of subordinates who each name units of that side nobody else commands (`bad_units`, `units_taken`, `role_taken`; `no_commander` before the side has its commander). The assignments are `LobbyGame.roles` (kept in the lobby record, so no new table); `GET /games/:id` lists the jobs filled per side and which is yours, never who holds them; `POST /games/:id/leave-role` gives one up. Role holders must be ready before `start`, vote on pauses, and see the game in `/games`. A side with no role holders plays shared HQ: its connections get `viewFor` and the wire view has no `role`. Once a side has any, each connection gets `viewForRole` for its seat and `SideView.role` says which. A role that may not know a unit's condition (intelligence sees an outline) gets `ownUnits` without `strength`, `morale` and `supply`, which are optional on the wire; the client shows them as unknown. **Signing.** Only the commander and subordinates sign. The hub refuses staff at once (`not_permitted`); the order's addressee is known only after the parse, so the actor checks `maySign` there and replaces a refused parse with a rejection in the log, which is what replay applies. The seat is carried on the logged `order` command as `signer`. **Forwarding.** `forwardDispatch { dispatchId, unit }` from the commander or chief of staff (`mayForward`) passes a paper (report or captured dispatch) in their own view to the subordinate commanding that unit. Forwards are kept in the lobby record (`LobbyGame.forwards`) and survive a restart; `viewForRole` adds exactly those papers to the subordinate's view and nothing else (no sightings or contacts come with it).

**Leaving and removing (#213).** While a game is in the lobby, `POST /games/:id/leave` gives up your seat or role (and your ready mark); the creator cannot leave (409 `creator_cannot_leave`). The creator removes someone with `POST /games/:id/kick { side, role?, unit? }`: no `role` is the side's seat holder, a subordinate is named by one of their units; `not_creator` (403), `cannot_kick_self` (400), `no_such_player` (404). Both are 409 `already_started` once the start begins. A removed account is kept in `LobbyGame.removed`: it cannot take a seat or role again, its `GET /games/:id` says `removed: true`, and it is told by push and email (its own preferences; the notice names no one). The room offers Leave seat to a guest and Remove (behind a confirmation) to the host.
**Open.** A forwarded paper arrives at once: the gameplay doc says it should take game time and may be withheld or mis-summarised, which is not built. Forwarding is per paper and per unit; there is no "forward everything" setting. Roles cannot change after the game starts, and no client UI joins a role or forwards yet (HTTP and WebSocket only). Notifications still go to the side's seat holder only. The shared-draft flow itself (D6c) does not yet apply `mayDraft`. A subordinate's reports are matched by unit name, since reports carry no unit id; the scenario loader rejects two units of one side with the same name so that match is safe.
**See.** [gameplay.md](gameplay.md), [architecture.md](architecture.md)

## LLM opposing commander (story 5.10, #70)

**Decision.** With `AI_COMMANDER=llm` a scripted side is played by `LlmCommander` (`server/src/opponent/llmCommander.ts`), a `SideAgent` with an async `decide(view)`. It uses a new umpire stage, `command`, so its model is configured like the others (`UMPIRE_PROVIDER_COMMAND`, `UMPIRE_MODEL_COMMAND`). The model gets the side's `EngineSideView` (`assertFogOnly` runs first), the objective, the named places, and the difficulty and personality text, and writes orders as free text. That text goes through the same `OrderParser` a human's does, so it can only address the side's own units and named places, and the orders leave HQ with a courier. `AI_DIFFICULTY` (easy, normal, hard; easy decides every 10 game minutes instead of 5) and `AI_PERSONALITY` (cautious, balanced, aggressive) tune it.

**Budget (#243).** The commander spends the game's LLM budget, so `GameUmpireClient` holds it to `COMMANDER_BUDGET_SHARE` (40%) of the cost, token and calls-per-minute caps, as it does staff (a quarter, #234). A decision whose view is unchanged since the last call (apart from time) asks nothing, so a quiet field costs no tokens.
**Fog.** Captured enemy dispatches and reports in the view are data; the prompt says so. The leak tests in `llmCommander.test.ts` check that the request carries only the side view and public facts, that master state is refused, and that orders cannot reach another side's units.
**Open.** Off by default; the scripted opponent stays the default. No client UI to choose difficulty or personality yet (environment only). Prompt quality is untested against a live model, and the commander has no memory of earlier decisions beyond what the view shows. A resumed game's agent does not carry over its last call's view, so it asks again.
## D6b: LLM staff officers fill empty roles (story 6.2, #73)
**Decision.** A `staff` umpire stage (`server/src/umpire/staff.ts`, prompt `staff-officer-v1`, default model Sonnet) plays every seat no human holds. A `StaffRoster` lists a side's seats (by default commander, chief of staff, intelligence and quartermaster; add `subordinate` seats with their units) and which are held by a human. `runStaff` calls one officer per vacant seat whose turn is due, showing the model only `viewForRole` for that seat plus the officer's name and traits. Officers are deterministic from game seed, side and role (`staffOfficer`), so a replay has the same staff; `SideView.staffOfficers` sends the four conference officers so the page shows them before the first question and after a reload (#342). An officer returns at most four messages, each a `report`, a `suggestion` (draft wording for one unit the seat may `mayDraft` for; never an order, since staff cannot sign) or `advice`. A reply is rejected, and asked for again, if it cites an id not in the seat's view, has empty text, or breaks the suggestion rules; after `maxCalls` the officer says nothing, as also when the umpire fails or the budget is spent, so a game never waits on its staff. An officer is due once a narration window (`narrateWindowMs(rate)`) has passed since they last spoke. `claim` and `release` change a seat at any time: a claimed seat gets no further calls, and a reply still in flight for it is dropped.
**Why.** The staff can only narrow what a side knows, never widen it, and a one-human side keeps a full staff without any human having to play it.
**Hardening (#234).** `StaffTurn.records` carries every call record of the turn (`runStaff` no longer discards them), so the caller can write them to the input log and replay makes no model call. Staff share the per-game caps with parsing and judging, so `GameUmpireClient` holds staff to `STAFF_BUDGET_SHARE` (a quarter) of the cost, token and calls-per-minute caps; a saturated staff share refuses only staff calls (as `budget` or `rate-limit`, the officer is silent) and never blocks an order parse. Staff `text` is bounded to `STAFF_TEXT_MAX_LENGTH` (600) characters in the schema and the check. The id check covers only ids ending in a number, and the view includes captured enemy-authored text (e.g. enemy orders and dispatches), which is an injection surface for the advisory text; it cannot reach game state, since staff output is never an order and the engine never reads it.
**Conference cost (#242).** The game-time cost of a staff conference question is enforced by the server, not the client. A player sends `askStaff { questionId, role, question }` over the WebSocket; the hub (`server/src/api/conference.ts`, `StaffDesk`) takes the cost for that officer (chief of staff 10 min, intelligence 15, quartermaster 10, engineer 20; unchanged from the client fixture), marks that side's officer busy until `askedAtGame + cost` in game time and replies `staffQueued { questionId, askedAtGame, answerAtGame, costMs }`. A second question to a busy officer is refused with `staff_busy`. The deadline is in game time from `GameClock.now()`, so it is the same at rates 1, 4 and 12, holds while the game is paused, and a client that skips the UI cannot avoid it. The client shows the answer at the server's `answerAtGame`. *Assumptions (the issue left these open):* "charges game time" means the officer is unavailable and the answer is held until that game time (game time itself is not advanced for anyone); busy state is in server memory, so a restart frees the officers; the answer text is still the client fixture until the REST/LLM endpoint in `docs/staff-conference.md` exists, so the server enforces timing, not content; the `askStaff` command is not written to the input log yet.
**Conference answers on the `staff` stage (#318).** A question the desk accepts is answered by `GameActor.answerStaff` (`answerStaffQuestion` in `staff.ts`, prompt `staff-answer-v3`): the officer for the seat (the engineer, who has no engine seat, sees what the chief of staff sees) gets `viewForRole` at the moment of the question and the question text, and the call is on the `staff` stage, so the admin LLM panel lists it and the game's budget and caps apply. The reply goes to the asker as `staffAnswer { questionId, role, text?, basedOnGame, officer }`; the client holds it until `answerAtGame`. With no umpire or no usable reply `text` is absent and the client answers from the view it holds when the answer is *shown*, not when it was asked. The call is logged as a journal-only `staffAnswer` input entry; it never changes the engine and game time does not wait for it. *(Superseded by #323 below: answers are now also filed in the Staff pile, and kept on the server.)* Staff and narration read the newest reports the side has received: the test staff and the client fallback cite the latest contact report or scouting dispatch even when no contact stands in the tables.
**Conference history and dispatches (#323).** The server keeps each side's questions and answers (`StaffExchange`: question id, role, question, asked and answer game times, the answer text, `basedOnGame`, the officer) and sends them in `SideView.staffHistory`, oldest first, so a reload or a reconnect restores the conference. The record is in memory on the actor and, for a restart, in the `staffAnswer` input-log entry (`exchange`); `GameHost.open` rebuilds it from the whole log. An answer's words are withheld from the view until game time reaches `answerAtGame`. When it is due the view also carries one Staff-pile dispatch (id `staff-<questionId>`, from the officer, written and received at `answerAtGame`), so it reaches the in-tray and the journal once. It is display-only like narration: it is built in `sideViewOf` from the side's own history, never put in the engine world, never shown to the other side. A question the stage could not answer (no umpire, or no usable reply) is recorded without words when an umpire exists, and the client fills it from its own view as before; with no umpire at all nothing is kept. `basedOnGame` is the delivery time of the newest report in the officer's view (else the time asked), not the time asked.
**Answers written once, at the due time (#418).** This supersedes the "moment of the question", the client fallback and the text-less record above. (1) *One officer per role.* `conferenceOfficers(seed, side)` in `staff.ts` is the only source of a conference officer's name, rank and traits: `SideView.staffOfficers` (the conference tab), the answer's `officer` (its signature) and the Staff-pile paper's `from` all read it, the unprompted staff (`runStaff`) uses the same officer for the chief of staff, intelligence and quartermaster posts, and no two roles share a name. (2) *Written at the due time.* `GameActor.answerStaff` logs the question at once (a `staffAnswer` entry whose `exchange` has no `text`) and the actor writes the answer when game time reaches `answerAtGame` (D14), from `viewForRole` at that time, so it never quotes anything received later. The actor wakes itself at that time, as it does for a narration window. A model answer is started then, so it arrives after the model's latency (up to two calls): at a fast rate that can be a few game minutes after `answerAtGame`, though still written from the view at the due time. The words, the officer and `basedOnGame` are then stored on the actor and logged in a second `staffAnswer` entry with the model's calls; `GameHost.open` keeps the latest entry per question id. Nothing recomputes them: every later view and a reload show the same words, and a restart restores them. A question still waiting when the game stopped is answered after the restart, from the view at its due time (the world then may be later, but reports are cut at the due time). (3) *Always words.* With no umpire, or when the stage gives nothing usable after its retry, the officer answers from `cannedAnswer`: built on the server from the same view, in a manner that fits the traits (terse gives the bare facts; long-winded gives them all, a caveat and signs off by name; cautious adds a caveat; the rest "I would not wait on it"). The failure is noted on the log entry. `textless` and the client fixture answer remain only for exchanges kept by an older server, and the fixture is then signed with the exchange's officer. (4) *Filed once.* Each answer is one Staff-pile dispatch (`staff-<questionId>`) and one answered journal entry; a question id is refused if used before, including while it is still pending. The hub sends `staffAnswer` to the asker when the answer is written, not when it is asked. Replay needs no model: the entries are journal-only.

**Report text (#318, #323).** Template report text opens with "Sir," for every kind but the umpire's own ruling and spells out "N minutes" ("1 minute"); the narrate input gives N as the lead between the event and the report reaching HQ, never an age against the clock at read time, so a dispatch received at 00:08 does not read "14 minutes since" when opened later. **One phrasing (#325).** The figure is the report's age when it reached HQ, not travel time, and every kind says it as "about N minutes ago" (or "just now" at 0), replacing "N minutes before it reached us". Staff answers open "Sir," for every officer, added by the client (`sirFirst`) when the officer's words lack it. **Map labels (#325).** "Fighting" labels are placed by `placeFightLabels`: north of the ring, else south, east or west and farther out, clear of every unit tag and earlier fight label. No "just now" tag appears on a sighting inside a fight (the fight marker names it), so the docs promise none. **Your games (#325).** `GET /games` adds `winner` to a finished game's row; the list says won, lost or ended (with the winner when you hold no side).
**Open.** Not wired into `GameActor` or the protocol yet: nothing calls `runStaff` on the clock, delivers `StaffMessage`s to the desk, writes the staff records to the input log, or lets a player claim a seat in the lobby. A vacant commander seat is advisory only, since no one can sign for it. Staff do not yet react to events between turns.

## D6c: Shared order drafts: server-sequenced operational transform (story 6.3, #74)
**Decision.** A side keeps shared drafts (`server/src/drafts`: `ot.ts` pure text OT, `book.ts` the document model, `DraftBook`). Sync is **operational transform with the server as the one sequencer**, not a CRDT. A client sends `draftEdit { baseRev, op }`; the server moves the op past every edit that landed after `baseRev`, applies it, gives it the next `rev` and sends the applied entry (`draftEntry`) to every connection of the side, the sender's included (its `opId` is echoed so the sender can tell it). A player who was away sends an old `baseRev` and is handled the same way, so players online at different times need no special case. Edits are idempotent on `(author, opId)`: a resend after a reconnect returns the original entry to the sender (not rebroadcast) and changes nothing. A comment's range is checked against the text length at its `baseRev`. A client that gets `bad_rev` sends `syncDrafts` and replaces its drafts from the `drafts` snapshot that comes back. An op is a list of retain (+n), delete (-n) and insert (string) components over UTF-16 code units. Edits, comments and comment resolutions all take the next `rev` of one history, which is kept whole. Hence tracked edits: each entry names its author and wall time, and the draft carries author runs saying who wrote each stretch of the current text. A comment anchors a range and follows later edits. A read receipt is the highest `rev` a reader has seen (`readDraft`, never backwards). A fork copies the current text into a new draft (`forkOf`); `mergeDraft` moves each of the fork's edits past what the parent gained since the fork, applies them to the parent under their original authors (`viaFork`), and closes the fork (`mergedInto`). A draft holds at most 2000 characters (an order's limit), 5000 history entries and a side 50 drafts. Drafts are stored per game and side (`saveDrafts`/`loadDrafts`, SQLite `side_drafts`), sent as one `drafts` message on connect, and never reach the engine, the input log or replay: they are the players' own writing, and the signed order text is what enters the log.
**Why.** The server already orders everything else, and the text is short, so central OT is a few hundred lines with no tombstones or per-character ids, and its history stays readable as a change log. A CRDT earns its keep for peer-to-peer or offline-first editing, which this game does not have: players are always talking to the server. OT's costs are that every client needs a matching transform to keep its own unacknowledged edits straight (the usual one-in-flight, one-buffered scheme), and that a merge picks a winner when both sides insert at one spot: the parent's text goes first.
**Open.** Not built: the client side (the drafting UI and its transform), the LLM staff check (built in D6d), and `mayDraft` on drafts (a draft has no addressee until it is parsed, so every seat of the side may still propose; see signing below). Suggested changes are made as edits or forks, not as a separate pending-change type. Deleting or discarding a draft is not supported. Long histories are never compacted.
**Signing (#77).** `issueOrder { draft }` signs a shared draft: the server sends the draft's own wording (the signer cannot swap the text), under the same authority rules as a typed order. Anyone with a seat can propose (create, edit, comment, fork); only the commander (any unit) and a subordinate (their own formations, checked once the parse names the addressee) can sign; staff get `not_permitted`. A refused or clarified order leaves the draft open. An order that is issued stamps the draft (`DraftSnapshot.sent`: order id, user, role, wall time); a sent draft takes no more edits or comments (`draft_sent`), cannot be signed again, and can still be forked. The order command in the input log carries the draft's text and the signer's seat, so replay needs no draft. **Authority follows the role.** The hub re-reads a connection's seat from the lobby record before every command (`Hub.setSeatResolver`): a seat that changed (say a subordinate's units) applies at once, and a user who no longer holds any seat on a roled side has the socket closed (1008) rather than falling back to shared HQ, which would let them sign for anyone. Roles still cannot change after the game starts through the API, so this covers a mid-game handover once something does it, and an account merge.

**See.** [gameplay.md](gameplay.md), [architecture.md](architecture.md)

## D6g: The drafting desk in the browser (story 6.4, #76)
**Decision.** The orders desk carries the shared drafts (`DraftsPanelComponent`, in `client/src/app/desk`; pure logic in `client/src/legacy/desk/drafts.ts`). The client half of D6c's operational transform is `DraftSession`: it keeps **one edit in flight** (`draftEdit` with the `baseRev` and an `opId`), turns whatever the player types meanwhile into the next edit by diffing the server's text against theirs (`textOt.diff`), and moves every edit that arrives from others past both, so the caret does not jump. The text OT now lives in `packages/protocol/src/ot.ts` (exported as `textOt`, with `diff` and `reattribute`); the server's `drafts/ot.ts` re-exports it, so the server and the browser run the same code. `applyDraftEntry` keeps the client's copy of a draft in step with `draftEntry` messages; an entry that skips a rev marks the drafts stale and the game service asks for `syncDrafts`. After a reconnect the edit in flight is sent again with the same `opId`, which the server applies once. An edit the server refuses (`bad_op`, `bad_rev`, `draft_closed`, `draft_full`) drops the unsent text and shows the server's. The panel shows the draft list with forks nested under their parent, unread counts (from the player's read receipt), who has a draft open, a read-by list, comment threads anchored to a selection (with replies and resolve), a "who wrote what" view built from the author runs plus a change history, and fork, merge (after a confirmation) and "Use in order" (puts the wording into the order form). **Presence** is new: a `draftPresence` command says which draft a connection has open (or none) and the server answers every connection of that side with a `draftPresence` message listing each player once, their staff role as the label and the drafts they have open. It is ephemeral (not stored, not logged, never reaches the engine), never leaves the side, and carries a role label, never a name or email. "Suggestions" are forks: a staff officer writes an alternative in a fork and the owner of the draft merges it, with every merged edit still credited to its writer (`viaFork`); there is no separate inline suggest mode.
**Why.** Moving the transform into the protocol package avoids two copies that could drift, and a diff-based buffer needs no `compose` and cannot diverge from the server: the next edit is always exactly the difference from the text the server has. Presence rides the same side-scoped broadcast as the drafts, so it adds no new path from master state to a client.
**Open.** The panel does not yet sign a draft (`issueOrder { draft }`, D6c, exists on the server); "Use in order" copies the wording into the local order form. The LLM staff check (D6d) has no button here either. The drafts are not yet filtered by `mayDraft` (see D6a's open note). A player who is not connected is named only if the client saw their label during this session (the server sends labels for connected players); older authors read "Another player". A comment can be added only when the player's own typing has been sent. Text composition (IME) is not given special treatment: a remote edit during composition may interrupt it. The panel is covered by component specs on a fake game and a randomized three-client convergence test; it has not been exercised in a real browser.

## D6d: LLM staff check on a draft (story 6.6, #78)
**Decision.** A player can ask the chief of staff to read a shared draft before it is signed. `checkDraft { checkId, draft }` goes to the hub, which takes the draft's **current text from its own draft book** (a client cannot have other text read), charges the chief of staff `DRAFT_CHECK_COST_MS` (10 game minutes) and sends the side `draftCheckQueued { checkId, draft, rev, askedAtGame, answerAtGame, costMs }`. The reading then goes to every connection of the side as `draftCheck { checkId, draft, rev, basedOnGame, officer, reading?, unitId?, findings[], unavailable?, caveat }`; the client shows it once game time reaches `answerAtGame` (as with conference answers, D6b). The other side hears nothing. `reading` says how a subordinate would most likely carry the draft out; each finding has a kind (`ambiguity`, `missing_place`, `missing_time`, `timing`, `condition`, `contradiction`, `unknown_reference`) and short text, and a `contradiction` with an order already sent names it (`earlierOrder`). `caveat` always says the reading is not a guarantee: the order is parsed afresh when signed, and the check and the parse are separate model calls that can differ.
**Cost.** The check is the chief of staff's time, so it uses the same busy state as a conference question to that officer (`StaffDesk.ask` with a cost): a second check or a question to the chief of staff before `answerAtGame` is `staff_busy`. The deadline is in game time from `GameClock.now()`, so it is the same at rates 1, 4, 12, in manual and fast-forward modes and while paused. A refused request (unknown or empty draft, finished game) charges nothing.
**Fog.** The model (`server/src/orders/staffCheck.ts`, prompt `staff-check-v1`, `staff` stage) sees the draft as data, the side's own units, the named places (as the order parser does) and the orders the side already sent (the same list as `sentOrders`, newest ten), never master state or the other side. Its unit and order ids are checked against what it was shown, its words may cite only what it was shown and may not name the other side's units (`checkProseAgainst`, `hiddenIn`), and a reply that fails is asked for once more, then dropped. The staff share of the game budget applies. With no umpire or no usable reply the message carries `unavailable: true` and no reading; nothing else changes.
**Replay.** The check is a journal-only `draftCheck` input-log entry (side, draft id, rev, the text read, the earlier orders shown, and the model calls), like `staffAnswer`. The engine never reads it, so replay needs no model and the barrier is not involved: game time does not wait for a check.
**Offline.** The test provider answers the schema from rules built on its parser (`testStaffCheck.ts`): parse questions become `missing_place` or `ambiguity`, unknown names `unknown_reference`, and patterns for conditions, clock times, vague timing, hold-and-move demands and conflicts with recent orders to the same unit. It is an approximation to test the plumbing and the corpus; a real model is expected to do better. `staffCheck.test.ts` runs it over the golden order corpus: clear orders get no findings, and each known vague, contradictory, impossible, conditional and timed order gets a finding of the expected kind.
**Open.** No client UI yet (the drafting panel, D6g, does not call it; `draftCheck` is not yet handled in `legacy/net/state.ts`). Not run against a live model, so prompt quality is unmeasured; a recorded-model corpus run like the parser's (`docs/order-eval.md`) is a follow-up. A check reads one draft: it does not compare forks. The earlier-orders list is only orders that parsed to intents (what `sentOrders` holds), and an intelligence seat gets none, as in `sentOrders`. Busy state is in server memory (a restart frees the officer), as for conference questions.
**See.** [gameplay.md](gameplay.md), [staff-conference.md](staff-conference.md)

## D6e: Dissent record and mid-game joining (story 6.9, #81)
**Decision.** Disputes are settled by the commander; a teammate's disagreement is recorded, not voted. A seat holder (any role at the table, not the signer of that order) sends `dissent { dissentId, orderId, body }` against an order the side signed. The hub checks the order in the input log (`signedOrders`, `server/src/journal.ts`) and refuses `own_order`, `no_such_order`, a repeated id (`bad_dissent`), more than 3 per seat per order or 200 per side (`too_many_dissents`), a seatless shared-HQ connection or an intelligence officer, who sees no orders (`not_permitted`; intelligence is also never sent the dissents, which quote orders) and a finished game. `GameActor.recordDissent` keeps it and logs a **journal-only** `dissent` input entry (like `staffAnswer`: no engine effect, nothing to replay, `GameHost.open` rebuilds the list from the log). Each side's connections get `dissents` (the whole list) on connect and after every new one; the other side never does. A dissent names the seat (`seatKey`: role, or the subordinate's units), never the account.
**Critique.** The post-game critique is not built (M4b); `dissentNotes` (`server/src/critique.ts`) is what it will read: each signed order with its dissents in order, from the log alone. `GET /games/:id/window/dissents` serves it behind the same game-over gate as the umpire's window.
**Joining mid-game.** `POST /games/:id/join` with a `role` now also works after the start, until the game is over, for any role nobody holds (`role_taken`, `units_taken`, `bad_units` as in the lobby); the reply has `midGame: true`. `POST /games/:id/leave-role` also works after the start and records a `PastHolder` (`LobbyGame.past`). A joiner's `RoleSeat.succeeds` lists the earlier holders of the same seat (same role; for a subordinate, the same units). The commander seat is not handed over (follow-up). The pause and ratio voters follow role changes in a running game (`setVoters`: a joiner may vote, a leaver's vote is dropped; an open vote is not re-counted and settles on the next vote or its timeout).
**Briefing.** On connect a mid-game joiner gets `briefing { seat, atGame, items }` (`buildBriefing`, `server/src/briefing.ts`, pure) from the journal of the seat they took: the orders it signed, its dissents, its staff questions with answers (all matched by `seatKey`), and the drafts and comments written by the accounts in `succeeds`. Everything in it was the seat's own work or on its side's desk, so the briefing does not widen what the seat may know; it is deterministic (no model call) and rebuilt from the log on every connect. A commander or a player who joined in the lobby gets none.
**Open.** No desk UI shows dissents or the briefing yet (`ClientState.dissents` and `.briefing` hold them); the commander seat cannot change hands; the critique text is not generated; a vote is not re-counted when a voter leaves.

## D15a: Annotated terrain layer: road classes, bridge capacity, fords (story 2.3, #28)

**Decision.** The truth layer is the `map` of a scenario (`parseTerrain` validates it; metres on the wire, mm in state). Besides the D15 attributes a feature may carry: `roadClass` on a road (`highway` 0.4, `road` 0.5, `track` 0.8 march-cost multiplier, `ROAD_CLASS_COST`; an explicit `moveCost` still wins), `capacity` on a bridge or ford (the widest marching column it carries, metres; default its diameter), and `risk` (0..1) on a ford. Fords are passable but slow (move cost 3, against 1 for a bridge) and carry a risk that the planner does not price: it is data for the umpire. Height tags (`height`: low, flat, rise, high) are set per feature and already feed line of sight, so a ridge or slope is a polygon with `height: "rise"` or `"high"`. Pathfinding prefers better road classes and fords only where they save more than they cost, and refuses a column wider than a crossing's capacity.
**Grid.** There is still no grid in the model. `rasterise(map, cellMm)` samples the vector map at cell centres into rows of glyphs for checking an annotation and for previews; nothing in the engine reads it. `SAMPLE_TERRAIN` is the documented tiny sample.

## Order de-duplication and rate limit — 2026-10-12
`Hub` ignores an `issueOrder` whose `orderId` a side has already sent (`duplicate_order`) and caps each connection at 3 orders parsing at once and 30 per wall-clock minute (`rate_limited`). ## Cross-side leak suite for LLM stages — 2026-10-12 (#44)
**Decision.** `server/src/umpire/leak.test.ts` plants canaries (distinctive unit names, officers and exact strengths) in the master state of a game in which both sides have met, runs the parse, narrate, staff (turns and conference answers) and command stages for each side, and fails with the secret, what it is and where it turned up (`LEAK: "Wrobeln Cuirassiers" (red-2 name) reached blue staff messages`). It checks three things: what a side's prompts carry holds no canary of the other side, a well-behaved model's output (the test provider) delivers none, and an adversarial model that names the other side's units, officers, ids and figures is stopped by the stage's checks. `LEAK_REAL_MODEL=1` (with `UMPIRE_PROVIDER` and its keys) runs the same corpus against a real model. The harness, `leakKit.testkit.ts` (`plantCanaries`, `LeakProbe`, `ScriptedModel`), is shared on purpose: the prompt-injection suite (#350) feeds hostile text through the same probes.
**What the suite found, and the fix.** Narration already refused invented names, numbers and ids. Staff messages checked only ids, and the parse stage passed a rejection reason or clarification question through as the model wrote it, so a model that named an enemy colonel or quoted an exact strength reached the player. Now (1) `checkStaffOutput` runs `checkProseAgainst` over each message: every number and every capitalised name (a sentence's first word excepted, as free prose needs imperatives) must be in the view the officer was given, and `hiddenTerms` (the other side's unit names and officers, `leakGuard.ts`) is refused outright, which also covers a name at the start of a sentence or written in lower case (the suite's `nameLower` and `commanderLower` variants fail without it); a term that one of the side's own units also bears is left out of `hiddenTerms`, so two sides sharing a unit name do not refuse each other's own wording; (2) `LlmOrderParser` applies the same checks to a rejection's reason and a clarification's question and options, and refuses the other side's unit names and officers (`ParseContext.hidden`, from `hiddenTerms`, so a lower-case commander too), and the ids of its units unless the player wrote them in the order; a refused reply takes the parser's usual fallback; (3) the LLM commander drops an order whose text names a hidden unit, officer or id before it is parsed. A figure is checked by the number rule, not by the list of terms, since an exact strength also matches ordinary numbers (a distance, a time).
**Limit.** The number and name rule on staff messages also refuses derived figures ("twice their number", a sum of two strengths); it has been tested only with scripted models, not measured against a real one, so whoever tunes the staff prompt should run `LEAK_REAL_MODEL=1` and watch the rejection rate. The name check cannot see a single-word name that opens a sentence and is not in `hiddenTerms` (a name the master state does not hold). Prompts never carry such names; the checks are the second line.

**Staff answer quality gate (#359).** `checkAnswerText` also rejects an answer that repeats a five-word phrase, uses stock filler ("observing the enemy's movements", "be prepared for any"), or names no unit, place or count from the officer's view. The reason goes back in `rejected` for the one retry; after that the officer gives the canned answer (`cannedAnswer`, on the server since #418). The #342 fragment check is kept.

**Narration per report (#359).** `narrateReports` makes one short call per report (prompt `narrate-dispatches-v3`, at most `NARRATE_MAX_REPORTS` = 6 newest per window; older ones keep the template text) instead of one call for the whole window, because a 0.5b model rejected or timed out on long batches while a single report passes the checks. A report that fails twice keeps its template text and the others keep the model's prose (`fallbacks` lists each report and why; the admin LLM panel shows a row per fallback). The call also rejects hidden names in any case (`hiddenIn`), which the batch form had only hidden behind "report not narrated".

**Dispatches as field notes (#390).** Prompt `narrate-dispatches-v5` asks for a hasty first-person note from the sending officer, not a restatement of the report: two or three sentences with his judgement and, where the report and his state call for it, one question or concern for the general (pursue a destroyed enemy, fall back after heavy losses, hold or be relieved when short of ammunition or spent). Each report in the input now also carries the sender's `commander`, public `trait` and `condition` (morale, fatigue and ammunition as words such as "shaken, tiring, ammunition running low", `unitCondition`), taken from the side's own `ownUnits`, so nothing beyond the side view and no new figure reaches the model. `unitLost` and `courierLost` reports are not from their unit (it is destroyed, or never had the orders), so they carry no sender and the prompt has them written by the staff at HQ in the third person. The condition buckets "spent" and "ammunition nearly gone" start at the engine's `EXHAUSTED_FATIGUE` and `LOW_AMMO`. The prose check also accepts question, request and imperative openers ("Shall", "Should", "May", "Must", "Request", "Hold", "Pursue", "Orders", "Advise" ...), and the commander's name, trait and condition words count as known words. The persona's voice colours the officer's note and does not change who writes it. The `dry` persona keeps its plain voice but no longer asks for terse prose. The hidden `personality` traits (D36) are still never sent.

## Judge stage and per-game case law — 2026-10-12 (#42, story 3.6)
**Decision.** The engine's `judgment.ts` holds the bounded discretion for situations no rule covers. A caller raises a `JudgmentRequest` (`key` names the kind of situation, `situation` is the question in words); the `judge` stage (`judgeSituation`, prompt `judge-situation-v2`) returns a `JudgmentProposal` (a `modifier`, `rationale`, `narrative`); `issueJudgment` queues it whole and the handler clamps the modifier to `JUDGMENT_CAP` (±0.25, a fraction of the rule's figure), applies nothing else, and records a `JudgmentRuling` in `world.rulings` (`requested`, `modifier`, `clamped`, `fallback`, `precedent`). The event carries the full proposal, so replay needs no model call. **Case law** is not a separate store: it is the game's non-fallback `JudgmentRuling`s (`caseLaw(world)`), so it persists and replays with the snapshot and never crosses games. It goes into every judge prompt. **Consistency:** the first ruling on a `key` is the precedent (`precedentFor`); a repeat of that key follows it with no model call (`precedent: true`), and a different key sees the case law in its prompt. **Weak or absent model:** answers are checked (finite modifier, non-empty rationale and narrative, narrative checked by `checkProseAgainst` against the prompt's own facts and any `hidden` names); a bad answer or a failed call is retried once (`maxCalls` 2), then the standard rule stands (modifier 0, `fallback: true`, which is no precedent, so a later call may still ask the model). The test provider answers modifier 0 with fixed wording. Ambiguity resolved simply: one modifier per ruling, `judgmentModifier(world, key)` reads it for the rule that wants it.
**Open.** No engine rule raises a judgment yet, so the actor does not call `judgeSituation` and registers no barrier dependency; the first raiser must hold game time at the request like an order parse (D14) and queue the proposal at that time. The modifier's use is the raiser's (for example scaling a ford crossing speed). `judge` is not Ollama-eligible, so a local setup falls back to the test provider for it. A followed precedent replays the stored narrative only for the same `unitId` and when it names no `hidden` term; otherwise the generic sentence is used. A raiser for a different side should also pass that side's `hidden` names. Followed precedents are not listed in `caseLaw` again.

## D38: Admin clock controls — 2026-10-12 (#128)

**Decision.** The admin view can pause, resume, step (1 min, 5 min or to the next queued event) and change the rate of a game's clock, from a control bar on the admin page. They are `POST /admin/api/games/:id/clock`, gated like the reads, and go through the same actor queue and clock as the host's own `pause`, `resume` and `setRate` commands. Stepping is a new `step` command: it moves game time forward in any mode, leaving the mode and pause state as they were (`GameClock.skipTo`, one `advance` history entry), with the target resolved inside the actor's queue and logged on the command. Every control is an input-log entry marked `admin: true` and a traced `command`, so replay stays exact and the audit trail shows who moved the clock. Rates are 1, 4, 12 or a custom value up to 1000.

**Why.** Debugging a stuck or slow demo game needs time to be held and stepped without editing the database. Reusing the command path keeps the LLM barrier (a step stalls at it, and replay follows the logged end time, not the target), pause voting state and replay unchanged.

**Open.** No event injection. A controlled game's players are not told that an admin moved the clock. The route is as open as the admin API (`ADMIN_OPEN` lets anyone use it); do not expose it publicly.

## Information forwarding and chain-of-command messaging — 2026-10-12 (#79, story 6.7)

**Decision.** The lobby record has a `hierarchy` (`shared`, the default, or `chain`; `POST /games` takes it). In **shared HQ** forwarding is instant and HQ sees every report of the side, as before. ## D6f: Deputy mode: an LLM officer who signs within a discretion the engine checks (story 6.8, #80)
**Decision.** A commander (or, in shared-HQ play, anyone on the side) sends `setDeputy { enabled, discretion, intent }`. `discretion` is `hold`, `adjust` or `act` (engine `DISCRETIONS`, `packages/engine/src/deputy.ts`); `intent` is the player's words, at most 600 characters, given to the model as data. The actor then runs a `DeputyAgent` (`server/src/deputy/deputy.ts`) for that side: a `SideAgent` that decides every ten game minutes, but only while the player is away (`Hub.isAway`: no open connection for the seat, or for the side in shared HQ), on the `staff` stage (prompt `deputy-v1`, so staff's budget share applies and a refused call is a quiet turn). It sees the side's `EngineSideView` (`assertFogOnly`), the player's intent, the discretion text, the units' standing orders and the named places, and writes orders as free text. **The engine, not the model, enforces the discretion:** each order goes through the ordinary `OrderParser`, then `deputyProblems` refuses it unless the player's own seat could sign it (`maySign`) and it is within the level. `hold`: a hold within 300 m of where the unit stands, or a withdrawal (below `act`, a withdrawal must fall back toward the side's own HQ, since one toward the enemy is a move); `adjust`: also a move or hold up to 1500 m at the ordinary pace (no forced march); `act`: anything. A `when`/`at` order is judged by what it would do. An order that names an enemy unit the side has not seen (`hiddenIn`) is dropped, and a report that does is blanked. A refused order is never sent.
**Orders and replay.** Allowed orders are issued at the decision's game time through the human order path and logged as `agent: true` entries with `deputy: { discretion }`; the engine `Order` carries `deputy: true`. Replay reads the logged parse and calls no model. Decisions are on multiples of ten game minutes, so they are the same at every rate and in fast-forward; a dormant deputy (player present) marks itself idle, and `noteDeputyPresence` wakes it when a connection closes. `deputySet` (the settings) and `deputyTurn` (the account of a turn) are journal-only input log entries, from which `GameHost.open` rebuilds both after a restart.
**What the player sees.** One `Dispatch` per turn (id `deputy-…`, from "Your deputy", category staff) in the in-tray listing the orders signed in their name, the refusals with reasons, and the deputy's own report; and `SideView.deputy { settings, account }`. Only the seats that run HQ (commander, chief of staff, shared HQ) are sent either; a subordinate or other staff seat gets neither.
**Why.** The player's trust depends on the deputy being unable to exceed the setting, whatever the model writes or an injected enemy dispatch tells it to, so the limit is code, tested without a model. Reusing the agent path gives the LLM barrier, the input log and replay for free.
**Open.** No settings or account UI: the account arrives as an ordinary in-tray paper, and `setDeputy` is WebSocket only. One deputy per side, appointed by the commander for the commander's authority; a subordinate cannot appoint one. The check is by distance and pace, not by purpose, so `hold` does not stop a withdrawal that gives up ground to HQ; "within standing orders" is the model's reading of the standing orders it is shown, not an engine test. There is no per-turn or per-game cap on orders beyond four a turn. A turn whose call fails or is refused by the budget writes nothing. Deputy orders are flagged on the engine `Order` but the client does not mark them yet.
**See.** [gameplay.md](gameplay.md), [architecture.md](architecture.md)

## D38: The post-game critique cites only events in the log (#82, story 6.10)
**Decision.** Once a game is over, `GET /games/:id/critique` (seated, `403 game_not_over` before the end, behind the same gate as the umpire's window) returns the umpire's critique: what each side knew and when, the decisions that mattered, misreadings and pauses. It is built in three steps. (1) `critiqueFacts` (`server/src/umpire/critiqueFacts.ts`) replays the input log (no model, no wall clock) into a digest of dated facts with ids `fact-N`: the result, every order sent, deliveries with their delay, intercepted or garbled couriers, contacts, units broken or destroyed, casualties per ten game minutes, the umpire's rulings, each report a side received (observed at, reached headquarters at), **misreadings** (a contact report whose subject stood beyond the report's uncertainty from the reported spot when it arrived; up to 8 true-position replays) and **pauses** (pause and resume votes, failed votes, restarts, ratio changes; never the voter's id). Each kind is capped so a long game stays within a prompt. (2) The `critique` stage (prompt `critique-v1`, default model Sonnet; `UMPIRE_STAGES`, `gameLimits` and the mock umpire know the new stage) is shown only that digest and returns a summary and up to twelve points, each with a kind (`knowledge`, `decision`, `misreading`, `pause`, `outcome`), a side, a game minute, text and `cites`. (3) `checkCritique` refuses a reply unless every cite is a fact of the digest, `minute` is the minute of one of its cites, a `knowledge`, `misreading`, `pause` or `outcome` point cites a fact of that kind, the side is real, and the prose names no id, unit, place or figure the digest does not hold (`checkProseAgainst`, as for staff and narrate). A refused reply is asked for again with the problems listed (`maxCalls` 2); after that, or if the umpire fails, is over budget or absent, `templateCritique` quotes the facts themselves (`source: 'template'`), so a critique always exists and always cites real events. This is the acceptance rule: a critique cites only events that exist in the log.
**Logged and replayable.** The first request writes the critique and appends a journal-only `critique` input-log entry holding the text and the model calls (`calls`), like `narrate` and `staffAnswer`; replay ignores it, later requests and restarts serve the stored text with no model call, and concurrent first requests share one run (`CritiqueService`, `server/src/api/critiqueService.ts`). A template written because no umpire was configured is not stored, so a later umpire can still write one; a template after rejected replies, a schema failure or a refusal is stored, so the same cost is not paid on every visit. A request waits at most 120 s for the umpire, then serves the template while the run carries on and is stored when it lands. The wire shape is `Critique` in `packages/protocol/src/critique.ts` (cites carry their minute and a short label).
**Shown.** The umpire's window has a Critique section: the summary, then each point with its kind, side and minute, and its cites as buttons that move the scrubber to that minute. It says when the text is the log's own wording.
**Leaks.** The critique carries master facts (both sides' reports, true positions in the misreading figures), so it is served only after the game, like the window; nothing in it is sent during play. Player order text is in the digest as data, truncated to 120 characters; the checks above bound what the model can say about it.
**Open.** The model sees the digest, not the dice or the map, so it can say little about why a fight went as it did beyond the casualty and ruling facts. Roles and dissent (#72, #74, #77 to #79) are not facts yet: the digest has no signing, forwarding or staff-check facts, and a draft disagreement is not recorded in the log, so the critique cannot mention dissent until it is. The check is lexical and structural: it cannot catch a wrong claim made of known words about real facts (for example crediting the wrong side), only an invented one. The text is English only. Local Ollama setups answer this stage with the test provider (`OLLAMA_STAGES` does not list it), which quotes facts. Not verified in a real browser.

## D39: Turn-based umpire mode: the umpire proposes a turn, the engine keeps the record and is the fallback (#397, story 11.1 of Epic #393)
**Decision.** A second way to play, chosen when a game is made and fixed for the game: a **turn-based game** in which every side's orders for a slice of game time are collected and sent together, and the umpire (a capable LLM, acting as a free-Kriegsspiel umpire rather than a rules clerk, `research.md` §2-3) decides what happens in that slice. It amends D1 (hybrid adjudication) and D4 (continuous clock) **for this mode only**; the real-time mode, its parse stage, judge cap, barrier and narration are unchanged. The engine stays the single store of state, checks every proposal against hard limits, rolls every die, and resolves the turn itself whenever the umpire cannot. Pipeline: collect, project, adjudicate, validate and clamp, apply, report, advance (see [architecture.md](architecture.md#turn-based-mode-the-turn-pipeline)).

**Setting (11.3, #399).** `UmpireSettings` (`packages/protocol/src/umpireSettings.ts`) gains, next to `dial` and `persona`: `mode: 'realtime' | 'turns'` (absent means `realtime`, so every existing game, header and replay is unchanged), `turnMinutes` (game minutes per turn, default 20, an integer from 5 to 60), and `turnDeadlineHours` (optional, wall-clock hours for asynchronous play; absent means the turn waits until every human side has sent). They travel the same way as the dial: `POST /games` body, the lobby record's `umpire`, the input-log header `settings` and `games.settings`. The rate setting is ignored in turn mode.

**Clock (11.3).** A turn-mode game runs its `GameClock` in `manual` mode for its whole life; nothing advances game time except resolving a turn. Turn `n` (from 1) covers game time `[T0, T1)` with `T0 = (n - 1) x turnMinutes` and `T1 = min(T0 + turnMinutes, deadline)`, where `deadline` is the scenario's time limit (`holdMs`, D13): the turn that contains the time limit ends at it, so the game ends at the same minute at every dial. A side sends once per turn; any seat whose role may sign orders (D6a) can send for it, and that send is final for the side (two seats cannot each send part of a side's orders; they share the side's held drafts until one sends). A turn **closes** when every human side has sent (`sendTurn`) or the deadline passes (a wall-clock timer on the actor, like a pause-vote timeout). The close is the `resolveTurn { turn, cause: 'all-sent' | 'deadline' }` input, so replay needs no wall clock. Scripted and agent sides are not waited for: they think at their own interval (see "Scripted sides in turns (#430)"). A side that sends nothing sends an empty set: its units carry on with their last delivered orders. Once a turn has closed, its resolution runs, and only after the turn is applied does the actor `advanceTo(T1)`. No LLM barrier holds a running clock, because there is none: a slow umpire makes the players wait for their reports, it does not stall or skew game time. The `staffAtWork` indicator shows that the umpire is adjudicating. Pause voting and the ratio vote are refused in turn mode (there is nothing to pause); the turn deadline is the only wall-clock element.

**Orders in turn mode.** An order is free text with an **addressee chosen on the desk** (the orders desk already addresses each draft to a unit) and the existing courier choice: `TurnOrder { orderId, side, to: unitId, text, courier: 'fast' | 'safe', signer? }`. Role permissions (D6a) apply at sending as for a real-time order. The umpire reads the text as written; there is no parse or interpret stage call in turn mode. The structured parse is kept in two places only: in real-time mode, unchanged; and in turn mode the **rules parser** (`server/src/umpire/providers/testParse.ts`, the canned rules of #389) turns each order into intents with no model, for the engine's projection and for the engine adjudicator. In turn mode it runs with two changes to its real-time rules, made as part of 11.4: the addressee is `TurnOrder.to`, never guessed from the text (no "nearest unit" rule); and an order with a condition or a time ("if the bridge is lost", "at noon"), which the rules cannot express, is not stripped to its plain verb but projects as "no new order", like a clarification or refusal. The engine adjudicator carries such an order out as "no new order"; under the umpire the text still counts. So whatever is decided about PR #394 must keep the rules parser able to answer every order this way; turn mode needs nothing from the parse stage's model path.

**Couriers across turns.** Couriers stay engine entities (D11, "Courier model v2"). Every order sent for turn `n` sets out at `T0`. Each turn's couriers are decided **once**, before anything else, by the **courier pass**: when the turn closes, the engine takes the start-of-turn state, issues the turn's orders at `T0` with the turn flag set (units held, as in "Applying an umpire turn") and advances to `T1`. That rolls every courier riding in the turn exactly as now (route, delivery time, loss, garbling, and interception against the enemy at its `T0` position, since units are held). Its results, `TurnCourier { orderId, outcome: 'delivered' | 'riding' | 'lost' | 'intercepted', atMs?, garbled? }`, are fixed for the turn: the umpire is told them, the projection and the engine adjudicator carry each courier to the same outcome with no roll of their own (see "The projection"), and an umpire turn's apply step is this same pass run on the real world (same state and RNG, so the same results; a difference fails loudly). A courier still riding at `T1` keeps its route and due minute, and the next turn's pass continues it against that turn's `T0` positions. An order whose delivery time falls inside `[T0, T1)` reaches its unit at that minute: the umpire is told "arrived at minute m" and the unit can act on it only from then. An order still riding at `T1` is shown to the umpire as "on the road, due at minute m of turn k" and may not be acted on; it is delivered in the turn its arrival falls in and is then given to that turn's umpire with its original text. A lost or intercepted order never reaches the umpire as an order (the captor's document and the lost-courier report work as now). A garbled order reaches the umpire with its true text and a `garbled: true` flag, and the umpire must have it misread (the engine adjudicator keeps the existing destination shift).

**The three adjudicators, chosen by the dial.** In turn mode the dial picks the adjudicator; the judgment cap (`DIAL_CAPS`) is a real-time mechanism and is not used.
- `rigid`: the **engine adjudicator** (11.4, #400) alone, with no model call. The real world is advanced exactly as the projection was (below): the turn's orders, rules-parsed, delivered at their courier-pass minutes, and the ordinary handlers (movement, combat, morale, rally, supply, visibility, victory) from `T0` to `T1` on the same RNG, so it ends in the projection's state. Its reports are the engine's own reports in their template text, with no report call. This is real-time play stepped in fixed slices.
- `standard`: the **umpire** adjudicates, given the engine's projection of the turn as the reference. Any unit outcome that departs from its projected outcome by more than the departure tolerance (100 m in end position, or 5% of its start-of-turn strength in losses, or a different status) must carry a `departure` reason. A departure with no reason is a problem (see "Validation"); after the one resend it is clamped to that unit's projected outcome.
- `free`: the umpire adjudicates with the projection given as **advice only**; no departure reasons are required. The hard limits are the same.

**The projection (11.4).** Before any model call the engine resolves the turn on a **copy** of the start-of-turn state: the rules-parsed orders issued at `T0` as courier entities whose outcomes are forced from the turn's `TurnCourier` results (11.4 adds a forced-outcome option to `ORDER_ISSUE` and `COURIER_STEP`, so they draw no rolls), then `advanceTo(T1)` under the ordinary handlers, starting from the RNG state the courier pass ended with. Its courier state at `T1` (`world.couriers`, including those still riding, captured documents and lost-courier reports) therefore equals the courier pass's, so in a `rigid` or fallback turn the real world keeps riding couriers for the next turn's pass and files the captures and reports as now. It is pure and deterministic (same seed, same state, same result), costs no model call, and gives a per-unit outcome (end position, facing, formation, strength, morale, status, fatigue, ammunition), the combat events, the sightings and the reports it filed. It is what the umpire is shown as reference or advice, and it is exactly what the engine adjudicator applies.

**The umpire's input (11.6, #402).** The umpire sees master state: it is the umpire. One call gets the start-of-turn state (units with position, facing, formation, strength, morale, fatigue, ammunition, status, standing intent), the map's named features, every side's turn orders as written with their courier status and arrival minute, the addressed commanders' personality traits (D36: master state, which the umpire may use to have an order carried out as that commander would, misunderstanding included), the projection, the umpire's journal (11.8, #404) and the game's case law. Order text is data, never instructions, as in every stage.

**The proposal.** The umpire returns a `TurnProposal` (zod schema in `packages/protocol`, so 11.2 can grade against it and 11.5 can apply it); metres and degrees on the wire as in `judgePlacement`:
```ts
TurnProposal {
  turn: number;                        // must equal the turn being resolved
  units: UnitOutcome[];                // exactly one per unit not destroyed at T0
  observations: Observation[];         // what each side's units saw this turn
  rolls?: RollRequest[];               // first call only; see "Dice"
  summary: string;                     // the umpire's account for the record; never sent to a side
}
UnitOutcome {
  unitId: string;
  x: number; y: number; facingDeg: number; formation: Formation; shape?: [number, number][];
  strength: number;                    // men at T1
  morale: number;                      // 0..100 at T1
  fatigue?: number; ammo?: number;     // 0..100 at T1; absent means the projected value
  status: 'active' | 'broken' | 'destroyed' | 'captured';
  continuing: { kind: 'idle' } | { kind: 'hold' } | { kind: 'move'; x: number; y: number };
                                       // standing intent carried into the next turn's projection
  orders: { orderId: string; result: 'carried-out' | 'partly' | 'misread' | 'refused' | 'not-arrived' }[];
  account: string;                     // what its commander did and why, in character (master; 11.9 filters it)
  departure?: string;                  // why it differs from the projection (required under `standard`)
  rollIds?: string[];                  // the rolls this outcome rests on
}
Observation { side: string; unitId: string; by: string; when: 'start' | 'end' }  // `by` is the side's own unit
RollRequest { id: string; why: string; chance: number }                          // 0 < chance < 1
```
Invariants the schema and validator enforce: `turn` matches; every unit id exists, appears once, and every unit not destroyed at `T0` appears (a destroyed unit may not); each listed `orderId` is an order sent to that unit (in this turn or earlier), and it is `not-arrived` exactly when the order had not reached the unit by `T1`; strings are bounded (account and departure 600 characters, summary 2000); at most 8 rolls.

**Validation and clamps: the hard limits (11.5, #401).** The engine checks the proposal against the start-of-turn state, in unit-id order, and never edits it in place:
- *March over the ground*: each end position goes through `validatePlacement` (D10) from the unit's `T0` position with `elapsedMs` = the turn length (inside the map, passable ground, no further than its march rate allows along the cheapest route in the turn). As written it cannot do this check (it rejects any unit not `active` and checks overlap against both sides' `T0` positions), so 11.5 gives it a turn option, `{ allowWithdrawn: true, overlapWith: 'friendly' }`, and calls it on a scratch world in which every unit not destroyed stands at its proposed end position: only overlap with a friendly unit at `T1` is a problem (two opposing units placed in contact may overlap, as in melee), so the result does not depend on unit-id order. `clamp` takes the reached point; `reject` keeps the `T0` position, and a unit put back at `T0` is checked again against the friendly end positions (if it still overlaps, the other unit is put back too, in unit-id order).
- *Strength*: `0 <= strength <= T0 strength` (no unit gains men in a turn). Strength 0 means `destroyed`. A unit no enemy could reach in the turn (outside every enemy's D13 contact range plus that enemy's march for the turn, at `T0` and at `T1`) takes no combat loss; any loss it shows is clamped to the projection's.
- *Bounds and status*: morale, fatigue and ammunition in 0..100; ammunition does not rise except by the engine's supply rule (the projection's value is the ceiling). `destroyed` and `captured` are final (a captured unit is stored as `destroyed` with the cause recorded on its ruling); `broken` becomes `withdrawn` with `brokenAt = T1` (so pursuit and rally rules see it next turn). Rally stays the engine's `combat.rally` chain (D13, Combat v2): in a held turn its handler does not roll but reschedules itself `retryMs` later (the 40-minute give-up still counts from `brokenAt`), and `umpire.turn` schedules the first `combat.rally` for each newly broken unit `firstTryMs` after `T1`, as a break in real time does, so the chain runs in later `rigid` and fallback turns. A proposal may set a unit `withdrawn` at `T0` to `active` only if the outcome cites a roll (11.7) and the unit meets `RALLY_RULES`' strength share, give-up time and enemy-clear distance at `T1`; otherwise it is clamped to `withdrawn`.
- *Observations*: an observation stands only if the observing unit is the side's own and the engine's sight test (`viewFor`'s range, line of sight and concealment, D12) passes between the two units at the end its `when` names, and only there: `start` is tested on the `T0` positions, `end` on the applied `T1` positions. Others are dropped, and anything in a side's reports that rests on them is refused (11.9).
- *Orders*: an `orderId` the unit had not received by `T1` must be `not-arrived`. This is checked on the `result` value only: the validator has no link from an outcome to the order behind it, so it does not try to tell whether an outcome "depends on" an order (nor, for the reach rule above, on anything but positions).
A proposal with problems is sent back **once** with the problems listed (as narrate and the critique do). Whatever is still wrong after that is clamped as above. Every check that changed something is recorded as a `TurnRuling` in `world.rulings` (`kind: 'turn'`, unit, field, proposed, applied, reason), so the admin view and the critique can show and explain every clamp.

**Applying an umpire turn (11.5).** The real world is not run through the movement and combat handlers in an umpire turn. At `T0` the engine runs the courier pass on the real world (couriers ride and roll as above, an arriving order is recorded as delivered and acknowledged, but no unit adopts an intent from it), advancing to `T1` with the world's turn flag set (`GameState.turn = { n, startMs, endMs, adjudicator }`): movement, combat, rally and pursuit handlers do nothing for a held turn, and the minute scan records no sightings. At `T1` one `umpire.turn` event carries the whole validated proposal and its rolls: it sets each unit's outcome fields, ends every march leg, sets each unit's standing intent from `continuing`, writes each stood observation into `intel` as a sighting at the end it was valid for (a `start` observation at `T0` with the `T0` position, an `end` one at `T1` with the applied position, so last-known contacts age from there as now), records the rulings, and then runs one victory check (objective held, broken force, deadline; D13) on the applied state. In an umpire turn the objective's `takeMs` is counted between turn ends: the attacker takes it at the first turn end at least `takeMs` after the turn end from which only it has held. In `rigid` and fallback turns the ordinary victory handlers run inside the turn as in real time, so `takeMs` is counted to the minute there (see Open). The engine's own reports for the turn (`engaged`, `heavyLosses`, `broke`, `unitLost`) are not filed in an umpire turn; each side's reports come from 11.9.

**Dice only when asked (11.7, #403).** The umpire rolls no dice itself. If the first reply lists `rolls`, the engine rolls each, in id order, as one draw (`rng.next() < chance`) and records `{ id, why, chance, roll, success }`. The umpire's dice have their own stream, `new Rng(seedRng(r0 ^ n))` where `r0` is the world's RNG state at `T0` and `n` the turn number; they never advance the world's RNG, so the courier pass, the projection and the fallback all draw from the same state whether or not the umpire asked for rolls; a second call shows the results and asks for the final proposal, whose outcomes cite the rolls they rest on. A final proposal may not ask for more rolls. The engine adjudicator keeps its ordinary dice.

**Fallback: a turn always resolves.** Any umpire failure falls back to the engine adjudicator for the whole turn: a transport error or timeout (`adjudicateTimeoutMs`, default 300 s, retried per D14's attempts), the whole adjudication (every call, retry and resend of the turn) running past `adjudicateTurnTimeoutMs` (default 15 minutes of wall clock), a spent per-game budget or rate limit (`GameUmpireClient`), a refusal, a reply that fails the schema after its repair attempts, or a proposal the validator would clamp in more than half of its units after the resend (taken as an umpire that has lost the thread). The turn is then resolved exactly as `rigid` would, from the same start state; the failure is logged on the turn's input entry, and each side's in-tray says in-fiction that the umpire's staff resolved the turn by the tables. Partial proposals are never mixed with the engine's resolution.

**Fog of war.** The umpire sees everything, as Reisswitz's umpire did; nothing it is given or returns goes to a side directly. Each side's reports (11.9, #405) are written from that side's own view after the turn is applied (`viewFor`, D12, the only path from master state to a client), plus the `account` of its own units only; the output passes the existing checks (`checkProseAgainst`, `hiddenTerms` from `leakGuard.ts`), and a refused report falls back to template text built from the side's view. The `summary`, the projection, other sides' accounts, departures and rolls stay in master state until the game is over (umpire's window, critique).

**Logged for replay (11.3, 11.11 #407).** Two new input-log commands. `sendTurn { side, turn, orders: TurnOrder[], signer? }` is journal-only (the held orders, so a reload shows what was sent). The hub never sends one side's `sendTurn` or held orders to another side; other sides learn only that it has sent (`turnState.sent: SideId[]`), so held orders are visible to their own side only. `resolveTurn { turn, cause }` carries everything replay needs on its `InputLogEntry`: `turn: { n, startMs, endMs, cause, orders: TurnOrder[] with their rules parse, couriers: TurnCourier[], adjudicator: 'engine' | 'umpire', proposal?: TurnProposal (the final raw proposal), rolls?: TurnRoll[], rulings?: TurnRuling[], fallback?: { error, attempts } }` and `calls: UmpireCallRecord[]` (adjudicate and report calls, as for `narrate`). The entry's `gameMs` is `T0` and `endGameMs` is `T1`. Replay advances to `T0` and runs the courier pass (its results must equal the logged `couriers`), then either advances as the projection does (`engine`) or redraws the rolls from the umpire's dice stream (they must equal the logged `rolls`) and applies the logged proposal through the same validator and `umpire.turn` handler (`umpire`); any difference from the logged couriers, rolls or rulings fails the replay loudly. No model is called. A projection is not logged: replay recomputes it from state wherever the validator needs it (the departure check under `standard`), and the admin view does the same. The per-side reports are journal data, like narration: replay does not need them, the window shows them.

**Cost and stages.** A new umpire stage, `adjudicate` (default model Sonnet; Opus where the benchmark says it is worth it), added to `UMPIRE_STAGES`, `gameLimits` and the mock umpire; the reports use the `narrate` stage route. Per umpire turn: one adjudicate call, a second when rolls are asked for, and one resend when the validator finds problems (so at most three adjudicate calls, within `adjudicateTurnTimeoutMs`), plus one report call per side. A `rigid` or fallback turn makes no model call: its reports are the engine's templates. Budgets and per-game caps apply as for every stage.

**Keyless demo.** `adjudicate` is not an Ollama stage by default (not in `OLLAMA_STAGES`), so the keyless demo answers it with the `test` provider, whose canned adjudicator returns the projection as the proposal with no departures. The demo therefore plays turn mode at every dial as the engine resolves it, with the same badge as for other canned stages. Whether a local model is good enough to be the default is decided by the benchmark (11.2, #398), not here.

**As built (11.5, #401).** `TurnProposal` is the zod schema in `packages/protocol/src/turn.ts`; the engine, which depends on no package, mirrors it in `packages/engine/src/turn.ts` and a server type test keeps the two equal. `validateProposal(world, proposal, { turn, dial, projection?, orders?, rolls? })` is pure and returns the applicable outcomes, the observations that stand, every correction and the problem list for the resend; `issueTurn` queues `umpire.turn` with the raw proposal and that context, and the handler runs the same validator before it applies. Where D39 left a detail open, 11.5 settled it as follows:
- A proposal for another turn is not clamped: `validateProposal` returns `fatal` (the pipeline falls back) and `umpire.turn` throws on one, since the log and the world then disagree.
- An outcome for an unknown unit, a repeated outcome (the first stands) and one for a unit destroyed before the turn are dropped; a unit with no outcome takes the projection's (or, with no projection, stays as it was). Each is a correction. The projection's position is where its unit stands at `T1` (`positionAt`, part-way along a leg if it is still marching), for the default and for the `standard` departure check.
- "More than half the units clamped" counts units not destroyed before the turn whose own outcome was clamped: a dropped observation or a dropped outcome for a unit already gone is a correction (and a problem for the resend) but not a clamped unit.
- No two friends end overlapping beyond `OVERLAP_TOLERANCE_MM`. Each march is checked with every other unit at its proposed end; then, once status is settled (so a unit the out-of-reach rule kept alive counts, at its start), every friendly pair that still overlaps is settled: the one that moved goes back to its `T0` place (the later in unit-id order if both moved), with a `position` correction, until none overlaps. Reach and rally are judged at the end positions as marched.
- An end observation of an enemy destroyed in the turn is dropped, as the engine's own scan never sees the dead.
- A broken unit whose outcome is the projection's own rally (the projection has it `active`) needs no `rollIds`: the engine rolled for it. The other rally rules still apply.
- An order listed `not-arrived` that had in fact reached the unit is recorded as `refused` (the umpire had the unit not act on it); one not sent to that unit is dropped.
- "Cites a roll" means `rollIds` is not empty and every id is a roll made this turn. A captured unit's ruling (`status`, captured to destroyed) records the cause but is not a clamp, so it does not count toward the fallback's "more than half the units"; a destroyed or captured unit is stored with strength 0, as the engine stores the dead. A unit out of every enemy's reach also cannot be destroyed or captured in the turn (its status reverts to the projection's).
- The reach rule takes each enemy's march at forced pace, in its fastest formation, on the best road class, so it errs toward allowing a loss. The march check (`validatePlacement`) uses the unit's own pace and fatigue at `T0`; the proposal has no pace.
- Held turn (`[T0, T1]`, `T1` included): besides movement, combat, rally and pursuit, the supply tick and the minute scan do nothing (each reschedules itself), an attack intent and an umpire placement do nothing, a `timeReached` standing order does not fire (the check is moved to just past `T1`, so the order is kept), an arriving order is delivered and acknowledged but adopts no intent, and the victory deadline is left to `umpire.turn`. A rally try reschedules itself only while the unit is still broken and inside `giveUpMs`, so a later break never runs two chains. What still runs, and why: the couriers (`order.issue`, `courier.step`, `courier.lost`, `order.deliver`), since orders ride during a turn; reports, which only file news; and `umpire.judgment`, which only records a ruling. The world's `turn` flag stays set after `umpire.turn` until the next turn begins, so nothing else at the turn's end (a scan, a step) changes the applied outcome; `beginTurn` replaces it. 11.5 does not run the courier pass or issue `TurnOrder`s; those are 11.3 and 11.4.
- An order delivered in a held turn stores none of its parts, its conditional ones (`when`, `at`) included: the umpire reads the order and decides each turn what the unit makes of it, and carries what is still under way in `continuing`. Standing orders a unit held before the turn are kept, and fire under the engine (see Open).
- Just past `T1`, `umpire.turn` queues a combat check and, for each active unit `continuing` a move, the march to its destination. A held next turn ignores both (the umpire decides again); under an engine-adjudicated next turn (`rigid`, fallback) the march sets off and units still in contact fight.

**As built (11.10, #406), the client.** The client knows a game is in turn mode from the first `turnState` (sent only in such a game) and keeps that for the game, so the real-time desk is untouched. The new-game form sends `mode: 'turns'`, `turnMinutes` and `turnDeadlineHours` only for a turn game (a real-time request is as before); the lobby's `NewGame` carries dial, persona and the turn settings, and game titles show "turns of 20 min" in place of the rate. A held order's text is the player's words plus any annex, with the addressee in `TurnOrder.to` (not prefixed to the text as in real time). Once `turnState.sent` names the side, its held orders become sent orders on the client (as `sentOrders` makes them after a reload). The list of sides for "who has sent" comes from `GET /games/:id`. The desk's details are in `hq-interface.md`. Until 11.6 (#402) `GameHost` decides every turn with the engine adjudicator whatever the dial, so the form's and the turn panel's words about the umpire describe the target ahead of it: today "standard" and "free" turns are decided by the tables, as "rigid" ones are. **Play again** repeats the dial, persona and turn settings. Known gap: a reload *after* a turn game has ended gets no `turnState`, so the desk shows real-time dress; #427 seeds `turnMode` from `GET /games/:id`. Send is offered to every seat, though only a commander or subordinate may send (#428).

**Why.** The owner wants a free-Kriegsspiel game in which an umpire who reads orders as a person would decides outcomes "in a complex and loose manner" (Epic #393). #389 showed the weak point of the real-time road: small models fail at turning free text into structured intents, and some orders ("move north until you meet the enemy") cannot be expressed as intents at all. Collecting a whole turn for one call lets a strong model read every side's orders together, and the manual clock removes the clock pressure that a large call would otherwise put on a running game. D1's objection to a pure LLM umpire (inconsistent, unauditable) is answered by keeping the engine as the record and the limit: every proposal is checked and clamped against the same physical rules, every die is the server's, every turn is logged and replays with no model, and the engine's own resolution is always one step away.

**Open.**
- Victory: an umpire turn counts `takeMs` between turn ends, a `rigid` or fallback turn to the minute, so the same game can end a few minutes apart by dial when an objective changes hands mid-turn. The time limit itself is the same at every dial (the last turn ends at it).
- The departure tolerance (100 m, 5%), the clamp threshold that triggers a fallback (half the units), the turn bounds (5 to 60 minutes), the 300 s call timeout and the 15-minute turn timeout are first guesses to tune in the benchmark and the playtest (11.2, 11.12).
- Couriers ride while the units are held at their `T0` positions (the courier pass, in every turn, `rigid` included), so interception is rolled against where the enemy stood at the start of the turn, not along its true path. Moving units along the umpire's path for the courier rolls would need per-minute positions in the proposal; deferred. It is also why a `rigid` game parts from real time once a courier rides near the enemy: the pass draws the rides' dice in its own order, so the world's later rolls differ (measured under "Scripted sides in turns (#430)"). Giving courier rolls a stream of their own would make the two match beyond that (#432).
- The march check measures from the `T0` position over the whole turn. A unit whose order arrived late in the turn can therefore be placed as far as one marching all turn under its previous order; the umpire is told the arrival minute, but the engine does not check against it (it cannot tell which order the unit was obeying).
- Sight is checked at the turn's two ends only. A scout that rode out and back within the turn has seen nothing according to the engine; the umpire can show it by placing the scout at the far end, or the observation is dropped. Mid-turn observations need a path in the proposal; deferred with the courier question.
- The "no loss out of reach" rule is coarse (reach plus a turn's march); artillery at long range and pursuit by cavalry should be checked against the projection's fire events, but are not yet.
- How a side's reports are timed within the turn (all at `T1`, or each at the minute it would have reached HQ) is for 11.9; the first version delivers all at `T1`.
- Whether turn mode keeps the post-game critique's real-time facts (deliveries, misreadings) unchanged or needs turn facts is for 11.11.
- An order delivered in an umpire turn leaves no standing orders on the unit (see "As built (11.5)"), so if the game later falls back to the engine, a `when` or `at` part the umpire was still honouring is not carried on. Whether the fallback or the next engine turn should parse the turn's delivered orders into intents is for 11.4.
- Whether the turn length may vary (Verdy's umpire made turns shorter in contact) is not decided; the first version keeps `turnMinutes` fixed.
- ~~The admin clock controls (D38, #128) can `step` game time in any mode.~~ Settled in 11.3: a turn-mode game refuses `step`, `setRate`, `pause`, `resume`, `setMode` and `advanceTo` from any source, admin included (see "As built in 11.3").
- The LLM commander (#70) and deputy (D6f) do not play turn mode yet; scripted Red thinks at its interval inside an engine-resolved turn, and once as a held (umpire) turn opens (see "Scripted sides in turns (#430)").
**As built in 11.3 (#399).** Where the turn clock adds to or settles the text above:
- *Settings.* `turnDeadlineHours` is from 0.25 to 336 (two weeks). `POST /games` takes `mode`, `turnMinutes` and `turnDeadlineHours`; a real-time game's record, header and `games.settings` carry none of the three (no migration: `games.settings` is JSON). The rate is ignored and the clock is created in `manual` mode.
- *Refusals.* Every clock and vote command (`setRate`, `pause`, `resume`, `setMode`, `advanceTo`, `step`, the pause, hold and ratio votes) is refused with one fixed reason (`TURN_MODE_REFUSAL`), whether a player or the admin view sent it; a turn-mode game has no pause voting. A real-time `order` is refused too. A reopened turn-mode game comes back running, not paused: game time cannot move without a turn, so there is nothing to confirm.
- *Wire.* Three client commands: `holdTurnOrder { order: TurnOrder }` (hold, or replace the held order with the same id), `withdrawTurnOrder { orderId }` and `sendTurn`. Any seat but intelligence may hold or withdraw (the side's held orders are shared); only the commander or a subordinate may send, and the send is refused if the sender may not sign for every held order's addressee (D6a). A seat holds, replaces or withdraws only orders to units it may draft for (`mayDraft`: a living unit, and for a subordinate their own formations). An order id a side sent in an earlier turn is refused, as a reused real-time id is, so `sentOrders` ids stay unique. Hold, withdraw and send together are limited to 120 a minute per connection (`rate_limited`), since each is journaled. `turnState` also carries `held`: the receiving side's own held (or sent) orders, empty for the intelligence officer, never another side's. `TurnOrder` is `{ orderId, to, text, courier? }` on the wire (`courier` absent is the ordinary ride, as for a real-time order); the server adds `side` and `signer` when it logs the send.
- *Log.* Three more journal-only commands, so a restart loses nothing: `openTurn { turn, startMs, endMs, deadlineWallMs? }` (the deadline is fixed when the turn opens and survives a restart), `turnOrder { side, turn, order, by? }` and `withdrawTurnOrder { side, turn, orderId, by? }`. A reopened game rebuilds its open turn from them (`openTurnFromLog`) and resolves it at once if every human side had already sent. A `resolveTurn` closes its turn even when it carries an `error` (the clock still moved to `T1`). If the store refuses a `resolveTurn`, the next turn opens anyway, so the live game is not left without one.
- *The seam.* A `TurnResolver` is given the state at `T0` and the turn (`n`, bounds, cause, the sent orders, who sent) and returns `{ adjudicator, output?, calls?, fallback? }`, never a state. The actor applies `output` at `T0` with the adjudicator named (`registerTurnAdjudicator`), the same pure function replay calls on the logged output, then moves the clock to `T1` and runs the ordinary handlers there. `resolveTurn`'s record is `turn: { n, startMs, endMs, cause, orders, sent, adjudicator, output?, fallback? }`: the courier results, proposal, rolls and rulings listed under "Logged for replay" live in `output` until 11.4 to 11.7 define them, and may then become named fields. A resolver that throws is logged as a fallback and the turn is applied as `none`.
- *Until 11.4.* The default resolver was `none`: the sent orders were logged but not carried out. 11.4 registers `engine` and makes it `GameHost`'s default (see "As built in 11.4"); 11.6 registers `umpire`.
- *Scripted sides* do not send: only sides no agent plays are waited for. Until 11.4 folded their orders into the turn, a scripted agent thinks on its interval while the turn is advanced from `T0` to `T1` and its orders are issued and logged as in real time (`agent: true`), so replay is unchanged. An LLM commander plays by its script in turn mode (nothing may hold the clock), a deputy cannot be appointed, and the narrate stage does not run (each turn's reports are 11.9's).

**As built in 11.4 (#400).** The engine adjudicator (`server/src/game/engineTurn.ts`, engine side in `packages/engine/src/engineTurn.ts`):
- *Courier pass.* `courierPass(state, orders, turn, registry)` runs on a copy: the turn flag set as held (`adjudicator: 'umpire'`), any earlier forcing cleared, the new orders issued at `T0`, advanced to `T1`. It returns one `TurnCourier { orderId, side, unitId, outcome, atMs?, dueMs?, garbled?, by?, reason? }` per courier still riding at `T0` and per new order, the RNG it ended with, and per ride what the engine's resolution must reproduce. `outcome` adds `failed` to D39's four, for an order that could not set out (`reason`: unit gone, no route). Couriers are keyed by the engine order id, `<side>-<orderId>` (desk order ids are unique per side only). A new courier's loss time and garbling are read as it sets out (the pass's registry notes each `order.issue`), so a ride lost at `T0` or delivered at once (a 0 ms ride) is forced like any other. A `TurnCourier` is the ride's outcome with the units held: in the turn itself a ride `delivered` to a unit destroyed before `atMs` fails there (`order_failed`, which the projection's events show), and one `intercepted` by a unit destroyed before `atMs` is not taken and rides on.
- *Forced rides.* A courier may carry `forced: { untilMs, takenAt?, takenBy? }`, and `order.issue` a forced payload (`issueForcedOrder`) that also carries the pass's loss time and garbled intents. Through `untilMs` (the turn's end) a forced ride draws nothing: it is lost and garbled as the pass rolled it, its interception checks roll nothing, and it is taken at the pass's check by the pass's captor, unless that unit has been destroyed by then. Real-time play never sets it. The loss time of a new order is the one the pass drew at issue, so a ride lost after `T1` is still lost at the same minute.
- *The turn itself.* `engineTurnStart` sets the turn flag (`adjudicator: 'engine'`, not held), forces the riding couriers and the new orders, and sets the RNG to the pass's; `advanceTo(T1)` under the ordinary handlers then resolves the turn. The projection does that on a copy; the `engine` adjudicator does it on the real world at `T0` and the actor's advance to `T1` runs it, so the turn ends in the projection's state exactly (tested at 5, 10, 20 and 60-minute turns and several seeds). The adjudicator runs the courier pass again and refuses a turn whose couriers differ from the logged ones.
- *Orders.* Every sent order rides. The rules parser (`testParse`) is offered only the addressee (`TurnOrder.to`), so the unit is never guessed (naming another unit in the text makes the order unreadable, not redirected), and an order that names no unit ("hold", "halt and hold here") is for the addressee. An order with a condition or a time (`hasConditionOrTime`: if, unless, when, until, before, after, "once the ...", at or by a time of day such as noon, first light, 2 pm or 14:00, "in 10 minutes"; not "at once", nor a number that is not a time, as in "in 2 columns" or "by 2 roads"), one the rules refuse or ask about, an attack (not modelled), or one to a unit not of the side, is "no new order": its engine order is `textOnly` with no intents; the courier rides and may be lost or taken, and on arrival it is delivered and acknowledged and the unit carries on as before.
- *Log.* The `resolveTurn` entry's `turn.output` is `{ orders, couriers, projection }`: each order as the rules read it (intents, or `none` with the reason), the courier results, and the projection summary. Replay rebuilds the engine orders from `orders` and the turn's sent orders, with no parser and no model.
- *The projection summary* (`projectTurn(state, input, registry)`, pure): per unit not destroyed at `T0`, where it stood and stands (`describePlace` and metres), its path sampled every 5 game minutes with halts left out, the enemy units it came into contact with, men lost, the change in morale, its status (and the one it had, if changed); the turn's events in order as short lines (combat fire and morale are summed into the units); the outcome if the game ended. For Hold the Bridge a 20-minute turn with contact measures about 350 to 500 tokens (JSON length / 4), asserted under 2,000.
- *Scripted sides.* ~~Each scripted agent thinks once when a turn opens (`openTurn`), at `T0`.~~ Superseded by "Scripted sides in turns (#430)" below: they think at their interval inside a turn the engine resolves, as in real time. Their orders are issued and logged as in real time (`agent: true`), and the courier pass covers their couriers like any other riding courier.
- *Default.* `GameHost` uses `EngineTurnResolver` for every turn-mode game unless given another resolver, at every dial until 11.6 registers the umpire. A `rigid` turn files the engine's own template reports.
- *Not done here.* The umpire stage and its fallback to this resolver are 11.6. The open question of re-parsing an umpire turn's delivered orders for a later engine turn is unchanged: an engine turn reads only its own orders, and units otherwise carry on with the intent they have (an umpire turn's `continuing`).

**Scripted sides in turns (#430).** A QA game in rigid 20-minute turns ended Blue 550 men lost to Red 62, where real time with the same orders is a Blue win. The cause was the scripted side's cadence, not Blue's orders or couriers: it thought only when a turn opened, and at minute 0 it is still forming up (`FORM_UP_MS`, 10 minutes), so Red sat out the whole first turn, then advanced all at once and reacted to the fight once a turn. The 1st Battalion's "hold the bridge" was read and delivered (a hold at the bridge, delivered at minute 2); it was broken there by Red's massed attack and fell back to where it started, about 200 m short of the bridge, which is what the tester saw. Now:
- In a turn the engine resolves (`rigid`, fallback), a scripted agent thinks at its interval (5 game minutes) on the world as it stands then, exactly as in real time (`GameActor.advanceEngine`). Its orders are logged at their minute (`agent: true`), so replay needs no agent; replay already puts entries in game-time order. One due when a turn opens thinks then, on the world caught up to `T0`; in a held (umpire) turn, which moves nothing, that is its one decision of the turn, as before. An idle agent (its last decision changed nothing and no event is queued) is not woken by a turn opening, as real time would not wake it. A game reopened while a turn is open does not run that turn's opening decisions again: they are in the log. An LLM commander plays by its script in turn mode (nothing may hold the turn's clock), now inside the turn too.
- The resolver is given copies of the scripted sides (`TurnResolveContext.agents`, beside the plain-data `TurnInput`; `SideAgent.fork()`), and the projection runs them through the turn at the same minutes, so a rigid turn still ends exactly as projected and the umpire's reference shows what real time would do. Copies issue their orders with ids of their own (`<game>-t<n>-o<k>`); the live orders take theirs from the log, so only order ids differ between a projection and its turn. An agent with no `fork` is left out of the projection.
- *Parity, measured* (`server/src/game/turnParity.test.ts`; Hold the Bridge, Blue's two battalions sent to the bridge at minute 0, scripted Red, seeds 1 to 8, 42 and 1815, turns of 10, 20 and 30 minutes, 30 games): the same winner as real time in 30 of 30 (before: 11 of 30), and the same field to the metre and the man at every turn end up to minute 20 or the first turn's end, whichever is later, in 30 of 30 (before: none past the first 10-minute turn). After the first fight the dice part: at later turn ends units stood up to 1.5 km and 500 men apart where a rout ran differently, the outcome's reason differed in 2 of 30 (an objective held to the time limit against an attack broken at minute 27) and its minute by up to 23. The cause is D39's courier pass, by design: couriers riding in a turn are rolled once against held units and then draw nothing, so the world's dice are drawn in a different order from real time once a courier rides near the enemy (see Open). The test holds the first two (the quiet turn ends exactly, the winner in 12 seed and turn-length cases) and that replay needs no agent.
- *Couriers across turns* are tested both ways: an order whose courier arrives mid-turn is acted on from that minute, at the minute real time delivers it and ending where real time ends; one still riding at a 5-minute turn's end is carried by the next turn's pass and delivered at its due minute, and its unit stands still until then.

## D40: Order interpretation debug page and dry-run playground (#395, story 8.10)
**Decision.** The admin view has an **Orders** panel. History (`GET /admin/api/games/:id/orders`) joins two read-only sources: the input log (each signed order, its side, signer, the parse result the engine got and any actor-level fallback) and the debug trace, by the order's correlation id (every `llm` call it caused and a new `order` trace kind that notes each pipeline step that did not take the model's answer: `{ step: 'parse' | 'interpret', text, reason, answeredBy }`, recorded by `orderParserFor`; `text` is the order as written, so calls and notes are matched to their order when one scheduler tick carries several). Each attempt says who answered: `model`, `canned` (the test provider, configured or as the fallback), `rules` (the stub), `none` (the player was asked to restate), `agent` (a scripted side, the AI commander or a deputy wrote the order with its intents; no parse ran) or `not traced` (a restart or the ring buffer moved on). The detail (`…/orders/:key`) shows every call as the trace recorded it: system prompt and version, input, schema, provider, model, raw reply, parsed output, latency, tokens and retries, the fallback reasons, the result handed to the engine and the correlated trace chain. Nothing in the panel knows the shape of a prompt or reply, so it keeps working whatever the interpretation design becomes (#396). The canned parser used as the local-model fallback is now built per game so its calls are traced too.
**Playground.** `POST /admin/api/games/:id/orders/dry-run` runs an order through the parse (and optionally interpret) step with an edited order text, context (units, places and hidden names, prefilled from `GET …/orders-context?side=`, which reads `GameActor.orderContext`), system prompts and route (a provider id from the server's umpire config, never a URL; model, temperature, max tokens, Ollama context size). It returns the model's raw reply, the checks' problems and the result, beside the canned parser's answer and the recorded one. A dry run has its own client built from the config with no game limits and no fallback provider (a model failure is shown, not hidden behind the canned answer), never touches the actor, the input log or the trace, is limited to 6 a minute per server (429), and its tokens and cost are counted on their own (`GET /admin/api/orders/playground`). That count is held to the server-wide budget (`UMPIRE_BUDGET_USD` / `UMPIRE_BUDGET_TOKENS`): once it reaches either cap, further dry runs are refused (`429 budget_spent`) until the server restarts, so an open admin page cannot spend past what the operator set. It is the admin API's only non-GET route besides the clock controls, behind the same gating.
**Why.** Understanding why an order was understood, questioned or refused meant reading raw trace JSON and re-running scripts (#389). The owner is rethinking the order pipeline (#396) and needs to see what models actually do with real orders, and to try a prompt or model on them without disturbing a game.
**Open.** Prompt versions offered are the ones the server ships (one each); free edits are tagged `<version>+edited`. The dry run calls the parse pipeline as it is today (`LlmOrderParser`, `InterpretingParser`); a new design must register its steps there to be tried. The rate limit and the dry-run count are per process and shared by all admins; the count resets on restart, like the umpire's own budget. With no server-wide budget set, dry runs are bounded only by the rate limit. History of a game whose trace was lost shows the logged result only.

## Narration on a small local model: no scripted sides, a circuit breaker, field-note checks and templates — 2026-10-13 (#419)
**Decision.** (1) **Scripted sides.** The actor never narrates a side that one of its `agents` plays (the scripted opponent or the LLM commander wrapping it): nobody reads those dispatches, and in QA most narrate calls were for Red. A deputy's side is still narrated, since its player reads the tray. (2) **Circuit breaker** (`server/src/umpire/narrateBreaker.ts`). One per game, shared by its sides. Every narrate model call is an outcome: a reply that passes the checks is a success; a rejected reply, a timed-out or failed call is a failure; a call refused by the game's budget or rate limit is neither. When 3 of the last 5 calls failed the breaker opens until `now + max(15 game min, 3 narration windows)`, where `now` is the window's game time (game time stands there while the stage works, under the barrier). While open, no model is called: the window's reports keep their template text, and the window is still journalled as a `narrate` entry with no `calls` and the error "model narration paused: n of m failed". Once game time passes the end of the cooling-off, the breaker closes with no history. The state is plain data and is a function of the outcomes and game times only; it is logged on every `narrate` entry (`narrateBreaker`), and a reopened game resumes from the last one, so the decision needs no model and is the same in replay. The admin LLM panel gets a `fallback` row (provider "narration breaker") when it opens and for each window it skips. (3) **Field-note checks** (`checkFieldNote`, run by `checkNarration` on each dispatch, each with a reason in the trace): a note from a unit that never says "I", "we", "my" or "our" but names its own unit or commander is a third-person account and is rejected; so is a duration ("for 10 minutes": a report has an age, never a duration), a strength the report does not give ("a strong line"), fire ("under fire") on a report that is not a fight, two condition words from one scale ("steady" and "wavering"), a condition word the unit's condition (or the report's kind) does not give, a note that recites the whole condition list, one with no word for the reported event (a generous list per kind), and one over 360 characters or 4 sentences. The two QA texts are unit tests. `situation` joins `unitLost` and `courierLost` as kinds HQ writes. (4) **Templates** (`packages/engine/src/fieldNotes.ts`). The engine's report text is now a field note: five or more first-person wordings per unit kind, a closing line in the manner of the sender's public `trait` (bold, cautious, steady or plain), signed with the unit and the age ("— 1st Battalion, about 3 minutes ago."); HQ kinds have five wordings each. The wording is drawn from an `Rng` seeded with the game seed and the report id, never the game's RNG, so it is the same on every reading and in replay and no die roll moves. The commander's name is not in the text and contact notes ignore the trait, because the intelligence seat reads contacts and is not told who commands what. Only an order acknowledgement says "your orders" in lower case. Every wording passes the checks a model's note must. (5) **Prompt** `narrate-dispatches-v7` is shorter and states only rules the checks enforce, plus one to hedge a low- or medium-confidence report; the keyless Ollama route caps a narrate reply at 220 tokens (`NARRATE_MAX_TOKENS`), and a route with its own `maxTokens` keeps it. One report per call stays (#359). `npm run bench:narrate -w server` measures it against a live Ollama.
**Why.** QA of the demo with `qwen2.5:0.5b` (#419): 25 of 42 narrate calls fell back, calls took 17 to 134 s, many were for the scripted side, and the model text that did pass was third-person nonsense ("held its position ... for 10 minutes ... wavering, fresh, and well supplied") which the fact-only check let through. A failed call now costs nothing once the breaker opens, and a fallback still reads like a note.
**Open.** The thresholds (3 of 5, three windows) are first guesses. The condition-word rule is strict: "shaken" for a "wavering" unit is rejected. The event-word lists are English-only. Narrations are still not restored when a game is reopened (template text shows for earlier reports), as before.
