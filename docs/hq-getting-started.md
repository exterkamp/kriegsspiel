# HQ getting started and validation guide

Use this guide to validate the HQ interface delivered in [PR #193](https://github.com/exterkamp/kriegsspiel/pull/193). It describes the fixture/local features implemented on the HQ branch, with expected results for hands-on checks. Feedback fixes and recorded browser checks are documented in the execution log. Physical-device and full live-game acceptance remain separate gates.

The default page is a **demonstration with fixed battle data**. You can read papers, plot private beliefs, write local drafts and keep notes. The HQ cannot yet run a live battle, sign/send orders, consult staff or reveal the battlefield after a game. A running display clock does not move units; the supplied default fixture is paused.

## 1. Open the right build

Use the HQ checkout, `/Users/dominic/code/kriegsspiel-hq`, on `feat/hq-interface`. The separate map-generation checkout is not this build.

If the HQ client is already running, open its root URL **without** `new`, `game`, `lobby` or `token` query parameters. Otherwise, once your `devrun` setup is ready:

```sh
cd /Users/dominic/code/kriegsspiel-hq
nvm use
npm ci
devrun up --name hq-web --port-env PORT -- npm run dev -w client
devrun url hq-web
```

Open the URL returned by the launcher. Use the separate `hq-web` name so this session does not take over another client's launcher entry. No game server is needed for the HQ demonstration. This guide does not start one for you.

The page should say **Headquarters** and **Fixture / demo — no live game services**. After loading, the source should say `ready`. A previously used browser may restore a saved desk view; choose **Map table** to begin.

Local records belong to this browser profile and origin, as well as the demo game/side/player. Keep the same URL origin and port for reload checks. Use a fresh browser profile for a clean run; a different port also creates separate browser storage. Use one writing tab for normal validation.

### Expected starting data in a clean browser

- Public schematic map: 4,000 metres east–west by 3,000 metres north–south.
- Four own formations: **1st Battalion**, **2nd Battalion**, **Cavalry Squadron**, **Light Company**; two last-known enemy contacts.
- Two papers: `demo-staff-1` from **Headquarters staff**, and `demo-scout-1` from **Scouting patrol**. Staff is the newer arrival. Only the scout paper supplies a location: **2,150 m east, 350 m south**.
- Paused fixture clock at `01:00:00` (one elapsed game hour), supplied rate **1**, realtime mode and a clear barrier. The paused time should hold while you wait.
- No personal marks, an empty local order draft and an empty personal notebook. Read/file state is new until you open a paper.

Game timestamps consistently show elapsed `HH:MM:SS`; hours can exceed 24. Invalid or unavailable times stay explicit. The fixture does not supply a calendar date. JSON and journal text exports retain their original precision.

No new papers or unit movement are generated by waiting on this page. The other category piles can legitimately be empty.

## 3. A 15-minute first pass

Use these checks in order. Leave Save/reload checks until the specified step so you can distinguish local edits from persisted data.

### A. Inspect and navigate the table

1. Open **Map table**. Try **Top-down** and **Oblique**.
2. Over the canvas, use left-drag to orbit, the wheel to zoom and right-drag to pan. These are the current table controls; verify their physical behavior in your browser.
3. Select **1st Battalion** in **Own-piece selection**, then choose **Focus selected piece**. Clicking an own piece on the canvas is another selection path.
4. Change the camera, visit **In-tray**, then return to **Map table**.

**Expected:** selection is reflected under **Shared selection**; focus moves the camera to the supplied formation position. The desk round trip retains the camera and pieces. A deliberate focus or camera snap changes that camera. Enemy contacts have stale/uncertain styling and are not own-unit recipients. Selecting or orbiting never moves units or sends orders.

### B. Read and file a paper

1. Open **In-tray**. Confirm staff precedes scout under **All papers**, **active**.
2. Choose **scouts**, then **Open demo-scout-1 — Scouting patrol**. Read the metadata and body.
3. Choose **File**. Inspect the **filed** pile and reopen the scout paper.
4. Choose **Discard**, inspect **discarded**, then choose **Restore to active**.
5. Clear filters and search for `north wood`; the scout should match.

**Expected:** opening hands focus to the reader and marks the paper read when storage is writable. Filing/discarding marks it handled/read and changes its pile. Reopening a filed or discarded paper keeps that disposition; restoring makes it active/read. The status reports successful local saving. Reading and filing create **no map mark**. Observed time is unknown, and attachments/sketches are explicitly unavailable.

### C. Plot a report at a chosen coordinate

1. With the scout open, choose **Choose report coordinates**.
2. Wait for **Map table** and **Place captured report pin**. Set **East** to `2400`, **South** to `600`, and **Pin label** to `Scout belief A`.
3. Choose **Create local report pin**.
4. In **Personal map marks**, find the new pin and choose **Edit**.

**Expected:** exactly one pin is created at `(2400, 600)`, with **Created locally; unsaved.** Its frozen source still names `demo-scout-1`, preserves the report text and records the original reported location `(2150, 350)`. Editing geometry changes your chosen belief, rather than rewriting the source report.

Choose **Save local marks** before proceeding. It should clear the unsaved mark status. Source papers and saved marks are separate records.

### D. Write a draft

1. Open **Orders**. Choose **1st Battalion** as **Recipient — own unit**.
2. Enter: `Hold near the bridge. Report any enemy crossing.`
3. Confirm the recipient and prose appear in **Draft preview**.
4. Type one final character, immediately visit another desk, then reopen **Orders**.

**Expected:** the final character and recipient return because draft edits autosave immediately. **Sign and send** stays disabled. Commander, courier choices/risk, delivery estimate/status and annexes remain unavailable. Writing a draft does not move a unit or create a sent-order journal entry.

### E. Save a note and reload

1. Open **Journal**. Write `Validation note: scout plotted manually.` in **Personal notes**, then choose **Save personal notes**.
2. Choose **Prepare text export**, select/copy the export and confirm your note and the matching papers are present. Filters affect this export.
3. Reload the browser. Revisit **Map table**, **In-tray**, **Orders** and **Journal**.

**Expected:** the saved pin, scout read/disposition state, draft recipient/text and saved notebook survive on the same origin/profile. Map marks and notebook edits that were never saved are not promised to survive a full reload. The paused clock remains held.

## 4. Complete feature checks

### Report placement: all three entry points

- **Supplied location:** open the scout, choose **Plot paper**. One new private pin appears at `(2150, 350)` without asking for chosen coordinates. Return to the table if needed and save it explicitly. Choosing this action again intentionally creates another pin; reading alone does not.
- **Pointer:** press and hold **Drag report to map** on the scout. Keep holding through the navigation, move over the exposed map, inspect the preview, then release. Expect one pin at the final map coordinate and released camera controls. The chosen point and original reported point remain distinct. A subsequent click must not create a duplicate.
- **Keyboard:** use Tab/Enter on **Choose report coordinates**, fill the labelled fields and submit. Expect focus in the East field once ready and the same source preservation as pointer placement. The drag button also opens coordinate placement when activated from the keyboard.

Repeat pointer placement with a mouse and, separately, a physical touch/pen device if available. Browser emulation alone is not physical-device evidence.

Check cancellation and invalid input:

1. Start placement and choose **Cancel placement**, or press Escape. No pin should be added, and camera gestures should work again.
2. Start a drag and release before the table transition finishes. No pin should be created.
3. Release over a panel or outside the map. No pin should be committed there; use the retained coordinate form or cancel.
4. Enter East `4001`, South `-1`, or nonnumeric text. Creation should fail visibly without adding a pin. Correct to a point inside `0–4000` east and `0–3000` south and try again.
5. Start placement, then navigate to another desk or switch away from the browser window. Placement should cancel without creating a mark. Camera/mark controls should recover.

If a rare error says **Creation outcome unknown**, inspect the local mark list before starting a new request. The controller prevents an automatic retry of that ambiguous request.

The staff paper has no supplied location: **Plot paper** should be disabled. You can still choose its coordinates explicitly; its captured reported location must remain unknown. There is no automatic staff plotting or accuracy policy.

### Create and edit all five mark shapes

On **Map table**, use **Create personal mark**. Coordinates are metres from the north-west corner: east increases right and south increases down. There is no tile snapping. Choose a label, shape and these example values:

| Shape | Example inputs | Expected rendering |
| --- | --- | --- |
| Pin | East `1000`, South `1000` | Pin at that location |
| Polyline | Points below | Connected pencil line |
| Arrow | Points below | Connected path with an arrowhead at the end |
| Ring | East `2000`, South `1500`, Radius `250` | Range ring centered there |
| Symbol | East `3000`, South `2200`; try Cross, Dot and Flag | Selected symbol at that location |

For Polyline and Arrow, enter one east, south pair per line:

```text
1000, 1000
1500, 1200
2000, 1000
```

Choose **Add local mark** for each. A source paper is optional; a manual mark has no report provenance. To change a mark, choose **Edit**, adjust its label/geometry and choose **Apply mark edit**. **Start a new mark** leaves edit mode. **Focus on map** centers the camera; **Delete** removes the mark from the local list. Save is separate for creation, edits and deletion.

**Validate:** all shapes appear, the arrow points toward its last point, focus works, decimal coordinates are retained, and an edited paper-backed mark keeps its frozen source. A ring centered at `(50, 50)` with radius `250` may cross the map edge; decorative geometry should be clipped, while its stored radius/center remain unchanged. Coordinates outside bounds, a nonpositive radius or fewer than two line points should be rejected. The limit is 200 marks per local list.

Choose **Export marks as JSON** and copy the displayed textarea. It includes the accepted local list and unsaved list changes, but excludes form edits that have not been submitted. Re-export after changes; the displayed export is a snapshot. No import button is implemented.

### Save versus autosave

| Data | When it persists | Reload/recovery action |
| --- | --- | --- |
| Personal marks | **Save local marks** | **Reload local marks**; confirm discarding dirty list/form edits |
| Personal notebook | **Save personal notes** | **Reload local notes (discard edits)** immediately discards the current notebook edits |
| Order draft | Every text/recipient change | **Retry save**, **Export draft**, **Reload saved draft**; confirm dirty discard |
| Paper read/file/discard state | Each state change | **Retry save**, **Export JSON**, **Reload saved state**; confirm dirty discard |
| Desk preferences | Navigation/selection/settings actions | Restored on the next page load when saving succeeded |

For a safe discard check, first save a mark, then edit it and apply the edit without saving. Choose **Reload local marks** after acknowledging the discard checkbox. Expect the previously saved version. Repeat with a saved draft only after exporting anything you want to keep.

For notebook discard, save a note, append a test sentence without saving, then choose **Reload local notes (discard edits)**. Expect the saved note immediately; this button has no separate confirmation checkbox.

### Roster and journal

- **Roster:** confirm four own formations. Snapshot times use the shared elapsed `HH:MM:SS` format and readable ages; identical provenance appears once in the table caption, while fields from different times keep their own annotation. **1st Battalion** has snapshot strength `600`, morale `80%`, supply `100%` and position `(1850, 2450)`. Commander is **Unknown**. Choose its **Focus on map table** action and expect table navigation to that supplied position. On a narrow window, keyboard-focus the labelled roster scroll region and check all columns remain readable.
- **Journal:** papers are chronological by received game time, so the scout precedes staff here, reversing the newest-first in-tray order. Search/filter should narrow the papers. **Personal notes** are separate from dated paper entries; the application invents no note timestamp. Preparing export uses the current search/filter and can include matching unsaved notes. It is a select-and-copy textarea, not an automatic file download.
- Filing/discarding a paper changes in-tray disposition; it does not remove a supplied paper from the journal or delete a mark made from it.

### Keyboard, display settings and layout

1. Visit every destination with Tab/Enter and check the destination heading receives focus. Headings remain plain semantic destinations; the next Tab reaches an action, with a visible focus indicator. Open a paper and verify the reader receives focus. Edit a mark and verify focus reaches its label; delete a mark and check focus stays in the mark list or its heading.
2. Type `miorjctp` in the draft, notebook and search fields. It should remain text and should not navigate.
3. Open **Settings** in the header. Check that focus enters its labelled dialog. Preference load/save status appears here. **Escape** or **Close settings** closes it and returns focus to Settings; there is no bottom preference bar. Preference failures and HQ errors remain visible in the header when Settings is closed. Disable **Enable letter shortcuts (this session)**. Letter navigation should stop; Tab/Enter and explicit return buttons should still work.
4. In **Settings**, enable **High contrast** and **Reduce motion**. Navigate between table and desks. Look for visible focus/current-route indication, readable text and reduced transitions. System reduced-motion preference also applies.
5. Reload after changing contrast/motion. Those settings should persist; the letter-shortcut toggle returns to its session default.
6. Resize to a narrow window and try browser zoom. Check long text, controls, placement form and scrollable roster do not obscure required actions. On touch, check page scrolling outside the drag handle and camera recovery after cancellation.

Capture actual screenshots and device/browser details for these checks. Automated headless axe checks currently report no violations with the unsupported jsdom color-contrast rule disabled; they do not establish browser contrast, layout or screen-reader usability.

### Storage failure and conflict checks (optional extended validation)

Use a disposable browser profile after exporting any edits you want to keep.

- If browser storage is denied/full, save failures should be visible. Marks/drafts retain recoverable current edits, and exports remain usable. The in-tray still lets you read valid papers even when durable read-state changes are unavailable. Restore storage and use the relevant retry action where available.
- To check conflicts, open the same demo in two tabs, load the same saved marks in both, save a change in tab A, then change/save in tab B. Expect a conflict rather than overwriting A. Export B's edits before an explicit reload. These are observed-conflict protections, not an atomic multiwriter editor; two-tab use is only this test.
- Corrupt or unsupported stored documents should be preserved with visible errors. Do not expect an automatic reset or silent migration. Automated tests cover these cases; manual corruption is not needed for the first pass.

## 5. Unavailable services and separate live routes

Open **Conference**, **Terrain studies** and **Replay**. They should say the service is unavailable. Expect no staff response, terrain sketch or hidden-truth reveal. **Orders** must keep **Sign and send** disabled. There is no HQ clock-rate/pause control, shared annotation service, courier workflow, order-status timeline or replay scrubber in this delivery.

The existing live client remains reachable separately with `/?new=1&side=blue&rate=12` to create a game, or `/?game=<id>` to join one. `/?lobby=1` opens the accepted new-game form and game list; hot-seat games choose a side with `&side=blue` or `&side=red`. Sign in with the emailed magic link first; session cookies authenticate the WebSocket and game seat. Those URLs need the game server and open the accepted live client, desk, in-tray and shared marks; they do not connect this HQ desk to a live game. The accepted `/admin/` entry is also separate. Treat live-client/admin regression checks separately from HQ fixture acceptance.

Still required before full Epic 4 acceptance: accepted live projection/clock/provenance and commands, server/shared marks, signing/couriers/delivery, conference service, authorized arbitrary-time replay, generated-map integration, physical pointer/touch evidence, browser visuals/contrast and a recorded 60-piece performance run. The two-paper page cannot validate the 200-dispatch browser benchmark; that scenario currently has headless test evidence only.
