## Required contract corrections and settled routine choices

### C1 — Freeze separate public, resolved and compatibility identities

The proposal must define exact digest inputs and wire evolution rather than relying on the word “revision.” Current `describeDefaultBattlefield` sets pairing `revision === scenarioRevision`, hashes the loaded world, and derives IDs from `world.scenarioId`. The 6081 client requires that equality, `source === 'scenario-default'` and `${pairing.scenarioId}:default`. Simply extending that producer with a new revision formula or public/resolved ID split would break the current default preview.

Settle the identities as follows:

- Public scenario ID is `hold-the-bridge` for both choices; resolved engine IDs identify immutable authored initial worlds. Keep the historical default engine ID working for legacy replay. Do not add the alternative as another public scenario row or pass its internal ID as an arbitrary public scenario selection.
- Preserve the existing `ScenarioInfo.battlefield` legacy default wire projection and existing logical default map/pairing IDs. Introduce an explicitly versioned modern `battlefields` entry schema/collection, including an unambiguous default designation. Modern consumers prefer it; old consumers continue receiving the original default projection. A new pairing revision in that collection is not interchangeable with a legacy `scenarioRevision`.
- Modern `scenarioRevision` identifies the complete normalized pre-runtime initial world. A separate domain/versioned pairing digest binds public scenario ID, resolved scenario ID, scenario revision, full terrain identity, assembly version and logical map/pairing IDs. Display names, ownership labels and cosmetic preview metadata do not silently change playable identity. Use full digests with recursive key sorting and preserved array order, as in R1.
- Freeze a named native assembly version and its terrain semantics, including implicit open ground. Current map hashes cover explicit map data, not executable engine code or `OPEN_GROUND` itself. Changed assembly/default-ground semantics require a version change; digest verification does not promise replay across arbitrary engine revisions.
- Keep old scenario-only creation resolving the default. If legacy default pairing revisions are ever accepted explicitly, recognize only a documented immutable default alias; do not weaken modern binding checks globally.
- Modern schema validation must compare the descriptor with the **parent public scenario ID**, not a display name or only internally coherent IDs. This closes R2 N1 for the expanded interface. Define foreign-scenario, stale revision, unknown pairing, invalid terrain and unavailable pairing as distinct failure categories; all remain failures before game effects. A modern list never certifies a client-supplied asset.

This correction belongs before registry/schema or picker work. The current default-only checker must remain scoped to legacy descriptors until a modern consumer replaces it deliberately.

### C2 — Choose and specify a private initial-world pin now

The proposed “either immutable definitions or private snapshot” is an unresolved implementation dependency. **Choose a private, versioned, normalized initial-world pin for new games**, shared by lobby creation/start and replay, with immutable retained definitions used for authored registration and explicit legacy resolution. This fits current snapshot persistence and avoids future catalog availability becoming a replay dependency.

The pin contains the complete validated **pre-runtime initial `GameState` at time zero**, the public/resolved IDs, map/pairing identity and revision, assembly/pin schema versions, and content digests. It precedes `startingState`, visibility scans, scheduled events, dial application and game RNG advancement. Existing per-game settings, seed and clock choices remain separately pinned and are applied identically in host creation and replay. The world may be stored once by immutable digest with lobby/header references; it need not be duplicated everywhere. Retain it as long as the game/log needs it, independently of library metadata/deletion.

Specify an actual decoder/validator for this pin. `loadScenario` accepts raw scenario input and **cannot validate a serialized `GameState` directly**: its geometry, unit and victory input formats differ. Registration must first obtain a world through real `loadScenario`; durable readback needs strict pin/schema/semantic validation and digest checks, not a TypeScript cast or a `time === 0` check. Validation must cover all initial fields, finite values, placements, HQs, crossings/objective and consistency with the declared identity. No invented normalization may silently change bytes or defaults on reopening.

Concrete caller requirements:

- `LobbyGame.scenario` remains the public scenario ID for existing UI/list behavior. Add an explicit private pin reference/contract version. Replace scenario-only resolution in `humanSides`, staff/unit-role checks and `startGame` with the pinned initial world. Identical current armies are not justification for leaving those seams divergent.
- `InputLogHeader.scenarioId` continues to equal the **resolved** `world.scenarioId`, as required by `replayLog`; add separate public scenario/pairing/pin fields rather than repurposing that equality. `GameHost.doCreate` must receive/persist the pin. Update Memory, JSONL and SQLite header implementations/migrations, not only the interface.
- Full replay CLI, admin replay/standing backfill, critique and postgame window must load by verified pin. Current CLI/admin loaders use the header's scenario ID and mutable registry. Snapshot reopening already restores the saved engine world; it must verify immutable scenario/map/pin agreement and retain identical settings/replay behavior, not replace it with today's registry world.
- Lobby, header and recovered snapshot contradictions or missing/corrupt **new-format** pins fail visibly. Missing metadata must not trigger default substitution. Explicitly identify legacy historical bridge records and keep their old replay path; `recordOf`'s current blanket historical bridge synthesis must never disguise a failed new-format assembly.
- Public game/room/list DTOs are projections from the pinned public descriptor, never spreads of the private record/header/world. Preserve current guest privacy, seat/host authorization and postgame master-state gate. Catalog renames/unavailability cannot change a pinned game's terrain or block normal public descriptor loading.

Chunk 2 must freeze and test the pin format/decoder and exact resolver output. Durable API/storage integration is chunk 3 work; the format cannot remain an “either/or” when its dependents start.

### C3 — Define a lossless public render adapter and fail-closed readiness

The proposal names the right consumers but must account for actual representation loss:

- `BaseFeature` has no layer; `mapTexture.paintOrder` discards supplied ordering semantics by sorting on a fixed **kind** table and insertion-order ties. Flat board paints the supplied array directly. An independent pure-function probe confirmed equal-layer IDs `a,z` remain painted `a,z`, while the engine requires smaller ID `a` on top. Merely sorting the public DTO before conversion will not fix arbitrary layer overrides if Three.js re-sorts it again.
- Settle one public-only adapter preserving extent, feature IDs/kinds, **explicit layer and ID-tie precedence**, shapes, full widths and radii in metres. Either preserve the layer in the render model and sort consistently in both renderers, or establish one final ordered render representation that downstream painters do not re-sort. No renderer may infer gameplay attributes or import master state.
- Replace live `fixtureMap` uses in `TableHostComponent` (including window frames), `FlatBoardComponent` (map, font/size, scene, summary and picker), and `MarksService` tolerance. The Three.js scene already rebuilds on serialized map changes, but its painter semantics still need correction. Postgame frames contain no map; use the same verified game pin's public descriptor with every frame, under the existing postgame access rules.
- `GameService.connect` currently starts WebSocket before `fetchGame` finishes, swallows HTTP failure and only extracts sides/settings. Require a verified pinned map before enabling scene/picking/marks, with explicit loading/error/retry state. Guard async map publication by connection/lifetime identity, not only a potentially reused game ID. A missing/invalid new-game descriptor cannot mean fixture terrain. A legacy fallback is allowed only when explicitly established by server legacy resolution.
- Old clients can still create default games, but can also follow invites to alternative games and currently ignore added metadata. Define modern render-capability/version negotiation and rejection for unsupported clients **before alternative seating/live connection**, including direct WebSocket paths. An old client must not play an alternative while silently drawing woods from its fixture. Exact transport syntax can be set in the chunk 3 API packet; the fail-closed compatibility behavior is a contract requirement now.

Pure adapter/render-model tests may be a bounded writer packet after schema acceptance. Alternative live availability stays disabled until create/pin/reopen/replay/render agreement passes end to end. A descriptor marked approved in an internal registry is not by itself a production playable-list readiness signal. Chunk 2 can register/test the alternative internally without exposing a clickable live option ahead of chunk 3.

### C4 — Replace “bounded” with initial numeric budgets and strict boundaries

For this small native catalog, adopt these conservative **initial contract limits**; changing them later is a reviewed schema/resource decision, not a generator policy:

| Boundary | Initial limit |
| --- | --- |
| ID / display text | IDs at most 128 characters; display names at most 160; full versioned digest fields at most 160. |
| Map extent / coordinates | Each dimension 1–20,000 m; coordinates finite, in extent, representable in integer millimetres; widths/radii positive, at most the larger extent. |
| Features / vertices | At most 128 features/map, unique IDs; at most 1024 points/geometry and 4096 total point entries/map; shape-specific minima; explicit bounded integer layer. |
| Catalog / wire size | At most 16 pairings/public scenario; descriptor at most 64 KiB and whole `/scenarios` response at most 256 KiB UTF-8. Both individual and aggregate budgets apply. |
| Private native pin | At most 1 MiB serialized; two sides and at most 128 initial units, with bounded strings/collections and the same terrain budgets. No unbounded nested unknown fields. |
| Create request | At most 16 KiB; strict existing options plus bounded pairing selection and a UUID operation key. |

Define an explicit finite integer layer range in the amended schema; using −1024 through 1024 is sufficient for this native release. Validate resource budgets before expensive processing and enforce them in registry publication, wire schemas and private readback. Cache validated immutable authored descriptors/pins; do not repeatedly load/hash large world data per `/scenarios` call or create membership check. Current `scenarioList()` does exactly that for one tiny map.

One shared public schema at transport boundaries is appropriate, but it is **not** a replacement for server assembly approval, private pin validation or registry membership. Preserve the explicit geography allowlist and reject unsupported shapes/kinds rather than dropping data. Shared limits and aggregate-size rejection tests are prerequisites for modern schema release. Larger owned libraries need additional byte/depth/time/quota limits; these native defaults do not establish that storage service's readiness.

### C5 — Specify idempotent creation and recovery before chunk 3

Settle optional modern `pairing: { pairingId, revision }` as an atomic selection object and optional `requestId: UUID` on the existing create request. The new UI always sends a key for both default and alternative submissions; legacy scenario-only/no-key clients keep current default behavior and receive no new deduplication promise. Reject half selections and unsupported properties strictly.

Define a durable owner-scoped receipt keyed by `(ownerId, requestId)`, with a versioned request fingerprint, effective normalized choices, resolved pin, allocated game ID and recoverable creation state/result. Compare retries against the accepted intent before consulting a possibly changed latest default/catalog or reapplying game limits. Fingerprint scenario/pairing, side, session/lobby mode, effective timing, rules/persona, hierarchy and pause options; object key order is irrelevant. A reused key with changed intent is 409 conflict. Failure before acceptance has no game effects; failure after durable acceptance must reconcile/resume the same game, not allocate a new one. Current sequential claim-seat → put-lobby → host/header → actor/start operations do not provide this guarantee.

Choose a creation transaction/unit-of-work boundary spanning receipt, pin, lobby and seat reservation in the durable SQLite backend, then make actor activation recoverable/idempotent outside that transaction. Current auth/lobby/game stores open **separate SQLite connections** to one path; wrapping calls on just one handle cannot atomically commit all of them. Memory implementations need equivalent concurrent-request serialization for tests, without a false process-restart guarantee. Specify receipt retention at least as long as its game and no silent key reuse after tombstoning/deletion. Provide an authenticated owner-only reconciliation operation/result state so timeout handling does not create duplicates.

Guest adoption must transfer receipt ownership and indexes as well as game/seat ownership, with a collision rule and crash-safe update; another account's identical UUID never reveals a receipt. Existing `adoptGuest` and the later lobby-reassignment callback are not one cross-store transaction. Test concurrent identical/conflicting requests, disconnect/retry, crash between allocation/seat/lobby/header/activation, restart, full game limits during retry, start failure and guest adoption. Do not call all 5xx/timeouts definite no-create failures or rotate the key until reconciliation permits a genuinely new request.

This state machine belongs to chunk 3 implementation, but its wire/storage/recovery contract must be agreed before dependent create UI or persistence work. It does not require an owned canonical-map library for this curated native alternative.
