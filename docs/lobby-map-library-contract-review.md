## Blocking findings

### B1 — The frozen list port cannot represent a retained over-quota library

Document line9 permits adoption above quota without deleting/truncating assets, but says list summaries are limited to20 guest/100 account. Port line12 returns one array without cursor, continuation or partial-result indication. An account with100 small maps adopting20 guest maps legally has120. Returning100 silently hides retained entries; returning120 contradicts the stated response bound. Repeated adoption makes an aggregate-all implementation unbounded even though new saves are blocked.

**Bounded correction:** distinguish save quotas from list page limits. Use stable keyset pagination,20 summaries per page and a32KiB UTF-8 response ceiling; expose an opaque bounded continuation in the port instead of silently aggregating every page. Bind cursors to authenticated owner/source, validate their size, and use deterministic immutable ordering. All adopted assets must remain reachable by pages and owner-scoped reference. Included geography can use the same bounded interface. The updated port and contract need a new hash-bound review before dependent presentation is frozen. This changes no retention or account-tier policy.

### B2 — Worker limits do not yet bound ingress/readback memory

Document lines9–11 bound each body to64MiB and active validation workers to2 globally/1 per owner. They do not say when admission happens. A route can satisfy those statements while buffering arbitrarily many64MiB requests before rejecting worker contention. The512MiB V8 old-generation ceiling is not a process/external-buffer memory ceiling. Reads that retrieve large SQLite values before acquiring validation capacity have the same gap.

**Bounded correction:** authenticate and reserve global2/owner1 capacity before accumulating a large body or retrieving a large stored asset. Hold the reservation through body receipt, validation, any readback and resource retirement; reject excess work429 without buffering it or queuing it. Bound body receipt to30s as well as the stated30s worker wait, reject unsupported content encodings, and cap streamed bytes independently of Content-Length. A disconnect/timeout must terminate and await worker exit before releasing its slot. The same pool must cover read/reconciliation certification, not only PUT. Check stored byte length before materializing an oversized SQLite value; bound client streaming before decoding. Tiny owner-only receipt lookups need not allocate a large-body slot until bytes/certification are needed. Keep Fastify's ordinary small-body limits on other routes.

These are admission/lifecycle requirements, not a demand for process-per-upload isolation or a claim that a V8 limit caps RSS. No benchmarking or actual service behavior was measured here.

## Routine agreements resolved for implementation

The following are required interpretations of the proposed semantics; they need no owner question:

- **Commit after asynchronous validation:** capture immutable intent, then recheck the live authenticated owner, ownership/key ambiguity, tombstone, exact prior intent and current quotas inside the final synchronous SQLite unit of work. Validation must not hold a transaction open. If adoption/deletion/expiry removed the old principal during the worker run, the old request must not recreate ownership or resurrect bytes. A new authenticated request may retry/reconcile under the adopted owner. Recheck uniqueness and quotas at commit so concurrent successes cannot exceed limits or create a third asset.
- **Exact identity/certification:** call `assetIdentity(asset, 'asset')` explicitly; its existing default is geometry identity. Retain all existing HARD_LIMITS, including the6,000,000-node cap, and current complete validation's100,000,000-work ceiling. Certification cache entries must also be scoped to the current validator/generator/fork identity or a fresh process epoch; immutable bytes alone do not make an old certificate current. No cached successful parse substitutes for complete certification. Unsupported old geography fails visibly without rewriting/deleting its retained bytes.
- **Retry and deletion:** an existing matching accepted operation is resolved before current quota/latest certification rejection; same key never creates another asset. A tombstoned operation never becomes a fresh save or reports an accessible live asset. Keep tombstones inaccessible after owner deletion and retain them while the corresponding operation identity is reserved. Post-commit readback/acknowledgment failure retains the accepted record and is ambiguous to the caller; the pre-commit “worker failure creates no rows” rule must not erase an already committed acceptance. Abort does not prove server cancellation. Preserve the exact request UUID/name/bytes/hash on ambiguous failures. Repeating PUT is sufficient with the current port; a separate GET helper is not required for the portable child if retry semantics remain explicit.
- **Boundary/privacy:** use a strict allowlist for summary fields, finite positive dimensions checked against the certified asset, lower-case64-hex identity, bounded references and nonnegative safe-integer timestamps. Display names are at most160 UTF-16 code units and nonblank; compare the exact accepted metadata on retry and render names as text. Define bounded URI-encoded metadata headers and reject malformed encodings/unknown fields. Owned asset/request lookups, including reconciliation, are authenticated and owner-scoped; foreign resources remain404. No raw bytes, original-owner identifiers or private failure payloads enter lists, logs or capability responses. Preserve existing cookie/origin policy; the raw PUT/custom headers are not an excuse to enable permissive credentialed CORS.
- **Port adapter:** `included`/`owned` is a new library reference namespace, distinct from existing development `premade`/`generated` references. Use an explicit adapter to BoardPreparation; do not cast or route the new port to `/__local/maps`. Preserve the summary's separate display name and full asset identity while independently checking returned canonical bytes. All geography stays `needs-scenario`; save never selects a pairing or starts a game.
- **Capability:** an actual successfully initialized durable shared database, ownership participants and reviewed transport are required; the mere presence of `DB_PATH` is insufficient. Task-only preview storage remains isolated. Portable presentation may be developed after contract acceptance, but public Add/save capability remains false until storage/transport/integration gates pass. Native default/curated play is independent of library availability; current validation/library outages must not replace a pinned game's terrain.
