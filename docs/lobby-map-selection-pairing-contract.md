# Lobby map pairing: chunk2 candidate contract

Coordinator candidate, 14 October 2026. This is a proposed implementation interface, not an accepted readiness claim. Independent review precedes dependent UI work. Chunk1 remains separately reviewed at its recorded commit.

## First curated alternative

Ship one explicit engine-native authored variant, **Open bridge approaches**, alongside the unchanged bridge default. It retains exactly Hold the Bridge's authored sides, seed, HQs, armies, formations, positions, objective, victory conditions, river, road and bridge. Its explicitly authored terrain omits the two woods. It is not a conversion of arbitrary generated geography and makes no historical or multiplayer balance claim. Its resolved engine scenario ID is versioned (`hold-the-bridge-open-v1`); the public scenario choice remains Hold the Bridge. Load/placement, crossing/objective, headless completion, deterministic replay and per-side privacy tests are acceptance gates. Do not advertise it as playable until those pass and chunk3 creates/renders the same assembly.

No canonical MapAsset conversion is included in this native pairing. Canonical assets, including the three included maps and newly saved maps, remain **Needs a scenario**. In particular no hole, ground, height, crossing or unsupported terrain layer is flattened into an engine approximation. A later canonical converter needs its own accepted semantic contract.

## Frozen boundaries proposed for chunks2–3

- Keep `ScenarioInfo.battlefield` as the default descriptor for older clients. Add an optional `battlefields` collection for the scenario's approved native pairings. Existing pairing IDs, terrain identities and default behavior remain stable.
- Add explicit `resolvedScenarioId` and `assemblyVersion` to the approved pairing DTO. `scenarioId` names the user's scenario choice; `resolvedScenarioId` names the exact initial engine world used by creation/replay. Revision binds the complete initial world plus assembly version and public scenario ID. Map identity binds every terrain gameplay attribute, not only preview geometry.
- One registry resolves `(scenarioId, pairingId, revision)` to a detached validated initial world and its public descriptor. A missing pairing selects that scenario's default for old clients. Unknown, stale, foreign-scenario and unpaired geography fail before seat/lobby/log/actor effects. Client canonical payloads are never accepted as a playable assembly.
- Runtime validation must bound public descriptor sizes/strings/coordinates and enforce geometry shape/kind, extent and map/pairing identity agreement. Use one shared schema at transport boundaries rather than several permissive client validators. Preview remains an explicit allowlist; never expose private placements or the private assembly snapshot.
- New create requests carry optional `{pairingId, revision}` plus a request UUID. Server persistence binds the accepted request to the authenticated owner, normalized choices and resulting game. Same-key identical retries return the same game; conflicting choices return conflict. Client retains the key across ambiguous network failures and reconciles before offering another create. Adoption follows existing guest policy. Definite rejection leaves the draft editable. The implementation must establish transaction/recovery behavior before claiming idempotency.
- Lobby records and private replay headers pin the exact approved assembly. Either retain immutable versioned definitions with revision verification on every resolution or persist a validated private initial-scenario snapshot; choose and test one before releasing chunk3. Catalog availability/name changes cannot substitute terrain or prevent an existing pinned game reopening. A corrupt/unresolvable pin fails visibly rather than using the latest/default world.
- Authenticated game information returns the pinned public battlefield descriptor. `GameService`, Three.js table, flat board, picking/marks and postgame window derive their base map from it. Preserve metre coordinates, layer/tie order and width/radius. No alternate map can ship while any live rendering path still substitutes fixtureMap. Existing old-game fallback remains only for legacy records known to use the historical bridge map.
- Room/list metadata names the pinned scenario/map. No map edits inside an existing room; ready/invite/host/auth/guest/turn behavior is preserved.

## Ownership and packets

Coordinator owns protocol/schema, scenario/pairing registry, API/create/persistence/replay, GameService, composition/shared entrypoints, Git and managed processes. Writer is not released to this contract yet. After independent acceptance, release isolated public map adapter/rendering files and their tests as one bounded writer packet; reserve all shared services and shell integration. Each packet freezes exact source IDs before review. Chunk2 stays a separate prerequisite commit/PR from chunk3's selectable live behavior.

## Subsequent owned-library boundary

Authenticated owner-private list/read/save stores exact certified canonical bytes separately from display name, with server resource/schema/certification limits, bounded owner quota, stable UUID operation key and identity readback. Account/guest adoption and expiry use the existing policy and need atomic durable ownership updates. The development catalog is never a production fallback. Renaming metadata does not recertify or alter asset bytes. Included canonical geography may be browsed but is unpaired. Add/generation is released only after this storage contract is accepted; chunk6 automatic army/objective placement remains excluded.

## Accepted-direction amendments for R4 follow-up

These concrete choices replace the earlier alternatives/unspecified limits. They are candidate amendments until independently accepted at their resulting document hash.

### Identity and compatible wire evolution

Retain the legacy `battlefield` projection byte-for-byte, including its existing default IDs and `revision === scenarioRevision`. The modern collection is `battlefields: { schemaVersion: 1, scenarioId, entries: [...] }`; each entry is `{ map, pairing, isDefault }`, with exactly one default and at most16 entries. Map IDs and pairing IDs are `hold-the-bridge:default` and `hold-the-bridge:open-v1`. Modern pairing adds required `resolvedScenarioId` and `assemblyVersion: 'engine-native-v1'`; public `scenarioId` remains `hold-the-bridge` for both. Alternative map source is `included`. Modern consumers validate against the parent scenario ID. The legacy checker remains limited to the unchanged legacy field until deliberately replaced.

`scenarioRevision` remains the existing domain-prefixed SHA-256 of the entire normalized, pre-runtime, loaded initial world. `terrainIdentity` remains the existing full engine-terrain digest. Modern pairing revision is `engine-pairing-v1:sha256:` plus SHA-256 of recursively key-sorted JSON (array order preserved) containing exactly public scenario ID, resolved scenario ID, scenarioRevision, terrainIdentity, assemblyVersion, mapId and pairingId. Display names/source labels/preview cosmetics are excluded. No legacy revision alias is accepted as a modern revision: old clients send no pairing and continue using the default. The native assembly version fixes existing millimetre quantization, engine terrain kinds/attributes, crossings, layer/ID precedence and implicit OPEN_GROUND semantics. Changing those semantics requires a new assembly version; this does not promise replay across arbitrary engine changes.

The alternative is an explicit retained authored definition, never computed from a future latest default. Its authored bytes, loaded-world digest and unchanged-army assertions are frozen in tests. It stays internal/unavailable in the public selectable list until chunk3 acceptance. Distinguish `unknown_pairing`, `stale_pairing`, `foreign_scenario`, `invalid_battlefield` and `unavailable_pairing`; reject them before effects.

### Private pin and decoder

Choose a private `NativeScenarioPinV1` containing pin schema1, assemblyVersion, public scenario ID, modern pairing/map descriptor, the complete time-zero loaded `initialWorld`, the exact authored raw scenario input needed to validate it, and full content digests. The raw input plus normalized world is deliberately redundant: durable decoding applies a strict resource-bounded raw-native schema, calls the real `loadScenario(raw)`, and requires exact canonical equality with stored `initialWorld`, scenario revision, terrain identity and pairing digest. Thus serialized engine state is never passed to the raw loader, cast to GameState, repaired, coerced or normalized into a replacement. Unknown fields, nonfinite values, placements/HQs/objective/crossing inconsistency and altered digests fail. Registration first obtains the world through loadScenario. Versioned decoder behavior is retained; incompatible engine semantics fail visibly rather than substituting current terrain.

Persist the pin inline in private lobby records and private input-log headers for this small release (bounded1MiB each); immutable digest equality reconciles the copies. No new assembly database or mutable lookup is needed. `LobbyGame.scenario` stays public; `InputLogHeader.scenarioId` stays resolved. All new records carry a format marker and pin, including default games. Their start, role/human-side checks, replay CLI/admin/backfill/critique/window and host recovery resolve that verified pin. Host applies dial/settings and initialization only afterward, identically for create/replay. Snapshot reopening verifies header/lobby/pin and recovered static map/scenario agreement without comparing dynamic unit positions to time-zero positions. Missing/contradictory new-format data is a visible failure. Only explicitly identified pre-pin historical bridge records use legacy registry fallback; record synthesis may not turn failed new-format recovery into a legacy game. Game information/room/list return only a fresh public projection; no private pin/raw/world spread.

### Lossless rendering and compatibility gate

Add an optional explicit layer to BaseFeature for backward-compatible existing fixtures; native descriptor adapters always set it. One paint-order helper uses explicit layer then reverse lexical ID tie order, so the lower lexical ID paints last/on top as in the engine. Legacy feature-kind fallback applies only when layer is absent. Both Three.js and flat board consume that same order; painters do not re-sort by kind afterward. Preserve geometry, extent, full widths and radii in metres. All game/window/picking/marks paths use the verified pinned public map.

Modern GameService obtains/validates the map before enabling scene interaction and publishes it only for its current connection token. Loading/failure/retry is explicit; missing new-format metadata never means fixture terrain. Modern REST seating/join and live WebSocket requests advertise `battlefieldVersion=1` (GET/join query for the existing endpoint shapes). Alternative games reject an absent/unsupported capability before seating or opening a side stream, with readable `battlefield_client_upgrade_required`. Default legacy clients retain existing behavior. The initial alternative creator also supplies this capability. Existing seats following an invite do not bypass this check. Public descriptors and the modern client add no master-state channel.

### Numeric/resource limits

IDs128 characters, display names160, versioned digests160; dimensions1–20,000m; coordinates finite, inside extent and representable in integer millimetres; widths/radii positive and no larger than the larger dimension. Layers are integers−1024…1024. At most128 features with unique IDs,1024 points per geometry and4096 total point entries, with existing shape-specific minima. Individual public descriptor64KiB and whole scenarios response256KiB UTF-8; collection16 pairings maximum. Private pin1MiB, exactly two sides and at most128 units, bounded strings and collections under a strict schema. Create body16KiB. Iterative preflight counts depth/nodes/strings/arrays before Zod clones/expensive work; JSON byte budgets and aggregate checks also apply. Cache detached validated authored descriptors/pins rather than reloading on each request. These limits do not establish canonical-library/generation budgets.

### Creation receipt, transaction and recovery

Modern create accepts optional atomic `pairing: { pairingId, revision }` and `requestId: UUID`; the modern UI always sends requestId, including default play. Legacy no-key requests retain current semantics. Receipt states are `reserved`, `lobby` or `started`, with an explicit recoverable activation error alongside a reserved receipt. Receipt includes allocated gameId, pin, normalized effective choices/default context, normalizer version, fingerprint and result; accepted intent is immutable. Normalize retries using the receipt's accepted default context, not latest catalog/defaults; compare every effective scenario/pairing/side/session/lobby/timing/dial/persona/hierarchy/pause choice. Changed effective intent returns409. Same effective intent returns/resumes the same allocated game before limits/default resolution. Object-key order is irrelevant.

Use a shared borrowed SQLite DatabaseSync for auth seats, lobby and creation receipts. One `BEGIN IMMEDIATE` unit of work writes receipt, pinned lobby record and seat reservation together; no await or actor/model call inside it. Constructors retain owned-handle defaults for compatibility/tests and do not close borrowed handles. Game log/snapshot storage may use its separate existing connection: actor activation occurs after commit and is recoverable using the allocated gameId/pin. Equivalent in-memory reservation is synchronously serialized but makes no restart durability claim. Failures before commit roll back all effects. Activation failures retain the receipt/gameId; retries reconcile header/snapshot/pin before resuming. A matching existing actor/snapshot is opened/returned, never recreated. Header-only interrupted creation is resumed only after verifying exact pin/settings and absence of conflicting inputs; inconsistent partial storage yields explicit recovery failure with the original receipt retained. Never allocate another ID to hide it.

Authenticated `GET /game-creations/:requestId` returns owner-only `pending`, `lobby`, `started` or `recovery_required` plus the existing gameId when accepted; unknown is404 and conveys no other owner's record. The client retains its request key through network/5xx ambiguity and reconciles before enabling a new submission. Explicit validation/auth/limit rejections before acceptance remain definite; a generic5xx is not proof of no creation. Activation retry uses the same key. Receipts are retained at least as long as games/logs, with a tombstone preventing reuse if a game is later removed.

Store receipts by immutable receipt ID/original-owner+request key with mutable current owner. Guest adoption transfers current ownership and all indexes on the same SQLite transaction as auth adoption (and lobby reassignment), rather than an after-commit callback. If the target already has that request UUID, preserve both owned receipts and mark the owner/key lookup ambiguous; return409 with the target's own existing game IDs for reconciliation, never overwrite either or create a third game. Other accounts' same UUIDs remain inaccessible. Deletion/guest expiry follows existing privacy policy while retaining inaccessible receipt tombstones/pins with retained games; no dangling readable ownership or cross-account lookup. Fault/concurrency/restart/adoption tests gate the durable claim.

Chunk2 may implement only authored definitions, bounded schemas, pure identities/pin codec/resolver and focused headless/replay/privacy tests. Chunk3 owns actual transaction/receipt/API/renderer enablement and must pass its integration gates before public alternative readiness. Writer release to a pure public render adapter can follow independent schema acceptance; services/API/config remain coordinator-owned.
